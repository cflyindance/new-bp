## 一、背景与目标

### 1.1 业务场景

在商家后台对功能进行修改时，需要进行**保存并下发**操作。下发的目的是将商家后台的设置同步到本地系统，包括本地 POS、本地 Kiosk、本地 eMenu 等终端，替代原先在终端本地各自维护配置的模式。

### 1.2 建设目标

1. **云端 SSOT**：商家后台为配置单一事实来源，终端为缓存与执行端。
2. **下发可追溯**：新增下发记录，能记录每个导航中某个菜单、某个功能的下发状况。
3. **连锁可治理**：支持集团/品牌/门店多级作用域，批量下发与失败重试。
4. **产线差异化**：同一配置可能只影响 POS，或同时影响 POS + Kiosk + eMenu（store-wide）。

### 1.3 与 PRD 的对应关系

| PRD 编号 | 需求 | 本方案覆盖 |
|----------|------|------------|
| FR-3.1 ~ FR-3.5 | POS/Kiosk/eMenu 配置上云、产线 scope | 配置域 + 同步协议 |
| FR-3.6 | 门店/品牌/集团级下发 | 下发目标选择 + Batch |
| FR-3.7 | 离线缓存、增量同步、设备状态 | Push + Pull + Target ACK |
| FR-3.8 | 审计日志 | 下发记录引用 auditLogId |
| FR-3.9 | 版本回滚 | rollback 触发 resync |
| NFR-1 | 下发端到端 < 60s | 异步 Job + 状态轮询 |
| NFR-6 | sync 成功率可监控 | DeploymentBatch 汇总指标 |
| US-04 | 集团菜单下发 + 下发记录 | `brand.menu` 域 + distribution-log |

## 二、核心设计原则

| 原则 | 说明 |
|------|------|
| **保存 ≠ 下发** | 保存只写云端草稿/已发布配置；下发是独立的「推送到终端」动作 |
| **配置域聚合** | 不按单个 L4 seq 逐条下发，而是按**配置域（Config Domain）**打包，减少碎片化和终端压力 |
| **导航可追溯** | 下发记录必须能反查到 L1→L4 导航路径，满足「哪个菜单/哪个功能」的审计诉求 |
| **产线差异化** | 同一配置域可能只影响 POS，或同时影响 POS+Kiosk+eMenu（store-wide） |
| **门店×设备两级** | 先确认门店级生效，再追踪到具体设备（POS 机、Kiosk 屏等） |

## 三、整体架构

```
┌─────────────────────────────────────────────────────────────┐
│  商家后台（云端 SSOT）                                       │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐   │
│  │ 设置页   │  │ 商品中心 │  │ 菜单管理 │  │ ...      │   │
│  └────┬─────┘  └────┬─────┘  └────┬─────┘  └────┬─────┘   │
│       └─────────────┴─────────────┴─────────────┘         │
│                         │                                    │
│              ① 保存 → 配置草稿层 / 已发布配置层（versioned） │
│              ③ 保存并下发 → 下发编排服务                     │
│                         │                                    │
│              ④ 生成 Deployment Job → 下发记录中心            │
└─────────────────────────┼───────────────────────────────────┘
                          │ ⑤ Push 通知 / Pull API
                          ▼
┌─────────────────────────────────────────────────────────────┐
│  门店本地                                                    │
│  ┌──────────────┐                                           │
│  │ Sync Agent   │ ← 心跳、拉取、ACK                         │
│  └──────┬───────┘                                           │
│         ├── POS 终端                                        │
│         ├── Kiosk                                           │
│         └── eMenu                                           │
└─────────────────────────────────────────────────────────────┘
```

与 PRD 治理链路的衔接：

```
M 平台（蓝图/预设）→ 商家后台（经营配置）→ 下发编排 → 终端生效
```

> **说明**：平台预设的 sync（`aligned` / `customized` / `outdated`）管的是**导航可见性**；本方案管的是**经营配置内容**（菜单、营业时间、打印路由等）的下发，两者独立但可在 UI 上统一展示「同步状态」。

## 四、配置域（Config Domain）

### 4.1 为什么需要配置域

不建议以「每个 L4 seq」或「每个菜单项」作为下发单元——472 个 seq 会产生海量碎片任务。建议在 catalog 上为每个 seq 标注所属的**配置域**，作为下发的最小业务单元。

### 4.2 配置域注册表

```typescript
/** 配置域注册表示例 */
interface ConfigDomain {
  domainKey: string;           // 如 "store.hours", "brand.menu", "pos.print-routing"
  displayName: string;         // "营业时间", "品牌菜单", "打印路由"

  // 导航追溯（可多个 L4 归属同一域）
  navRefs: Array<{
    l1Key: string;             // 如 "store-mgmt"
    l2Key: string;             // 如 "store-hours"
    l3GroupKey?: string;
    seqIds?: number[];         // 关联的 L4 seq
  }>;

  // 产线影响范围
  scope: 'store-wide' | 'product-line';
  productLines: ProductLine[]; // POS | Kiosk | eMenu | ...

  // 下发策略
  syncMode: 'immediate' | 'scheduled' | 'manual-only';
  bundleWith?: string[];       // 依赖/捆绑域，如菜单变更自动带上渠道可见性

  // 数据形态
  payloadType: 'settings-kv' | 'menu-tree' | 'asset-binary' | 'composite';
  apiEndpoint: string;         // 终端拉取的 API path

  // 下发粒度
  granularity: 'store' | 'device';  // 门店级 or 设备级
}
```

### 4.3 配置域与导航映射示例

| 配置域 | 导航路径 | 影响产线 | 下发粒度 |
|--------|----------|----------|----------|
| `brand.menu` | 商品中心 → 品牌菜单 | POS + Kiosk + eMenu | 品牌级 → 多门店 |
| `store.hours` | 门店管理 → 营业时间 | store-wide | 门店级 |
| `pos.print-routing` | 打印中心 → 厨打路由 | POS | 门店级 → 按设备 |
| `kiosk.homepage` | 前厅 → Kiosk 首页 | Kiosk | 门店级 |
| `settings.payment` | 支付中心 → 支付方式 | store-wide | 门店级 |

### 4.4 与现有导航节点的关系

商品中心里已有的「下发记录」页面（`/brand-menu/distribution-log`）可视为 `brand.menu` 域的**专页视图**；全局下发记录中心则聚合所有配置域。

## 五、「保存并下发」交互流程

### 5.1 两种保存模式

| 操作 | 行为 |
|------|------|
| **保存** | 仅写云端，终端仍使用上一版已下发配置 |
| **保存并下发** | 写云端 + 触发下发 Job |

### 5.2 下发编排流程

```
用户点击「保存并下发」
    │
    ├─ 1. 校验：Scope（集团/品牌/门店）、RBAC、产线开通
    ├─ 2. 保存配置 → 生成 configVersion（如 v42）
    ├─ 3. 解析本次变更涉及的 configDomain 列表
    ├─ 4. 展开下发目标：门店列表 × 产线 × 设备（可选）
    ├─ 5. 创建 DeploymentBatch（批次）
    ├─ 6. 为每个 (门店, 域) 创建 DeploymentItem
    ├─ 7. 异步推送 / 等待终端 Pull
    └─ 8. 收集 ACK → 更新状态 → 通知 UI
```

### 5.3 下发目标选择 UI（连锁场景）

```
下发范围：
  ○ 当前门店
  ○ 品牌下全部门店
  ○ 自定义选择门店 [多选]

下发内容预览：
  ✓ 品牌菜单（v42）→ 影响 12 家门店 × 3 产线
  ✓ 渠道可见性（v18）→ 自动捆绑
  ⚠ 打印路由 未变更，跳过

预计影响设备：POS ×28 · Kiosk ×12 · eMenu ×12
```

## 六、下发记录数据模型

### 6.1 四层记录结构

```
DeploymentBatch（一次下发操作）
  └── DeploymentItem（门店 × 配置域）
        └── DeploymentTarget（门店 × 产线 × 设备）
              └── DeploymentAck（设备回报）
```

### 6.2 核心表结构

```typescript
/** 下发批次 — 对应用户一次「保存并下发」操作 */
interface DeploymentBatch {
  id: string;
  merchantId: string;

  // 操作上下文
  triggeredBy: string;          // 操作人
  triggeredAt: string;
  triggerSource: 'manual' | 'scheduled' | 'rollback' | 'bulk';

  // 数据视角
  scopeLevel: 'group' | 'brand' | 'store';
  brandId?: string;
  storeIds: string[];           // 目标门店

  // 配置版本快照
  configVersions: Record<string, number>;  // domainKey → version

  // 导航追溯（供 UI 展示「从哪个菜单发起」）
  originNav: {
    l1Key: string;
    l2Key: string;
    l3GroupKey?: string;
    pagePath: string;           // 如 /brand-menu/menus
  };

  // 关联审计
  auditLogId?: string;

  // 批次状态
  status: 'pending' | 'in_progress' | 'partial_success' | 'success' | 'failed' | 'cancelled';

  // 汇总
  totalItems: number;
  successCount: number;
  failedCount: number;
  pendingCount: number;
}

/** 下发项 — 门店 × 配置域 粒度 */
interface DeploymentItem {
  id: string;
  batchId: string;

  storeId: string;
  storeName: string;
  domainKey: string;            // 如 "brand.menu"
  domainDisplayName: string;    // "品牌菜单"

  configVersion: number;
  productLines: ProductLine[];  // 该域影响的产线

  status: 'pending' | 'pushing' | 'success' | 'failed' | 'skipped' | 'timeout';
  errorCode?: string;
  errorMessage?: string;

  pushedAt?: string;
  completedAt?: string;
  retryCount: number;
}

/** 下发目标 — 设备级（POS 打印等需要精确到设备） */
interface DeploymentTarget {
  id: string;
  itemId: string;

  storeId: string;
  productLine: ProductLine;
  deviceId: string;
  deviceName: string;           // "收银台1号机"

  status: 'pending' | 'syncing' | 'success' | 'failed' | 'offline';
  localVersion?: number;        // 终端确认的版本
  ackedAt?: string;
  errorDetail?: string;
}
```

### 6.3 状态机

```
Batch:  pending → in_progress → partial_success | success | failed
Item:   pending → pushing → success | failed | timeout
Target: pending → syncing → success | failed | offline
```

> `partial_success` 很重要：连锁 12 家店里 10 家成功、2 家离线，批次不能标为全失败，要支持**对失败项重试**。

### 6.4 门店配置游标

```typescript
interface StoreConfigCursor {
  storeId: string;
  domains: Record<string, {
    cloudVersion: number;      // 云端最新已发布
    deployedVersion: number;   // 上次成功下发到终端
    localVersion: number;      // 终端回报的实际版本
    lastDeployedAt: string;
    lastAckedAt: string;
  }>;
}
```

## 七、云端 ↔ 本地同步协议

### 7.1 推荐：Push 通知 + Pull 拉取（混合模式）

| 阶段 | 机制 | 说明 |
|------|------|------|
| 触发 | WebSocket / MQTT / FCM | 云端通知「store-123 有 menu v42 待同步」 |
| 拉取 | REST / gRPC | 终端按 domain 增量拉取 payload |
| 确认 | ACK API | 终端回报 `deviceId + domain + version + status` |
| 兜底 | 定时轮询 | 离线设备联网后按 `lastSyncedVersion` 增量补拉 |

### 7.2 终端 Sync API 设计

```
GET  /api/stores/{storeId}/sync/manifest
     → 返回各 domain 的 latestVersion、checksum

GET  /api/stores/{storeId}/sync/{domainKey}?sinceVersion=41
     → 返回 v42 的增量或全量 payload

POST /api/stores/{storeId}/sync/ack
     Body: { deviceId, domainKey, version, status, errorCode? }
```

### 7.3 冲突策略

| 场景 | 策略 |
|------|------|
| 云端新下发 vs 终端本地旧版 | 云端优先（SSOT） |
| 终端离线期间云端多次更新 | 拉取最新版，跳过中间版 |
| 终端本地有未上报的脏改（迁移期） | 标记 conflict，Dashboard 告警，人工处理 |
| 下发中用户再次保存 | 合并为新 batch，旧 batch 中未完成的 item 可取消或继续 |

### 7.4 失败处理原则

下发失败时，终端**继续用上一版有效配置**——不回滚云端，不清空本地。

## 九、与现有概念的关系

| 概念 | 职责 | 关系 |
|------|------|------|
| **审计日志**（FR-3.8） | 记录谁改了什么（旧值→新值） | 下发记录引用 `auditLogId` |
| **平台预设 sync** | 导航可见性（M→企业→商家） | 独立链路，不触发终端下发 |
| **配置版本** | 云端每次发布的 version | 下发记录携带 `configVersion` |
| **设备心跳** | 设备在线状态 | 下发 Target 的 offline 判定依据 |

## 十一、关键设计决策（待产品确认）

| # | 决策点 | 建议 |
|---|--------|------|
| 1 | **下发粒度** | 默认「配置域」级；部分场景（如单品停售）是否支持「即时推送」绕过批次？ |
| 2 | **保存并下发是否默认** | 高频操作（停售）建议自动下发；低频大改（整本菜单）建议二次确认 |
| 3 | **设备级 vs 门店级** | POS 打印路由需要设备级；营业时间门店级即可。domain registry 需标注 `granularity` |
| 4 | **失败是否阻断营业** | 下发失败时终端继续用上一版有效配置 |
| 5 | **下发记录保留期** | 建议 90 天在线 + 归档，与审计日志对齐 |

## 附录 B · 术语表

| 术语 | 定义 |
|------|------|
| **配置域（Config Domain）** | 下发的最小业务单元，聚合一个或多个 L4 seq |
