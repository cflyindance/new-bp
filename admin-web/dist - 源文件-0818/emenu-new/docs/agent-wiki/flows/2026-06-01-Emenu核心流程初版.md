# Emenu 核心流程初版

## 已确认事实

- 本文只记录从源码结构、调用关系和现有配置中可确认的流程。
- 业务含义未由用户确认的内容，放在“从结构观察到”或“待确认问题”中。
- 主要流程证据来自 `src/index.jsx`、`src/App.jsx`、`src/pages/Index.jsx`、`src/hooks/useClientLogin.js`、`src/hooks/useSetMenus.js`、`src/hooks/useFetchOrder.js`、`src/services/*.js` 和 `src/store/slices/systemConfig.slice.js`。

## 关键入口

- 应用启动：`src/index.jsx`
- 应用路由和初始化：`src/App.jsx`
- 顶层业务容器：`src/pages/Index.jsx`
- 登录/license：`src/hooks/useClientLogin.js`、`src/services/system.js`
- 配置读取/保存：`src/store/slices/systemConfig.slice.js`、`src/services/setting.js`
- 菜单加载：`src/hooks/useSetMenus.js`、`src/services/menus.js`
- 订单读取：`src/hooks/useFetchOrder.js`、`src/services/orders.js`
- 订单生成/保存/送厨：`src/services/orders.js`、`src/hooks/useSendKitchen.js`
- 消息发送：`src/hooks/useSendMessage.js`、`src/services/system.js`
- CRM/会员初始化：`src/App.jsx`、`src/services/crm.js`、`src/crm/`、`src/services/crmIntegration*.js`

## 应用初始化流程

1. `src/index.jsx` 引入 `./i18n` 并调用 `initLanguageCode()` 初始化语言。
2. `src/index.jsx` 创建 Material UI theme，并设置项目主色、圆角、按钮、对话框、图标、Backdrop 等样式覆盖。
3. `src/index.jsx` 使用 `Provider` 注入 Redux store。
4. `src/index.jsx` 使用 `HashRouter` 包裹 `App`。
5. `src/App.jsx` 懒加载页面，并定义主要路由。
6. `src/App.jsx` 挂载时读取本地存储中的语言、桌台、区域等信息。
7. 非设置页调用 `effects.initConfig({ tableName, tableId })` 初始化配置。
8. 设置页通过 `window.parent.postMessage({ type: 'getSessionKey' }, '*')` 请求 session key，再调用 `effects.fetchConfig({ isSettingInit: true })` 拉取配置。

## License 和 Session 流程

1. `src/pages/Index.jsx` 通过 `listAppInstances` 获取 EMENU 类型 app instances。
2. 未选择 license 且不在设置页时，`src/pages/Index.jsx` 打开 `ChooseLicense`。
3. 用户选择或新建 license 后，`src/hooks/useClientLogin.js` 调用 `clientLogin`。
4. `clientLogin` 成功后，`useClientLogin` 组装并暂存 `instanceName`、`secretKey`、`sessionKey`、`LastLoginTime`、`sessionExpireTime`。
5. 如果设备存在 `window.deviceUuId`，`useClientLogin` 会结合 `deviceBindInfo` 和 `configList.deviceConfig` 检查 license 与设备绑定关系。
6. 检查通过后，登录信息写入本地状态，关闭选择弹窗并刷新页面。
7. `src/utils/request.js` 在响应中发现 session key 失效时，会调用 `/license/clientInstanceLogin` 刷新 session key，并重试原请求。

## 配置流程

1. `src/store/slices/systemConfig.slice.js` 通过 `getEmenuConfig(sessionKey)` 获取 `product: 'EMENU'` 的配置。
2. `initConfig` 在没有配置时构造默认全局配置和当前设备配置。
3. 已有配置时，`initConfig` 合并后端配置和 `ALL_CONFIG_ITEM`，以补齐新增配置项。
4. 当前设备存在 `window.deviceUuId` 时，`initConfig` 会用设备信息补齐或更新设备配置。
5. `setConfig` 将配置 JSON 字符串通过 `setEmenuConfig` 保存到后端。
6. `fetchEmenuProConfig` 使用 `getEmenuProConfig(sessionKey)` 获取 `product: 'EMENUPRO'` 的配置并保存到 Redux。

## 菜单加载流程

1. `src/hooks/useSetMenus.js` 的 `runGetMenus` 调用 `src/services/menus.js` 的 `getMenus`。
2. `getMenus` 请求 `/menu/menu`，默认参数包含 `product: 'EMENU'`、`showInactive: false`、`showDeleted: false`。
3. `useSetMenus` 调用 `transformMenus` 保存菜单源数据到 `Menu_Source`。
4. `transformMenus` 处理菜单组、分类、菜品、combo、option、价格、标签、多语言资源等前端结构。
5. `useSetMenus` 获取餐厅营业时间和 POS 系统时间。
6. `filterMenuByHour` 按营业时间过滤菜单组。
7. `useSetMenus` 根据配置继续处理显示菜单、品牌/品类模式、特殊菜单、锅底下单后显示等前端过滤逻辑。
8. 处理后的菜单写入 `All_Menus` 和 `Temp_Menus` 等全局状态。

## 订单读取流程

1. `src/hooks/useFetchOrder.js` 从本地 `emenu_table` 读取当前订单。
2. 如果存在当前订单或父订单 id，调用 `src/services/orders.js` 的 `fetchOrder` 请求 `/order/fetch`。
3. 返回订单为空时，将全局 `Orders` 清空。
4. 如果订单状态为取消、支付、清台、系统作废，或订单桌台与当前桌台不一致，则清理当前订单、购物车、会员、buffet、分类和权限相关状态，并回到首页。
5. 有效订单会写回 `emenu_table.currentOrder`。
6. `transformOrder` 将接口订单转换为前端订单结构。
7. 转换后的订单写入全局 `Orders`。
8. 订单扩展字段 `emenuKioskextendedInfo` 会被解析，用于恢复菜单分类、用餐时长、特殊菜单、buffet 等 EMENU 扩展数据。

## 订单生成、保存和送厨流程

1. `src/services/orders.js` 的 `generateOrder` 根据购物车、桌台、用户、配置、税、服务费、会员/CRM、buffet 等信息生成后端订单结构。
2. `generateOrder` 会把 EMENU 扩展数据写入 `emenuKioskextendedInfo`。
3. `generateOrder` 会将生成结果暂存到 `localStorage.emenu_temporarily_order`。
4. `saveOrder` 调用 `/order/save` 保存订单，并附带 `userAuth.sessionKey`。
5. `sendKitchen` 调用 `/print/kitchen/ticket` 发送厨房打印。
6. `src/hooks/useSendKitchen.js` 根据延迟送厨配置计算每个菜品的 delay，再调用 `sendKitchen`。
7. `printReceipt` 调用 `/print/receipt` 打印收据。

## 消息发送流程

1. `src/hooks/useSendMessage.js` 根据系统配置开关决定是否允许发送不同类型通知。
2. 支持的通知类型包括 call server、checkout、new order、edit order、add water、tableware、napkin、add soup broth、change grill top、order drinks 等。
3. 允许发送时调用 `src/services/system.js` 的 `saveMessage`。
4. `saveMessage` 向后端提交 sender 为 `EMENU`、topicName 为 `EMENU` 的消息。

## CRM 和会员流程

1. `src/App.jsx` 通过 `useIsMemberLogin` 获取 `crmStatus`、`crmType`、`crmProvider`。
2. 当 CRM 开启且类型为 `2` 时，调用 Avocado 相关 Redux effect 获取活动列表。
3. 当 CRM 类型为 `1` 时，调用 `searchRewardRule`、`getPointRule`、`searchPrivileges`、`getAllMenu` 初始化奖励规则、积分规则、权益和会员权益菜品。
4. 当 `crmProvider === CRM_PROVIDER.INTEGRATION` 时，`src/App.jsx` 调用集成型 CRM provider 的 `fetchBootstrapData`。
5. 集成型 CRM bootstrap 结果会保存到 `crmProviderSlice`，包含 rewards 和 metaData。
6. `src/services/orders.js` 在订单生成和转换中读取 CRM integration validation 状态，用于写入折扣和权益相关信息。

## 状态和 API 位置

- 全局 UI/业务状态：`src/hooks/useGlobalState.js`

- 本地存储工具：`src/utils/storage.js`
- axios 请求实例：`src/utils/request.js`
- 配置接口：`src/services/setting.js`
- 系统/license/消息接口：`src/services/system.js`
- 菜单接口和转换：`src/services/menus.js`
- 订单接口和转换：`src/services/orders.js`
- CRM 接口：`src/services/crm.js`、`src/services/crmIntegration*.js`

## 从结构观察到

- 普通点餐页和 Emenu Pro 点餐页通过系统配置切换。
- 菜单和订单结构转换逻辑集中在 service 层，页面和 hooks 主要负责状态读写与流程编排。
- CRM integration 近期有较多计划文档和测试脚本，是当前项目中的高频演进区域。

## 待确认问题

- 普通点餐页与 Emenu Pro 点餐页的业务边界是否只由配置项 `63` 控制。
- CRM 类型 `1`、`2` 和 `CRM_PROVIDER.INTEGRATION` 的业务命名，需要产品或后端文档确认。
- `emenuKioskextendedInfo` 的字段规范是否有后端/跨端文档。
- `scripts/*.test.mjs` 是否是团队认可的回归测试入口。
