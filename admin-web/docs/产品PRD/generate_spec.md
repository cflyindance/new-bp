# 手动兜底：从现有代码逆向生成 PRD + 技术规格

> 优先使用项目 Skill：`.cursor/skills/export-prd-spec/`（对话中说「导出 PRD/规格」）。  
> 本文仅在 Skill 未触发时使用。完整模板见该 Skill 的 `references/`。  
> 设计：`docs/superpowers/specs/2026-07-28-export-prd-spec-design.md`

## 角色

你同时扮演产品经理与技术架构师：从指定范围内的原型代码提取业务逻辑，输出 **PRD + SPEC + DIFF** 三件套。

## 输入

1. **必须**：用户指定的范围（模块名 / 页面 / 文件或目录）— 禁止整仓盲扫  
2. 可选：2～3 句业务目标  
3. 分析材料（范围内）：types/enums、store、`*-ui.ts`、permissions、路由、`docs/` 设计稿  

## 输出目录

```
docs/产品PRD/exports/YYYY-MM-DD-<scope-slug>/
  ├── PRD.md
  ├── SPEC.md
  └── DIFF.md
```

同日同范围再导出使用 `-v2`，不覆盖。

## 需求编号

`<PREFIX>-<序号>`（如 `TIP-01`）。前缀由 scope-slug 得 3～5 位大写缩写。表格列：编号 | 需求类型 | 需求描述 | 关联编号。

## PRD.md 必备章节

1. 元信息（范围、版本、日期、代码依据、互链）  
2. 背景与目标（缺则「待产品补充」）  
3. 角色与权限边界  
4. In / Out  
5. 核心场景（Mermaid）  
6. 功能需求清单  
7. 用户故事 + Given/When/Then  
8. 页面/入口清单  
9. 非功能（无则 N/A）  
10. 开放问题  

## SPEC.md 必备章节

1. 规格元信息与证据清单  
2. 术语与枚举  
3. 数据模型字段表  
4. 状态机（无则 N/A）  
5. 核心业务逻辑（输入/输出/伪代码/异常，互链 PRD 编号）  
6. 交互与 UI 契约  
7. 接口/存储契约（无真实 API 不编造；可写「建议契约」并标推测）  
8. 权限与作用域  
9. 边界与并发  
10. 实现检查清单  

字段表示例：

| 字段名 | 类型 | 必填 | 默认值 | 说明 | 约束/校验规则 |
|--------|------|------|--------|------|---------------|
| id | string | 是 | 自动生成 | 主键 | UUID v4 |

## DIFF.md

| 类型 | 说明 | 证据 | 建议处理 |
|------|------|------|----------|
| 代码有、意图未写清 | … | path | 补 PRD |
| 意图有、代码未做 | … | PRD 编号 | 标原型未实现 / 补代码 |
| 行为冲突 | … | … | 待 PM 裁决 |
| 推测项 | … | … | 置信度 + 建议 |

## 分析策略

1. 定范围 → 列文件（大范围先确认）  
2. types → store → UI → permissions → 路由 → docs  
3. 挖隐式规则（if/switch、禁用、空态、默认值、视角差异）  
4. 先写 SPEC，再写 PRD，最后 DIFF  
5. 自检：证据可追溯、编号闭环、不编造、三件套齐全  

## 语言与格式

- 简体中文；标识符保留英文  
- Markdown + 表格 + Mermaid  
- 关键结论旁注明代码路径或符号
