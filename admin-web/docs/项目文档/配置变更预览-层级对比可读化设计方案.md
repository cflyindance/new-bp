# 配置变更预览 · 层级对比可读化设计方案

> **模块**：功能设置「确认变更」弹窗 + 下发「变更记录」详情（共用预览）  
> **版本**：v1.0  
> **日期**：2026-07-22  
> **状态**：已落地  
> **关联实现**：`deployment-change-preview.ts`、`module-settings-deployment-change.ts`、`page-save-confirm-dialog.ts`、`deployment-ui.ts`

---

## 一、背景与问题

### 1.1 现状

保存并下发时弹出「确认变更」；下发列表可打开「变更记录」详情。二者共用 `renderChangePreviewDialog` / `renderChangePreviewSections`。

当前体验问题：

| 问题 | 影响 |
|------|------|
| 左右双栏整块对比 | 多行/多子项时难对齐，改前改后不易逐项对应 |
| 无导航层级 | 同一批次多设置项时缺少「属于哪一页」的上下文 |
| 原代码/JSON 直出 | `formatConfigDisplayValue` 对 object 使用 `JSON.stringify`，用户看到原始结构 |

### 1.2 目标

1. **按导航层级分组**，再展示设置项  
2. **配置值按结构展开**（产线、子字段等）  
3. **逐行「改前 → 改后」**，一眼看清差异  
4. **禁止默认路径展示 JSON/原代码**；已知类型走专用文案，其余对象拆字段  

### 1.3 非目标

- 不改平台预设「变更记录」UI  
- 不引入通用 JSON Diff 引擎  
- 不提供「查看原始 JSON」入口  
- 不改下发协议 / 后端 API  

---

## 二、方案定稿

**渲染层结构化写入 + 预览层层级渲染**（方案 2）

- 写入变更时产出可选结构化明细 `details` 与分组路径 `groupPath`  
- 预览统一：导航分组 → 设置项卡片 → 子项逐行对比  
- 保留 `before` / `after` 摘要字符串，兼容旧历史记录  

---

## 三、信息架构

```
确认变更 / 变更记录（同一预览壳）
└── 导航分组（如：前厅管理中心 / 设置 / 账户安全与授权）
    └── 设置项卡片（功能名 + 新增|修改|删除 徽标）
        └── 子项行：子项名 | 改前 | → | 改后（改后高亮）
```

### 3.1 分组规则

- 优先使用写入时的 `groupPath`  
- 缺失时由 `settingsPath` 解析为 `l1Title / l2Title`（复用 `resolveOriginNavFromPath` 一类逻辑）  
- 仍无法解析时归入「其他变更」  

### 3.2 逐行对比规则

- 有 `details`：每个 detail 一行  
- 无 `details`：整值作为单行「配置值」对比（纯文本，非代码块）  
- 仅展示 before ≠ after 的子行（写入侧已过滤；预览侧再兜底过滤）  
- 简单开关同样一行：`关闭 → 开启`  

### 3.3 操作徽标

沿用现有推断：改前空 → 新增；改后空 → 删除；否则修改。徽标展示 `operation` 文案（若有），否则用新增/修改/删除。

## 四、数据模型

在 `DeploymentConfigChange` 上扩展（均可选，向后兼容）：

```ts
interface ChangeDetailRow {
  key: string;
  label: string;
  before: string;
  after: string;
}

interface DeploymentConfigChange {
  fieldKey?: string;
  label: string;
  operation?: string;
  before: string;   // 摘要，兼容旧数据与列表摘要场景
  after: string;
  settingsPath?: string;
  /** 导航分组路径，如 ["前厅管理中心", "设置", "账户安全与授权"] */
  groupPath?: string[];
  /** 结构化子行；预览优先使用 */
  details?: ChangeDetailRow[];
}
```

### 4.1 摘要与相等性（强制）

缓冲层当前用 `before === after` 判断是否丢弃/合并消除变更。因此：

- **禁止**将有实质差异的两侧摘要都写成相同文案（例如两侧都是「2 项变更」）  
- 有 `details` 时，摘要采用 **首行差异拼接**：改前取前 **2** 条子行的 `label：before`，改后取对应 `label：after`，超出加「等 N 项」，保证两侧摘要通常不同且对称可读  
- 相等性判断升级为：  
  1. 若存在 `details`：按 `key` 对齐后，任一行 `before !== after` 即视为有变更；合并时按 `key` 合并 detail 行，再重算摘要  
  2. 若无 `details`：仍用 `before === after`  

无 `details` 时，`before` / `after` 保持可读单值（与现网一致）。

## 五、可读化规则

优先级（从高到低）：

1. **已知类型专用格式**  
   - 开关 / 勾选 → 开启/关闭  
   - 适用产线 → 产线中文名列表  
   - 按产线配置（如 seq 75 / 111 / 582）→ 每产线一行可读文案（写入为 `details`，而非仅多行字符串）  

2. **通用对象拆字段**  
   - 浅层（建议深度 ≤ 2）展开为 `label: value`  
   - key 尽量映射中文（已有 field 标签缓存优先）；无映射则用可读化后的 key，仍禁止整段 JSON  

3. **数组**  
   - 元素含 `name` → 名称列表  
   - 否则 →「N 项」摘要，必要时前若干项展开为子行  

4. **禁止**  
   - 默认路径不再 `JSON.stringify` 整段展示给用户  

### 5.1 旧记录回退

预览时若无 `details`：

1. 若 `before`/`after` 为多行「标签：文案」格式 → 按行拆成 detail  
2. 若为 JSON 对象字符串 → 解析后走通用拆字段  
3. 仍失败 → 单行纯文本对比

## 六、UI 行为

- 「确认变更」与「变更记录」详情共用 `renderChangePreviewSections`（或其后继）  
- 弹窗壳（标题、取消/确认、关闭）不变  
- 去掉/不再依赖左右整块双栏作为主对比形态  
- `deployment-ui` 中若仍有旁路旧表格样式，与弹窗详情保持一致或复用同一渲染函数

## 八、验收点

1. 打开「确认变更」：变更按导航分组，设置项内子项逐行「改前 → 改后」  
2. 下发列表打开「变更记录」：与确认弹窗同构  
3. 修改按产线配置（如自动登出）：每产线一行，界面无 `{...}` JSON  
4. 修改普通对象类设置：字段列表可读，无代码块式原代码  
5. 打开仅含旧字符串明细的历史批次：可展示且不报错

## 九、实现备注

- 合并去重（`deployment-change-buffer`）时按 `key` 合并 `details` 并重算摘要；相等性见 §4.1  
- `groupPath` 写入侧尽量一次算好：优先 `resolveOriginNavFromPath` 的 L1/L2；若 `settingsPath` 能对应 catalog 的 `groupTitle`，作为第三段追加，否则仅 L1/L2  
- 现有 `normalizeChangeForDisplay`（预览侧对 75/111/582 等重格式化）：**保留作旧历史回退**；新写入已带 `details` 的记录预览优先渲染 `details`，不再二次整段重写  
- 视觉沿用现有 design token（border / muted / primary），新增/修改/删除徽标色与现状一致
