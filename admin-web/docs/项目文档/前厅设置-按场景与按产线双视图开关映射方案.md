# 前厅设置 · 按场景与按产线双视图开关映射方案

> **模块**：前厅管理中心 → 设置（`/operations/queue-call/settings`）
> **版本**：v1.1
> **日期**：2026-07-30
> **状态**：P0 已落地（结构体存储 + 按产线通用路径）；缺口二 / 缺口三 / 60 个模块迁移待做
> **选定路径**：方案 A —— `lines` 存储值改为 `{ v: 1, lines: [...] }` 结构体，从根上消除空数组二义性
> **相关文件**：`foh-settings-lines-codec.ts`、`foh-settings-lines-store.ts`、`foh-settings-by-line-toggle.ts`、`module-settings-form-ui.ts`、`page-settings-draft.ts`

---

## 一、背景与目标

### 产品语义（本方案的前提）

前厅设置有两种查看方式，共用同一份配置：

- **按场景**：功能按业务场景分组。同一个功能可能适用多条产线，用「适用产线」多选组表达 —— **勾选 = 该产线开启，未勾选 = 该产线关闭**。
- **按产线**：先选产线，再看该产线下的功能。此时每个功能对当前产线只有唯一状态，因此不出现多选组，直接给**开启 / 关闭开关**。

两个视图必须是同一份数据的两种投影：在按产线视图把 POS 关掉，回到按场景视图，该功能的 POS 复选框必须变成未勾选；反之亦然。

### 现状

映射机制已存在，单一数据源是 `lines[]` 数组：

- 范围矩阵 `FOH_LINE_SCOPE_BY_SEQ`（159 条）定义「功能允许出现在哪些产线」，属产品定义。
- 存储注册表 `FOH_LINE_STORAGE_BY_SEQ`（114 条）把 seq 映射到 localStorage 的 JSON 键，存「实际开在哪些产线」，属商户配置。
- 按场景视图渲染多选组，按产线视图渲染 `lines.includes(当前产线)`。

这两层分开是正确的，本方案不改变这个分层。

### 目标

1. 消除 `lines: []` 的二义性，使「全部关闭」不再被复活成「全部开启」。
2. 让全部 155 个非全店通用功能都具备按产线独立开关的能力（当前 41 个是全局的）。
3. 明确多产线 / 单产线 / 全店通用三类功能在两个视图下的展示形态。
4. 存量商户配置在升级后保持不变。

### 非目标

- 不改动范围矩阵 `FOH_LINE_SCOPE_BY_SEQ` 的产线归属。
- 不重构已有的 60 余个 `module-settings-*-ui.ts` 的面板 UI，只改其读写产线数组的那几行。
- 不引入后端接口，仍是 localStorage 原型。

## 二、映射规则

设 `scope(seq)` 为范围矩阵中该功能的产线集合，`lines(seq)` 为已开启产线集合，恒有 `lines(seq) ⊆ scope(seq)`。

| 方向 | 规则 |
|------|------|
| 按场景 → 按产线 | `开关(seq, line) = lines(seq).includes(line)` |
| 按产线 → 按场景 | 开 → `lines(seq) ∪ {line}`；关 → `lines(seq) \ {line}` |
| 产线是否可见 | `scope(seq).includes(line)`，不在范围内的功能在该产线下不渲染 |

写入始终落在 `lines(seq)` 上，两个视图没有各自的私有状态，因此不存在需要额外同步的第二份数据。

## 三、数据模型（方案 A）

### 存储值结构

fieldId 沿用现有命名（`<seq>-...-lines`），只替换值形态：

```ts
type FohLinesValue = {
  v: 1;
  lines: string[];
};
```

示例：

```json
{ "v": 1, "lines": ["pos", "paypad"] }
```

全部关闭时写入的是 `{ "v": 1, "lines": [] }`，而不是 `[]`。**结构体的存在本身就代表「已配置」**，于是 `lines: []` 唯一地表示「全部关闭」，不再需要靠额外的 seeded 标记或一次性播种来区分。这是选择方案 A 而非显式播种方案的核心收益。

### 读写收口

新增 `src/config/foh-settings-lines-store.ts`，所有产线数组的读写都经过它：

| API | 语义 |
|-----|------|
| `readFohLines(seq): string[] \| undefined` | `undefined` = 未配置；`[]` = 全部关闭 |
| `writeFohLines(seq, lines): void` | 始终写结构体，空数组也写 |
| `isFohLinesConfigured(seq): boolean` | 是否已有商户配置 |
| `resolveFohLines(seq): string[]` | 未配置时返回矩阵默认（即 `scope(seq)` 全选），**只读不落盘** |

`resolveFohLines` 是 UI 渲染与业务判断的唯一入口；`readFohLines` 只给需要区分「未配置」的场景用。

### 存量数据兼容

`readFohLines` 的解析优先级：

1. 值为 `{ v: 1, lines: [...] }` → 已配置，返回 `lines`（按 `scope(seq)` 过滤非法 ID）。
2. 值为**非空**裸数组 → 旧数据，视为已配置，返回该数组；同时就地升级为结构体。
3. 值为**空**裸数组 `[]` → 历史二义值，按**未配置**处理，不升级。
4. 键不存在 / JSON 解析失败 → 未配置。

第 3 条是有意的取舍：存量的 `[]` 无法判断是「老商户从没配过」还是「老商户全关了」，按现网行为一律当未配置（等价于全选）。这样升级不会让任何商户的功能突然全部关闭。新写入的空值一律是结构体，语义明确。代价是极少数「升级前刚好把某功能全部产线取消勾选」的商户，该功能会回到全选 —— 由于当前代码路径下这种状态本来就会被复活成全选，实际上没有行为退化。

### 全局镜像键

`bplant-module-setting-toggle:<seq>` 在前厅范围内停止维护。它的值等价于 `lines.length > 0`，可随时算出，且当前是绕过批量保存立即落盘的（见第五节）。非前厅 hub 的开关继续使用该键，不受影响。

## 四、缺口二：补齐 41 个功能的按产线存储

范围矩阵有 155 条非全店通用条目，注册表只有 114 个键，缺 41 个。缺失时 `writeFohByLineToggleState` 会落到全局镜像键：

```ts
if (lineId === "store-wide" || !hasFohLineStorage(seq)) {
  localStorage.setItem(moduleSettingToggleStorageKey(seq), on ? "1" : "0");
  return;
}
```

后果是在 POS 下关掉，POS GO 与 PayPad 一起关，且按场景视图看不到任何勾选变化 —— 映射断裂。

缺失的 seq：91、125、132、133、174、193–215、483–487、502、526、567、575、581、623、637–639。绝大多数是 `[pos, pos-go, paypad]`（点单页按钮显隐、工具栏配置那一批）与 `[kiosk, emenu, sdi, online-order]`。

### 处理

1. `scripts/generate-foh-line-storage-registry.mjs` 改为以范围矩阵为准生成：凡非 `store-wide` 条目一律产出键，新增的统一命名 `<seq>-lines`。
2. 按场景视图新增**通用适用产线多选组件**。这 41 个 seq 没有专属 UI 模块，不新建 41 个文件；写一个 generic renderer，产线选项直接取 `scope(seq)`，DOM 用 `data-foh-generic-lines="<seq>"` 统一绑定。已有 60 余个专用模块保持不动，后续可逐步收敛。
3. `scripts/verify-foh-line-scope.mjs` 增加断言：任何非 `store-wide` 的范围条目必须有对应存储键，防止后续新增功能再次遗漏。

## 五、缺口三：三类功能的展示形态

按当前数据，159 条中 4 条为全店通用，155 条非全店通用中 15 条仅适用单一产线。

| 类型 | 数量 | 按场景视图 | 按产线视图 |
|------|------|-----------|-----------|
| 多产线 | 140 | 适用产线多选组 | 单个开关 |
| 单产线 | 15 | 单个开关 + 「仅 Kiosk」类产线标签，不渲染多选组 | 单个开关 |
| 全店通用 | 4 | 单个开关 | 仅在「全店通用」节点出现 |

单产线功能渲染一个只有一个复选框的多选组是别扭的交互，改为开关加产线标签。全店通用继续直接读写全局开关键，形态不变。

### 按场景视图的状态可见性

`renderModuleSettingToggleSwitch` 当前对前厅 seq 恒返回开启并隐藏开关按钮：

```ts
if (isFohHubSettingToggleSeq(item.seq) && on) return "";
```

于是「一条产线都没勾」在语义上是关闭，但视觉上没有明确标识。建议在功能标题旁增加状态徽标，如「已开启 3/6 产线」或「未开启」，让两个视图语义对齐。

## 六、连带改动

### 批量保存一致性

前厅设置页启用页面级批量保存。`lines` 写入经 `writeModuleSettingJson` 会正确进入草稿层，但 `writeFohByLineToggleState` 末尾的全局镜像写入是立即落盘的，用户点「放弃」时 `lines` 回滚而镜像不回滚。停止维护镜像键后此问题自然消失。

### 下发预览的 product_line 识别

`isProductLineJsonField` 依赖 `Array.isArray(value)`：

```ts
function isProductLineJsonField(fieldId: string, value: unknown): boolean {
  if (!fieldId.includes("-lines") && !fieldId.endsWith("lines")) return false;
  if (!Array.isArray(value)) return false;
  if (value.length === 0) return true;
  const known = new Set(["pos", "emenu", "kiosk", "cds", "paypad", "sdi", "online-order"]);
  return value.every((v) => typeof v === "string" && known.has(v.toLowerCase()));
}
```

改为结构体后必然返回 `false`，`kind` 会从 `product_line` 退化成 `json`，下发预览文案会变。必须同步改造该函数以识别 `{ v, lines }`，并相应更新 `module-settings-deployment-change.ts` 的格式化逻辑。这是方案 A 的额外成本。

顺带修一个存量 bug：`known` 集合漏了 `pos-go`。由于大量前厅功能的产线数组形如 `["pos", "pos-go", "paypad"]`，`every` 检查当前就已失败，这些字段今天的 `kind` 就是错的。补上 `pos-go`，并改为直接引用 `FOH_LINE_NAV_ORDER` 以避免再次漂移。

## 八、验收标准

1. 按场景视图取消勾选某功能的全部产线并保存 → 切到按产线视图，各产线均显示关闭。
2. 按产线视图在 POS 下关闭某功能 → 回到按场景视图，该功能的 POS 未勾选，其余产线勾选状态不变。
3. 41 个原先缺存储的功能：在 POS 下关闭后，POS GO / PayPad 仍为开启。
4. 单产线功能在按场景视图渲染开关而非多选组。
5. 全店通用功能只在「全店通用」节点出现。
6. 存量商户数据升级后配置不变：非空裸数组原样保留，空数组与缺失键仍表现为全选。
7. 修改后不点保存直接离开 → 全部产线状态回到保存前，无残留。
8. 下发预览对产线字段仍识别为 `product_line`，含 `pos-go` 的数组不再误判。
9. `verify-foh-line-scope` 通过；非全店通用条目无缺失存储键。

## 九、决策记录

| 项 | 结论 |
|----|------|
| 空数组二义性 | 方案 A：结构体 `{ v: 1, lines: [] }`，不做一次性播种 |
| 存量空数组 | 按未配置处理，等价全选，保证升级无行为变化 |
| 全局镜像键 | 产线写入时同步；全部关闭写 `"0"`，以挡住各模块的空数组迁移回写 |
| 41 个缺失存储 | 由 generator 以范围矩阵为准全量生成（待做） |
| 41 个功能的场景视图 UI | 通用组件，不新建 41 个专用模块（待做） |
| 60 个专用模块迁移 | 分批推进，store 层同时兼容两种值形态（待做） |
| 单产线功能 | 开关 + 产线标签，不用多选组（待做） |
