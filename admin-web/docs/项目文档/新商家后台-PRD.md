## 一、文档概述

### 1.1 产品定位

**新商家后台**是 MenuSifu 面向餐饮商家的 **统一 Web 经营与配置平台**，用于替代分散在 POS 本地、Kiosk 云后台、eMenu 云后台及各产线独立系统中的配置与管理能力，并与 **M 平台（企业级控制台）** 形成「企业策略下发 → 商户经营配置 → 终端同步生效」的完整治理闭环。

### 1.2 建设首要目标

1. **POS / Kiosk / eMenu 本地配置上云** — 原分散在终端本地的设置项迁移至云端统一存储与下发。
2. **各云平台后台集成统一** — 收敛至单一商家 Web 后台，按 **业态 × 产线** 的平台预设控制可见能力。
3. **与 M 平台形成治理闭环** — M 平台负责导航蓝图、企业级预设、商户开通；商家后台继承企业策略，支持授权范围内局部覆盖。

### 1.3 产品形态概要

| 维度 | 说明 |
|------|------|
| **信息架构** | 约 28 个一级导航（品牌、门店、商品、订单、前厅/后厨、硬件等） |
| **配置树** | L1 侧栏模块 → L2 子入口 → L3 场景分组 → L4 设置项（seq），共 1201 节点 / 472 个 L4 设置 |
| **运行时视角** | 集团总部 / 品牌多门店 / 门店单店；同一 preset + RBAC + Scope 过滤 |
| **产线差异化** | 业态 × 产线（POS / Kiosk / eMenu 等 9 条）平台预设，非独立后台 |

## 二、背景说明（What）

### 2.1 行业与产品语境

MenuSifu 面向北美餐饮市场，为商家提供 **POS 收银、Kiosk 自助点餐、eMenu 桌边扫码点餐** 等多产线 SaaS 能力，并配套报表、会员、外卖、支付、硬件管理等经营模块。商家在日常运营中，需要频繁调整菜单、价格、营业时间、打印路由、支付规则、渠道开关等 **大量配置项** — 这些配置直接决定门店能否正常接单、出餐与结账。

过去十年，上述能力随产线独立演进：**POS 本地后台、Kiosk 云后台、eMenu 云后台、会员/报表等各自为政**，形成「多入口、多账号、多逻辑」的碎片化体验。随着连锁客户占比提升、产线组合日益复杂（单店可能同时用 POS + Kiosk + eMenu），以及竞品（Toast、Square、Clover 等）均已提供 **统一商家 Web 后台**，我们亟需建设 **新一代统一商家后台**，并完成 **本地配置上云** 与 **多云后台集成** 的战略升级。

### 2.2 现状：老商家平台的结构性问题

| 维度 | 现状描述 | 影响 |
|------|----------|------|
| **系统分散** | POS、Kiosk、eMenu、会员、报表等产线各自维护独立后台或配置入口 | 商家需记住多个 URL/账号；同一业务概念在不同系统重复出现 |
| **配置本地化** | 大量设置项（约 **472 个四级设置**、**1200+ 导航节点**）仍存储在 POS 本地，通过远程桌面/远程工具在终端上修改 | 配置效率低、无法批量/连锁下发、变更不可审计、依赖门店网络与设备在线 |
| **功能重复** | 营业时间、品牌展示、打印、支付、菜单可见性等在 POS/Kiosk/eMenu 各自有一套配置界面与存储 | 改一处漏一处，多产线组合门店配置不一致，实施与客诉成本高 |
| **架构陈旧** | 约 10 年前形成的设置体系，按产线堆叠而非按 **商家经营对象**（门店、品牌、商品、订单…）组织 | 新功能无处安放；培训与文档难以维护；与 M 平台企业级能力无法对齐 |
| **缺乏统一入口** | 无「一个商家、一个后台」的主工作台；连锁场景下集团/品牌/门店数据边界模糊 | 总部无法高效治理多品牌多店；店长/实施人员学习曲线陡峭 |

### 2.3 新方案与旧体系对比

```
┌─────────────────────────────────────────────────────────────┐
│  老体系：产线 × 本地 × 重复                                 │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐        │
│  │ POS本地 │  │ Kiosk云 │  │ eMenu云 │  │ 会员/报表│        │
│  │  设置   │  │  后台   │  │  后台   │  │  分散   │        │
│  └────┬────┘  └────┬────┘  └────┬────┘  └────┬────┘        │
│       └────────────┴────────────┴────────────┘              │
│                         ↓                                   │
│              商家：多入口、重复配、难治理                    │
└─────────────────────────────────────────────────────────────┘
                              ↓ 新商家后台
┌─────────────────────────────────────────────────────────────┐
│  新体系：统一 Web 后台 + 云端配置 + 产线预设                  │
│  M 平台（蓝图/预设/商户） → 商家后台（经营配置） → 终端同步   │
└─────────────────────────────────────────────────────────────┘
```

## 三、动机与价值（Why）

### 3.1 业务价值

| 价值维度 | 具体呈现 | 可量化方向（目标期） |
|----------|----------|----------------------|
| **运营效率** | 总部/实施可在 Web 端批量改配置，无需逐台 POS 远程操作 | 单店标准配置上线时间缩短；连锁新店复制配置分钟级完成 |
| **一致性** | 同一门店多产线共享主数据（菜单、品牌、营业时间），减少「Kiosk 与 POS 菜单不一致」类客诉 | 多产线配置冲突工单下降 |
| **可治理** | 配置变更有版本、有审计、可回滚；M 平台可对企业下全部商户做能力开通与预设下发 | 实施/support 可追溯「谁在何时改了什么」 |
| **可扩展** | 新产线/新模块接入统一导航与预设体系，而非再建独立后台 | 新功能上线周期缩短；减少重复建设 |
| **商业竞争力** | 对齐 Toast/Square 等「一个后台管全店」的行业预期，支撑连锁大客户签约与续费 | 连锁客户 NPS / 续约率提升 |

### 3.2 用户价值

- **商家老板 / 集团总部**：一处看清全品牌全店经营与配置状态，扩张开店不再依赖现场 IT。
- **品牌运营 / 区域经理**：按品牌或区域批量下发菜单、营销、渠道规则，数据视角清晰。
- **店长 / 值班经理**：日常改价、停售、营业时间等高频操作在浏览器完成，不绑在收银台旁。
- **实施 / 客户成功**：标准配置模板 + 平台预设，降低交付差异与培训成本。
- **一线收银 / 服务员**：终端配置自动同步，减少因误改本地设置导致的营业中断。

### 3.3 技术价值

- **配置 SSOT（单一事实来源）**：云端为主，终端缓存；消除多系统双写。
- **与 M 平台分层**：企业级策略（导航蓝图、企业预设、商户能力包）与商户级经营配置职责清晰。
- **为后续能力铺路**：硬件资产中心、权限 RBAC、报表字段统一定义等，均依赖统一后台与配置模型。

## 四、用户画像

### 4.1 集团总部管理员（Corporate Admin）

| 属性 | 描述 |
|------|------|
| **角色** | 餐饮集团 IT 负责人、运营总监、多品牌持有人 |
| **典型场景** | 新品牌立项、统一菜单/支付策略、查看全集团 KPI、审批敏感配置 |
| **使用频率** | 中低（战略配置），但对系统完整性要求高 |
| **核心诉求** | 多品牌多店一览；能力按合约开通；配置可审计、可下发、不可被单店随意破坏 |
| **痛点** | 现需分别登录多个产线后台；无法确认各店配置是否与总部一致 |

### 4.2 品牌运营经理（Brand Operator）

| 属性 | 描述 |

| **典型场景** | 维护品牌菜单结构、营销活动、Kiosk/eMenu 品牌首页展示、品牌下门店开业 |

| **痛点** | 品牌级设置在 POS 本地与 Kiosk 云各改一遍；连锁扩张时复制配置困难 |

| 属性 | 描述 |
|------|------|
| **角色** | 单店负责人、值班经理 |
| **典型场景** | 调整当日营业时间、单品停售、查看订单与报表、管理当班员工与小费 |
| **使用频率** | 每日 |
| **核心诉求** | 移动端/PC 均可快速操作；只看到自己门店；改动立即同步到 POS/Kiosk |
| **痛点** | 改一个打印设置要远程进 POS；不懂技术；怕改错导致不能收银 |

### 4.4 实施 / 客户成功顾问（Implementation CSM）

| 属性 | 描述 |
|------|------|
| **角色** | MenuSifu 实施、支持、客户成功 |

| **使用频率** | 项目期极高 |
| **核心诉求** | 标准模板、清晰导航、配置项有说明；M 平台代开户 + 商家后台交付一条龙 |
| **痛点** | 472+ 设置项分散且命名不统一；各产线文档不一致；远程 POS 配置耗时长 |

### 4.5 一线店员（Frontline Staff）— 间接用户

| 属性 | 描述 |
|------|------|

## 五、核心痛点

### 5.1 分角色痛点矩阵

| 痛点 | 集团总部 | 品牌运营 | 店长 | 实施 |
|------|:--------:|:--------:|:----:|:----:|
| 多个后台/账号，不知去哪改 | ● | ● | ● | ● |
| POS 远程改配置，耗时长、易失败 | ○ | ○ | ● | ● |
| 多产线同一概念重复配置 | ● | ● | ● | ● |
| 连锁批量下发能力不足 | ● | ● | ○ | ● |
| 配置变更无审计/难回滚 | ● | ○ | ○ | ● |
| 设置项过多、分类混乱 | ○ | ● | ● | ● |
| 新开店复制标准配置困难 | ● | ● | ○ | ● |

（● 强相关，○ 中等相关）

### 5.2 典型痛点场景

**场景 A：多产线菜单不一致**  
某火锅连锁同时使用 POS 与 Kiosk。总部在 Kiosk 云后台更新了品牌首页与套餐结构，但 POS 本地菜单未同步更新。顾客在 Kiosk 点的套餐与柜台价格不一致，引发退款与投诉。  
→ **根因**：菜单与展示规则分散在多个系统，缺乏统一商品中心与下发机制。

**场景 B：远程改 POS 打印设置**  
店长反馈小票打印机路由错误。支持人员需远程连接 POS，在本地设置里翻找数十项打印相关 seq，营业高峰不敢改，低峰改完还需重启客户端。  
→ **根因**：打印/后厨配置绑在终端本地，未上云，缺乏 Web 端可视化与一键下发。

**场景 C：连锁新店开业**  
品牌下新开第 20 家门店，实施需从老店 POS 导出配置、再导入新店，并分别登录 Kiosk/eMenu 后台复制一遍。全程 1–2 天，且无法保证与总部最新策略一致。  
→ **根因**：无「门店模板 + 平台预设 + 云端复制」的标准交付路径。

**场景 D：实施培训成本高**  
新商家签约 POS + eMenu，实施需培训商家记住两套后台入口，且 eMenu 的「品牌页作为首页」与 POS 的「品牌管理」设置描述不一致。  
→ **根因**：10 年堆叠的设置体系未按经营对象重组；缺乏统一导航与四级树文档。

## 六、核心业务场景

### 6.1 新商户入驻（与 M 平台联动）

1. M 平台运营创建商户，选择 **业态 × 产线**（如：火锅 × POS + Kiosk）。
2. 企业级平台预设与导航蓝图下发至商家。
3. 商家管理员首次登录 `#/onboarding`，确认业态产线 → 侧栏按预设展示。
4. 在统一后台完成品牌、首店、菜单、支付、硬件绑定，终端联网拉取配置。

### 6.2 日常门店运营

- 店长在 **门店视角** 下修改营业时段、单品售罄、小费规则。
- 变更写入云端，POS/Kiosk/eMenu 按产线订阅同步。
- Dashboard 展示当日 KPI 与待办（设备离线、待处理订单等）。

### 6.3 连锁批量治理

- 集团管理员切换 **集团总部视角**，在商品中心维护品牌菜单，下发至品牌下全部门店。
- 品牌运营在 **品牌多门店视角** 下对比各店配置差异，批量启用营销或渠道开关。
- 敏感操作走 RBAC 与审计日志。

### 6.4 产线扩展

- 商户加购 Kiosk 产线：M 平台开通能力包 → 商家平台预设增加 Kiosk 组合 → 侧栏露出 Kiosk 相关模块，**无需新后台账号**。

### 6.5 配置治理与升级

- M 平台发布导航蓝图 vN+1，同步企业预设；商家可选择同步或保留局部自定义。
- 十年老设置按四级树归位到对应一级导航（如打印归后厨/硬件，支付归支付中心），逐步下线 POS 本地设置入口。

## 七、建设范围边界

| 范围内（In Scope） | 范围外（Out of Scope / 后续阶段） |
|--------------------|-----------------------------------|
| 统一商家 Web 后台信息架构与导航 | POS 客户端 UI 大改版（仅消费云端配置） |
| 472+ 设置项上云与四级树归位 | 非餐饮业态的通用 ERP |
| POS / Kiosk / eMenu 配置云端下发 | 第三方外卖平台本体改造 |
| 三视角（集团/品牌/门店）与 RBAC | M 平台商户管理中心完整实施（可并行） |
| 与 M 平台预设/蓝图同步 | 所有历史数据一次性迁移（可分波次） |

## 八、成功标准

| 指标 | 说明 |
|------|------|
| **配置上云覆盖率** | 原 POS 本地核心设置项迁移至云端的比例（分阶段 60% → 90% → 100%） |
| **后台统一率** | 商家日常配置操作发生在统一 Web 后台的比例（替代原 Kiosk/eMenu 独立后台） |
| **多产线配置一致率** | 抽样门店 POS vs Kiosk vs eMenu 关键字段一致比例 |
| **新店交付时长** | 从开户到可营业的标准配置完成时间 |
| **支持工单** | 「配置找不到 / 改错 / 不同步」类工单数量趋势 |
| **商家满意度** | 连锁客户对「一个后台管全店」能力的调研评分 |

## 九、功能需求

功能需求按 **平台能力层 → 配置上云层 → 业务模块层 → 治理与集成层** 组织。编号 `FR-x.y` 便于追溯；优先级：**P0** 首发必达，**P1** 同期或紧接迭代，**P2** 增强项。

### 9.1 统一后台与信息架构

| 编号 | 需求描述 | 优先级 | 验收要点 |
|------|----------|--------|----------|
| FR-1.1 | 提供单一 Web 商家后台入口，替代 POS 本地设置界面及 Kiosk/eMenu 独立云后台的日常配置场景 | P0 | 商家仅用一个账号登录；核心配置操作可在 Web 完成 |
