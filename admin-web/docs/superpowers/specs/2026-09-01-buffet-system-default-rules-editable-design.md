# 自助餐系统默认规则全面可编辑设计

## 1. 背景与目标

当前自助餐规则将 8 条系统默认规则的限购主体、额度周期、限购对象和周期内限购维度锁定，用户无法按实际门店业务调整完整规则。

本次调整要求系统默认规则与普通规则一样支持六个步骤的完整编辑，其中“限购数量”步骤包含商品选择与数量配置；同时保留 8 个默认场景自动补齐机制。

## 2. 核心规则

系统默认规则进入编辑器后全部步骤开放：

1. 规则类型；
2. 场景配置；
3. 限购数量；
4. 超限授权；
5. 生效范围；
6. 确认发布。

系统默认身份由原始 `defaultScenarioKey` 对应的三个核心维度决定：

- 限购主体；
- 额度周期；
- 限购对象。

保存时比较当前语义和原始模板：

- 三个核心维度均未改变：保留系统默认身份；
- 任一核心维度改变：转为普通规则，清除系统默认身份；
- 仅修改名称、描述、人数区间、轮次区间、周期内限购维度、商品、数量、授权、会员、时间或门店：仍保留系统默认身份。

“原始模板”是本次编辑会话的不可变基准：编辑已有规则时始终通过草稿 `sourceRuleId` 读取原系统默认正式规则的 `defaultScenarioKey` 和版本，不从可能已经 detach 的草稿读取。`sourceRuleId` 是普通来源引用，不属于系统身份字段，草稿 detach 后继续保留。

## 3. 草稿隔离与身份转换时点

- 编辑已有规则时沿用现有 `source rule + edit draft` 隔离模型；编辑草稿不得提前改写原正式规则、已发布配置或运行快照。
- 编辑器现有约 1.2 秒自动保存继续启用。自动保存、手动保存草稿和保存并返回均执行同一套草稿身份判断。
- 只要 `sourceRuleId` 仍指向原系统默认正式规则，每次自动或手动保存都重新与不可变原模板比较，因此编辑草稿可以在 `detach` 与 `preserve` 之间可逆切换。
- 核心维度变化后，编辑草稿转为普通草稿；原系统默认正式规则保持不变。
- 保存普通草稿并返回列表时，同时展示原系统默认规则和修改后的普通草稿，不执行默认补齐，因为原默认规则仍存在。
- 放弃编辑时删除编辑草稿，原系统默认规则、发布配置和运行快照不变。
- 确认发布时，普通草稿替换原系统默认正式规则；发布事务成功后，进入自助餐作者列表时由现有对账流程补回原场景的空白、禁用系统默认规则。
- 发布失败时保留原系统默认正式规则和原运行快照，不补回新默认规则。
- 对账必须保持幂等，重复刷新不能重复补齐。

| 操作 | 编辑草稿 | 原系统默认正式规则 | 运行快照 | 是否补回默认 |
| --- | --- | --- | --- | --- |
| 自动保存 | 核心维度变化则转普通草稿 | 不变 | 不变 | 否 |
| 保存草稿 | 核心维度变化则转普通草稿 | 不变 | 不变 | 否 |
| 保存并返回 | 列表展示普通草稿 | 保留并继续展示 | 不变 | 否 |
| 放弃编辑 | 删除编辑草稿 | 不变 | 不变 | 否 |
| 确认发布成功 | 发布为普通正式规则 | 被本次发布替换 | 生成新快照 | 是，后续作者列表加载时补回原场景 |
| 确认发布失败 | 保留普通草稿 | 不变 | 不变 | 否 |

身份转换清除编辑草稿及其所有持久化作者态副本中的：

```text
origin
defaultScenarioKey
defaultCatalogVersion
```

清理范围包括草稿顶层、`editorDraft`、`authoringDraft` 和 `authoringConfig`。发布形成普通正式规则后，其顶层、全部作者态和 `publishedConfig` 也不得残留系统身份。历史运行快照保持当时的不可变数据，不回写；新运行快照只包含发布后的普通规则。原系统默认正式规则在发布成功前不清理。

## 4. 页面交互

- 移除“系统默认场景，规则类型不可修改”及同义提示。
- 移除系统默认规则主体、周期、对象和周期配置块的 `disabled`、锁定样式与事件拦截。
- 系统默认规则使用与普通规则一致的卡片、开关和选择器。
- 修改主体、周期或对象且存在不兼容的商品或数量配置时，继续使用现有“重置后续配置”二次确认。
- 确认修改后，页面展示：`规则类型已调整，保存后将转为普通规则`。
- 核心维度未变化时可展示轻量的 `系统默认规则` 状态，不表达不可编辑。
- 转换后的规则在列表中进入“其他规则”，不再显示“系统默认”标签。
- 补回的原默认场景显示在原“整单限制”或“每轮限制”分组，状态为禁用且未配置。
- 普通草稿不占用 `defaultScenarioKey`，也不触发或阻止默认场景补齐。

## 5. 数据处理

新增统一保存前处理函数，返回：

```text
preserve：核心维度与模板一致，保留系统默认身份
detach：核心维度与模板不一致，清除系统默认身份
```

处理要求：

- 以稳定 `defaultScenarioKey` 查找原始模板，不依赖可编辑名称。
- `detach` 只清除身份字段，不额外删除业务数据。
- 因修改类型产生的不兼容数据，仍由现有重置确认和清理逻辑负责。
- source rule 本身为普通规则时不进入该判断。
- 复制系统默认规则仍按现有逻辑直接生成普通规则。
- 不修改 8 条默认模板注册表、历史迁移规则、冲突算法、授权规则和运行时计算。
- 仅 `moduleId === "buffet-rule"` 时执行该处理；不写入菜单下单限制的 `restaurantRules`，不修改其路由、profile、默认规则、保存行为或运行快照。
- 默认补齐仍只由 `repository.loadForAuthoringList` 的现有对账入口触发；普通规则、普通草稿和历史快照均不占用默认键。

## 6. 异常与边界

- 找不到原始模板或身份版本无效时，沿用现有安全策略降级为普通规则，不猜测模板语义。
- 保存失败时不得提前清除持久化系统身份。
- 修改后又改回原主体、周期和对象，并在同一次编辑中保存，应继续保留系统默认身份。
- 即使中间一次自动保存已经将草稿 detach，改回原核心维度后下一次保存仍通过 `sourceRuleId` 恢复系统默认身份；不得要求草稿自身仍持有旧 `defaultScenarioKey`。
- 周期内限购维度可以自由调整；只要核心周期本身未改变，不触发身份转换。
- 核心周期比较复用 buffet v4 周期规范化：过滤非法值、去重，并按 `order_lifetime`、`per_round`、`multi_round` 固定顺序比较 `enabledPeriods`；不使用展示文案，也不单独使用兼容字段 `period` 判断。
- 多周期普通化：系统默认单周期规则增加、删除或切换为不同周期，均视为核心周期变化并转为普通规则。

## 7. 验收标准

### 7.1 可编辑性

- 8 条系统默认规则均可进入并操作全部六个步骤。
- 主体、周期、对象、周期配置块、商品和数量控件均可操作。
- 页面不再出现“规则类型不可修改”提示。

### 7.2 身份保留

- 仅修改名称、商品、数量、授权、生效范围或周期内限购维度，保存后仍显示“系统默认”。
- 查看、再次编辑、启用和发布流程正常。

### 7.3 身份转换

- 修改主体、周期或对象后，自动保存和手动保存只将编辑草稿转为普通草稿；确认发布成功后才替换原系统默认正式规则。
- 转换后的规则保留用户保存的兼容业务数据。
- 保存草稿返回列表时保留原默认正式规则，不补回；发布成功后仅补回一条原默认规则，补回项为禁用、未配置。
- 重复进入列表不会继续新增同一默认规则。
- 修改后改回原核心维度再保存，不发生转换或补齐。
- 覆盖“先自动保存 detach，再改回并自动保存 preserve”的可逆流程。

### 7.4 保存入口

- 自动保存、保存草稿、保存并返回、发布确认使用同一转换函数。
- 自动保存只转换编辑草稿身份，不修改原正式规则。
- 放弃编辑删除草稿，不转换原正式规则、不补齐。
- 保存或发布失败不得形成部分身份清理，不改变原正式规则和运行快照。
- 序列化后重新加载时，普通草稿/普通正式规则的顶层、`editorDraft`、`authoringDraft`、`authoringConfig` 和新 `publishedConfig` 均不得残留系统身份。

### 7.5 回归

- 系统默认规则复制后仍是普通规则。
- 菜品集重叠提示、启用/发布阻断正常。
- 8 场景生命周期、人数倍率、每轮上下限和同菜保护不回归。
- 普通自助餐规则保持现有行为。
- 菜单下单限制不受影响；测试需断言菜单路由、profile、`restaurantRules` 存储、默认规则和保存前后快照均零写入、零语义变化。
- 5173 最新 main 页面完成浏览器验证。

## 8. 不在本期范围

- 改变 8 条系统默认模板的数量或内容；
- 取消默认规则自动补齐；
- 修改历史规则迁移策略；
- 修改冲突、授权或运行时计算口径；
- 修改菜单下单限制。
