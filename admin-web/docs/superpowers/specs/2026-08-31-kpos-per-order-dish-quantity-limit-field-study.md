# KPOS「订单下单数量限制」完整操作调研

> 调研日期：2026-08-31  
> 调研入口：KPOS → admin → eMenu → 全局设置 → 权限设置 → 订单下单数量限制  
> 调研方式：在未保存表单中逐项增加、选择、输入和删除；未点击“保存”。

## 1. 调研范围

本次完整操作以下四个历史功能：

1. 每个订单指定菜品限制下单份数。
2. 每个订单指定菜品集限制下单份数。
3. 每位食客每单指定菜品限制下单份数。
4. 每位食客每单菜品集下单份数。

四个功能都只包含商品范围和最大份数，不包含轮次、人数区间、时间或最小下单数量设置，统计周期均为整个订单。

## 2. 四类规则定义

| 功能 | 统计主体 | 统计对象 | 统计周期 |
| --- | --- | --- | --- |
| 每个订单指定菜品限制下单份数 | 当前订单 | 每个选中菜品分别统计 | 整个订单 |
| 每个订单指定菜品集限制下单份数 | 当前订单 | 所选菜品合并统计 | 整个订单 |
| 每位食客每单指定菜品限制下单份数 | 有效就餐人数 | 每个选中菜品分别统计 | 整个订单 |
| 每位食客每单菜品集下单份数 | 有效就餐人数 | 所选菜品合并统计 | 整个订单 |

## 3. 每个订单指定菜品限制

配置表达：

```text
每个菜最多下单 N 份
```

已验证行为：

- 支持分类、菜品树形多选。
- 选择分类后，系统将其展开为该分类下的具体菜品。
- 页面保存和展示的是具体菜品，不是分类节点。
- 一条规则可以选择多个菜品。
- 多个菜品分别享有 N 份额度，不合并共享额度。

例如选择 A、B、C，配置 2 份：

```text
A ≤ 2
B ≤ 2
C ≤ 2
```

而不是 `A + B + C ≤ 2`。

## 4. 每个订单指定菜品集限制

配置表达：

```text
每个菜品集最多下单 N 份
```

已验证行为：

- 同样通过分类、菜品树形多选。
- 选择分类后展开为多个具体菜品。
- 一条规则内选中的菜品共同组成一个临时菜品集。
- 没有菜品集名称、编码等额外字段。
- 集合内全部菜品合并累计数量。

例如菜品集包含 A、B、C，配置 5 份：

```text
A + B + C ≤ 5
```

历史功能中的“菜品集”本质是“一条规则内选择多个菜品并共享额度”，不是独立维护的可复用对象。

## 5. 每位食客每单指定菜品限制

配置表达：

```text
每位食客每个菜最多下单 N 份
```

页面不存在具体食客选择、食客身份或菜品归属配置，因此“每位食客”应按订单有效就餐人数换算：

```text
指定菜品整单上限 = N × 当前有效就餐人数
```

例如 3 人用餐，A 配置每人每单 2 份，则 A 整单最多 6 份。

一条规则选择多个菜品时，每个菜品分别获得换算后的额度：

```text
A ≤ 6
B ≤ 6
C ≤ 6
```

该规则不要求系统识别具体是哪位食客点了菜。

## 6. 每位食客每单菜品集限制

配置表达：

```text
每位食客每个菜品集最多下 N 份
```

计算方式：

```text
菜品集整单上限 = N × 当前有效就餐人数
```

例如菜品集包含 A、B、C，每人每单最多 2 份，3 人用餐：

```text
A + B + C ≤ 2 × 3 = 6
```

集合内部可以任意组合，只控制合并后的总份数。

## 7. 增加、删除与数量输入

四个功能均支持：

- 点击“增加”创建多条规则。
- 每条规则独立设置额度和商品范围。
- 点击“删除”移除指定规则行。
- 新增规则默认额度为 1 份。
- 数量控件声明的最小值为 1。

实际操作还发现：

- 手工输入 0 时没有立即显示错误。
- 清空输入后，页面会恢复为 0。
- 配置页面不能证明保存接口是否接受 0。

新方案应明确：

- 空值：未配置。
- 0：禁止下单。
- 正整数：最大允许份数。

## 8. 重复选择与冲突控制

### 8.1 同一个功能内部

第一条规则已经选择的菜品，会从该功能后续新增规则的可选列表中排除。

因此同一菜品不能在同一个功能中重复配置两个额度，可以避免：

```text
每个订单 A 最多 2 份
每个订单 A 最多 5 份
```

这类同主体、同对象、同周期冲突。

### 8.2 不同功能之间

同一菜品可以跨功能重复选择，本次已验证同一菜品可以同时参与：

- 每个订单指定菜品。
- 每个订单指定菜品集。
- 每位食客每单指定菜品。
- 每位食客每单菜品集。

这属于不同维度的组合限制，所有命中规则共同生效。

## 9. 规则组合计算

### 9.1 订单单品上限与人数单品上限

例如：

- 每个订单 A 最多 2 份。
- 每人每单 A 最多 1 份。
- 3 人用餐。

```text
订单单品上限 = 2
人数单品上限 = 1 × 3 = 3
最终 A 上限 = min(2, 3) = 2
```

### 9.2 订单菜品集上限与人数菜品集上限

例如：

- 每个订单菜品集 {A,B,C} 最多 5 份。
- 每人每单该菜品集最多 2 份。
- 3 人用餐。

```text
订单菜品集上限 = 5
人数菜品集上限 = 2 × 3 = 6
最终集合上限 = min(5, 6) = 5
```

### 9.3 单品上限与菜品集上限

例如：

- 每个订单 A 最多 2 份。
- 每个订单菜品集 {A,B,C} 最多 5 份。

必须同时满足：

```text
A ≤ 2
A + B + C ≤ 5
```

### 9.4 四类规则全部叠加

同一菜品可以同时受到：

1. 订单单品上限。
2. 订单菜品集共享上限。
3. 按人数换算的单品上限。
4. 按人数换算的菜品集共享上限。

每次加购和提交时应逐条校验，任一命中规则超限即拦截。

## 10. 与每轮限制的区别

权限设置中的四类规则全部是整单累计：

```text
订单累计数量 = 第 1 轮 + 第 2 轮 + 第 3 轮 + ……
```

- “每人每单”不会在下一轮重置。
- “每个订单”不会在下一轮重置。
- 订单结束、取消或重新开单后才开始新的统计周期。

| 功能 | 统计周期 |
| --- | --- |
| 权限设置中的四类订单数量限制 | 整个订单 |
| 下单设置中的每人每轮/每轮数量限制 | 当前轮 |

两者是不同额度周期，不能互相替代。

## 11. 新自助餐规则建议

- 按订单＋菜品：单品整单累计。
- 按订单＋菜品集：集合整单合并累计。
- 按人数＋菜品：`单品额度 × 有效就餐人数`，整单累计。
- 按人数＋菜品集：`集合额度 × 有效就餐人数`，整单累计。
- 同主体、同周期、同对象不允许重复配置。
- 不同主体或不同对象维度允许叠加。
- 所有命中规则同时生效，取更严格的结果。
- 菜品集由一条规则内选择的多个商品组成，不新增额外字段。
- 菜品集至少选择 2 个商品。
- 菜品集支持跨产线合并统计。
- 服务员授权只绕过当前数量规则。
- 整单限制与每轮限制保持独立的统计桶。

## 12. 仍需真实下单或接口验证

1. 历史“每位食客”是否确实按有效就餐人数乘算。
2. 历史保存接口是否接受限额 0，以及 0 的运行时含义。
3. 普通菜品多选在历史执行引擎中是否确实逐菜统计。
4. 修改就餐人数后，已产生的整单额度如何重算。
5. 服务员授权后，是放行本次操作、当前轮还是当前订单。

以上内容无法仅通过配置页面完全证明，新方案应形成明确产品定义并补充接口与真实下单测试。
