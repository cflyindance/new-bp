# 日期小费发放确认与结果锁定设计

## 目标

在日期分配汇总中增加按日期整体确认的小费发放状态。正常营业日期完成分配后可确认“已发放”；一旦确认，该日期的分配快照成为不可变结果，任何入口都不得修改、覆盖或取消。

## 状态模型

发放状态独立于营业状态和分配状态：

| 营业状态 | 分配状态 | 发放状态 | 可用动作 |
| --- | --- | --- | --- |
| 未营业 | 无需分配 | 无需发放 | 无 |
| 正常营业 | 待分配 | 待发放 | 分配 |
| 正常营业 | 已分配 | 待发放 | 查看、导出、重新确认、取消分配、确认发放 |
| 正常营业 | 已分配 | 已发放 | 仅查看、导出 |

每个合法已确认分配必须生成不可变 `allocationSnapshot`，至少包含 `snapshotId`、`snapshotVersion`、`snapshotHash`、`schemaVersion`、`storeId`、`businessDate`、完整员工/池/金额/工时/比例结果、`confirmedAt` 和 `confirmedBy`。同一 `storeId + businessDate` 每次合法重新确认后，`snapshotVersion` 必须单调递增；`snapshotHash` 对去除瞬时字段后的完整快照业务内容执行 JSON Canonicalization Scheme（RFC 8785）序列化，再计算 SHA-256 十六进制摘要。

发放记录以 `storeId + businessDate` 为唯一键，必须绑定 `snapshotId + snapshotVersion + snapshotHash`，三者不得省略，且满足不变量：`paid => payout.snapshotId/version/hash === allocationSnapshot.snapshotId/version/hash`。已发放后的明细、汇总和导出只能读取该快照，不得使用实时规则、员工、工时、小费数据或重新计算结果。快照缺失、无效或摘要不一致时，导出失败并提示“发放快照不可用”，不得静默输出实时结果。

发放记录为 append-only，包含 `recordId`、`schemaVersion`、`storeId`、`businessDate`、`status=paid`、可信时间源生成的 UTC ISO `paidAt`、`paidById`、`paidByDisplayNameAtConfirmation`、`snapshotId`、`snapshotVersion`、`snapshotHash`、`requestId` 和 `source=manual-confirm`。不提供 update/delete API。演示环境使用稳定的 demo actor ID；展示名缺失时 UI 可显示“当前用户”，但审计主体 ID 不得缺失。

## 状态优先级与转换

1. 只要该日期存在任何发放记录，或无法可靠判定其不存在，锁定优先级最高，不得因营业状态变化而降级。
2. 发放记录与有效快照一致：已发放。
3. 发放记录存在，但快照缺失、无效、摘要不匹配、记录重复或损坏：发放数据异常（锁定）。
4. 无发放记录，正常营业且存在有效快照：待发放。
5. 无发放记录，正常营业但无有效快照：待分配；仅有已分配日期索引不算已分配。
6. 无发放记录且未营业：无需发放。
7. 快照与已分配索引不一致：分配数据异常，禁止确认发放，修复后才能继续。

允许转换只有 `待分配 -> 待发放 -> 已发放`；未发放日期取消分配可由 `待发放 -> 待分配`；`已发放`无出边。

## 原子性与并发

所有按 `storeId + businessDate` 执行的发放确认、快照新增或覆盖、分配索引增删、手工工时写入、数据更新、自动重算和薪资同步进入同一领域互斥/事务边界。确认发放请求携带页面所见 `expectedSnapshotId + expectedSnapshotVersion + expectedSnapshotHash + requestId`；事务内重新读取并校验当前快照，三者一致且无发放记录时才原子创建记录。快照已变化则失败并要求刷新；发放先提交后，后续 mutation 返回统一锁定错误。

确认请求幂等：相同 `requestId` 重试只返回首次结果，不刷新 `paidAt` 或覆盖确认人；不同请求并发确认也只能产生一条记录。演示环境以每个 `storeId + businessDate` 一个独立版本化状态文档保存该日快照、索引和发放记录；所有读改写通过 `navigator.locks.request` 对规范化日期键获取跨标签页独占锁，取得锁后重新读取并比较文档版本，再以一次写入提交完整日期状态。不支持 `navigator.locks` 或无法取得可靠独占锁时 fail closed，拒绝 mutation。`BroadcastChannel/storage` 仅用于提交后的刷新通知，不承担并发控制；禁止“先检查再分别写多个 localStorage key”。

## 日期分配汇总

- 列表新增“发放状态”列：待发放、已发放、无需发放。
- 已分配且未发放的正常营业日期显示“确认发放”操作。
- 点击后弹出二次确认：“确认该日期的小费已全部发放？确认后分配结果将锁定，无法修改或取消。”
- 确认成功后立即更新列表为“已发放”，记录确认人和确认时间。
- 已发放日期仍可进入明细和导出。

## 锁定规则

锁定校验必须位于所有写入与删除入口共用的领域边界，不能只依赖按钮禁用。以下动作对已发放日期全部拒绝：

- 明细页重新确认分配；
- 修改金额、工时、员工、比例或删除行；
- 更新小费数据后覆盖结果；
- 自动分配或规则重算覆盖；
- 单日或批量取消分配；
- 日期范围批量分配或重新分配。

统一提示：“小费已发放，分配结果已锁定，无法修改”。快照有效时，读取、查看详情和导出不受影响；发放数据异常时仅允许查看发放审计信息与异常原因，分配明细不得实时重算，导出失败并提示“发放快照不可用”。拒绝操作不得改变分配快照、已分配日期集合、发放记录或薪资同步状态。

所有 mutation 必须调用唯一公开守卫 `assertDateWritable(storeId, businessDate, expectedVersion)`，底层存储不得公开无守卫写方法。封闭清单包括：分配快照 create/upsert/delete；已分配索引 add/remove；手工工时 set/seed/delete；明细行金额、员工、比例增删改；小费数据刷新或导入落盘；自动分配和规则重算；单日及批量分配/取消；迁移、初始化、修复、演示重置；薪资同步及其状态和时间元数据。页面渲染、详情打开和只读查询不得产生写入。

全局员工档案和规则仍可编辑，但不得反向修改已发放快照；已发放详情与导出展示快照中冻结的姓名、角色、规则、工时和比例。已发放日期禁止手工重新触发薪资同步，避免更新发放后的外部状态。

批量操作按日期逐项进入原子事务，并在每个日期实际提交时重新读取锁定状态。单日失败不终止其余日期，归入 `failedCount`。结果返回 `selectedCount`、`successCount`、`paidSkippedCount`、`closedSkippedCount`、`invalidSkippedCount`、`failedCount`；分类互斥且总和等于选择数。仅 `successCount > 0` 时触发后续同步；全锁定范围不得发生存储写入、同步或时间戳更新。

## 明细页

已发放日期展示只读锁定提示，包含确认时间和确认人。确认分配按钮禁用；所有编辑控件、增删行入口和更新数据入口禁用或隐藏。即使通过程序直接调用处理函数，也必须由领域锁定校验拒绝。

## 不可撤销与异常

本次不提供“撤销发放”。如真实业务需要冲正，应另行设计权限、原因、审批与审计记录。发放记录存在但分配快照缺失或校验失败时显示“发放数据异常”，继续保持锁定，并禁止任何分配变更。损坏 JSON、非法时间、缺少 actor、未知 schema、重复记录都 fail closed。

## 验收标准

1. 日期汇总正确展示待发放、已发放和无需发放。
2. 只有正常营业且已分配、未发放的日期可确认发放。
3. 二次确认后保存确认人和确认时间，刷新页面状态保持。
4. 已发放日期可以查看和导出，但不能重新确认、编辑、更新、取消或被批量覆盖。
5. 所有程序化写入和删除入口均无法绕过锁定。
6. 混合批量操作跳过已发放日期并准确提示数量；全锁定范围不写入。
7. 异常发放记录保持锁定并显示异常，不允许通过重新分配“修复”。
8. 发放后修改全局规则、员工、打卡、手工工时和原始小费，详情与导出逐字段仍等于锁定快照。
9. 两个标签页并发确认发放与重新分配、取消或更新，最终快照与发放摘要始终一致。
10. 双击、刷新重试和跨标签重复确认只生成一条记录，原始确认时间和确认人不变。
11. 逐项直接调用所有底层 mutation 均返回锁定错误，相关存储内容逐字节不变。
12. 混合批量执行期间某日并发发放时计入 `paidSkippedCount`，所有分类计数守恒；全部已发放时写入与同步调用均为零。
13. 注入确认流程各写步骤失败，不产生半成功状态。
14. 发放记录损坏、重复、缺快照或摘要不匹配时保持异常锁定，查看和导出不使用实时结果。
15. 发放后营业状态变为未营业，仍保持已发放和锁定。
