# eMenu 本地配置后台调味设置设计

## 目标

将 `/emenu-local/seasoning-settings` 升级为支持两套独立调味配置方案的工作台。方案1保留现有“商品 → 动作 → Option”向导；方案2使用“先选商品，再在 Option 设置弹窗累积动作 + 多选 Option + 价格关系”的操作方式。门店可同时维护两套方案，但一次只启用其中一套供 eMenu 终端使用。

本设计解决以下问题：

- 调味 Option 在门店内统一维护和复用，不随商品重复创建。
- 不同商品可以关联不同动作、不同 Option 和不同价格。
- 同一个 Option 可以同时关联同一商品的多个动作。
- 商品规模不固定时，仍能通过搜索、分类、批量操作和单商品维护完成配置。
- 门店所有 eMenu 终端使用同一份本地配置，不产生设备级分叉。
- 方案1与方案2的商品关系、价格、状态和顺序完全隔离，Tab 切换不覆盖数据，也不切换当前生效方案。

## 范围

### 本期范围

- 调味关联总览。
- 公共调味库的新增、编辑、启用和停用。
- 方案1的“商品 → 动作 → Option → 预览确认”批量关联向导。
- 方案1/方案2切换、门店级启用方案开关和方案2关系篮。
- 方案2的“组 / 类 / 菜”三列商品选择及动作、Option Category、Option、价格分段弹窗。
- 单商品四动作维护抽屉。
- 关联价格、显示顺序和启用状态。
- 草稿、防误关、冲突检查、原子保存和并发版本校验。
- 门店级配置版本和 eMenu 终端同步契约。
- 查看与编辑权限、操作日志和历史订单快照规则。
- 中英文界面文案、键盘操作和窄屏可用性。

### 不在本期范围

- 品牌或云端向门店下发调味配置。
- 审批、发布计划和配置版本回滚界面。
- 每台 eMenu 设备单独覆盖门店配置。
- 动作类型自定义；首期动作固定为四种。
- 商品分类规则继承、动态条件规则或自动推荐调味。
- 每个动作的最少/最多选择数量限制。
- 配方、库存或厨房用量联动。
- 同时向终端下发两套方案、按设备或按商品选择生效方案。

## 核心概念

### 公共调味 Option

门店级可复用的调味条目，例如葱、蒜、辣椒、花生。公共库只回答“门店有哪些调味”，不决定它适用于哪个商品或动作。

每个 Option 包含：

- `id`：稳定内部 ID。
- `code`：门店内唯一的稳定编码，用于同步和订单快照识别。
- `name` / `nameEn`：中英文展示名称；英文可为空并按现有国际化降级规则显示。
- `status`：`active` 或 `inactive`。
- `sortOrder`：公共库中的默认排列顺序。
- `createdAt` / `updatedAt`。
- `categoryId`：所属公共 Option Category；现有 Option 迁移到系统“未分类”。

公共 Option 不保存销售价格。价格属于具体的“商品 + 动作 + Option”关联。

### 公共 Option Category

Option Category 由两套方案共用，只承担 Option 的组织与筛选，例如调味、酱料、配菜；它不写入商品调味关联或订单快照。公共调味库负责维护 Category 及 Option 的分类归属。

```ts
type SeasoningOptionCategory = {
  id: string;
  code: string;
  name: string;
  nameEn?: string;
  status: "active" | "inactive";
  sortOrder: number;
  system: boolean;
  createdAt: string;
  updatedAt: string;
};
```

`code` 在门店内唯一且创建后不可编辑；名称必填，中英文、排序和状态可编辑。每店固定创建一个 `system: true` 的“未分类”Category，其编码为 `UNCATEGORIZED`，不可改码、停用或删除。普通 Category 无 Option 且无历史引用时可删除，否则只能停用。停用 Category 不会停用或改写其中 Option，也不会影响两个方案的既有关系；它只从 Category 快捷筛选中隐藏。其启用 Option 仍出现在“全部”筛选中，并显示原 Category 名称与停用标记，可继续选择；用户可在公共库中把 Option 移到其他 Category。

### 配置方案

固定方案编码为 `SCHEME_1` 和 `SCHEME_2`。门店配置保存 `activeSchemeCode`，值只能为其中之一。方案 Tab 表示当前编辑目标，门店启用开关表示终端当前生效目标，两者必须独立：切换 Tab 不改变 `activeSchemeCode`，切换启用方案也不丢弃任一方案的数据。

现有商品调味关系升级时全部迁入 `SCHEME_1`，`SCHEME_2` 初始为空，不自动复制方案1。切换到空方案可以维护；启用空方案时必须明确显示影响商品数和“终端将不显示任何调味关系”的警告并二次确认。

### 升级迁移

升级使用单个可重入事务，按门店执行：

1. 创建系统 `UNCATEGORIZED` Category；若稳定编码已存在则复用并校验其系统属性。
2. 为没有 `categoryId` 的 Option 回填该系统 Category。
3. 为没有 `schemeCode` 的历史关系回填 `SCHEME_1`，保留原 ID、价格、状态、顺序、创建和更新时间。
4. 为没有 `activeSchemeCode` 的门店回填 `SCHEME_1`。
5. 创建 `activeSchemeCode IN ('SCHEME_1','SCHEME_2')` 检查约束、关系 `schemeCode NOT NULL`、Option `categoryId NOT NULL`，并把旧唯一索引替换为门店作用域的 `(storeId, schemeCode, productId, action, optionId)` 唯一索引。

迁移全部成功后才递增一次 `seasoningConfigVersion` 并提交；任一步失败整店回滚，终端继续使用升级前最后有效快照。重复运行不能重复创建 Category、关系或审计记录。滚动部署期间，服务端对旧终端继续输出兼容的单方案快照，其内容等同 `SCHEME_1`；只有支持双方案契约的新终端读取 `activeSchemeCode`。在所有目标终端升级前，不允许把门店启用方案切到 `SCHEME_2`，后台显示阻止原因而不是产生旧终端空配置。

### 固定动作

| 编码 | 中文 | English | 语义 |
| --- | --- | --- | --- |
| `ADD` | 添加 | Add | 在标准配方之外额外添加 |
| `LESS` | 少放 | Less | 少于标准配方用量 |
| `MORE` | 多放 | More | 多于标准配方用量 |
| `NONE` | 不要 | No | 从标准配方中移除 |

界面和食客端始终按“添加、少放、多放、不要”的顺序展示。动作不可新增、删除、改名或排序。

### 商品调味关联

一条原子关联表示某商品在某动作下允许使用某个 Option：

```ts
type ProductSeasoningRelation = {
  id: string;
  schemeCode: "SCHEME_1" | "SCHEME_2";
  productId: string;
  action: "ADD" | "LESS" | "MORE" | "NONE";
  optionId: string;
  priceDelta: number;
  sortOrder: number;
  status: "active" | "inactive";
  createdAt: string;
  updatedAt: string;
};
```

约束如下：

- `(schemeCode, productId, action, optionId)` 在门店内唯一。
- `priceDelta` 使用门店币种和现有金额精度，默认 `0`，首期不允许负数。
- 同一个 Option 可以出现在同一商品的多个动作中。
- 不建立单独的“批量默认价”继承层。批量向导中的默认价只用于生成候选关联，保存后每条关系拥有自己的最终价格。
- `sortOrder` 只控制同一商品、同一动作内的食客端显示顺序。
- 新建关系的 `status` 固定为 `active`。批量向导不能停用关系；关系启停由关联商品清单或单商品抽屉维护。

## 信息架构

调味设置保留现有一级路由：

```text
/emenu-local/seasoning-settings
```

页面不增加新的一级导航。内容区第一层使用两个方案 Tab：

1. **方案1**：现有流程，保留调味关联、公共调味库、批量向导和单商品抽屉。
2. **方案2**：独立关系配置，先选择商品，再通过 Option 设置弹窗建立关系。

方案1内部继续使用两个子页签：

1. **调味关联**：默认页，查看和维护动作、Option、商品之间的关系。
2. **公共调味库**：维护公共 Option。

页面右上提供两个稳定入口：

- “公共调味库”：切换到公共调味库页签。
- “批量建立关联”：打开批量向导。

方案 Tab 上方固定显示“当前门店启用：方案1/方案2”和“切换启用方案”入口。编辑 Tab 与启用状态同时可见，避免用户把“正在查看”误认为“已经生效”。

## 方案1：现有流程关系工作台

### 总览表

总览按“动作 + Option”聚合为一行，避免商品量增大后形成巨型商品矩阵。

| 列 | 内容 |
| --- | --- |
| 动作 | 固定动作标签 |
| Option | 公共调味名称 |
| 关联商品 | 已启用关联的商品数量，可打开商品清单 |
| 价格情况 | “全部 ¥0”“全部 ¥1.00”或“¥0–¥1.00，共 2 种价格”等汇总，不暗示持久化继承 |
| 状态 | 启用、部分停用或已停用 |
| 操作 | 查看商品、编辑关系 |

筛选区支持：

- 搜索 Option 名称、编码或商品名称。
- 按动作筛选。
- 按商品分类筛选。
- 按关联状态筛选。
- 清空筛选。

筛选和搜索组合生效。结果为空时区分“公共库为空”“尚未建立关联”和“当前筛选无结果”。

所有可能随商品和关系数量增长的列表均使用服务端搜索、筛选、排序和游标分页，而不是把全量数据加载到浏览器。总览默认按固定动作顺序、Option `sortOrder`、Option 名称和稳定 ID 排序；公共库按 `sortOrder`、名称和稳定 ID 排序；关联商品清单按商品分类顺序、商品 `sortOrder`、名称和稳定 ID 排序。翻页和刷新不能造成重复或漏项。

### 关联商品清单

点击“关联商品”数量后展示当前“动作 + Option”对应的商品清单。清单支持商品搜索、分类筛选、价格编辑、启停和移除关联。移除前显示影响数量并要求确认。

### 单商品维护抽屉

从商品清单或搜索结果进入商品后，在右侧抽屉中同时展示四个动作区域。每个区域支持：

- 从已启用公共 Option 中添加关联。
- 查看 Option 名称和价格。
- 修改价格、启用状态和显示顺序。
- 移除关联。
- 拖动排序，并提供键盘可操作的上移/下移替代方式。

抽屉额外支持“复制自其他商品”和“清空某个动作”。复制前展示将新增、更新和跳过的关系；清空必须二次确认。抽屉关闭时若存在未保存修改，必须确认是否放弃。

## 公共调味库

公共调味库包含“Option”和“Category”两个管理视图。Category 视图提供服务端分页的列表、新增、编辑、排序、启停和受引用保护的删除；Option 编辑器增加 Category 选择。名称必填，编码必填且在门店内唯一。编码创建后默认不可编辑，避免终端同步和历史数据引用失效。Category API 与 Option API 均显式使用门店作用域、`expectedVersion` 和稳定 ID，不允许客户端仅按名称关联。

状态规则：

- 新建 Option 默认为启用。
- 启用 Option 可以用于新关联。
- 停用 Option 不允许用于新关联，并从食客端隐藏。
- 已存在关联的 Option 不允许物理删除，只能停用。
- 无关联且从未进入订单快照的 Option 才可以删除；若服务端无法确认历史引用，则仍只允许停用。
- 停用不自动删除关系，后台继续显示历史关系及影响商品数。停用确认必须按方案1、方案2分别显示受影响关系数、商品数，并标明当前启用方案的终端影响，不能只展示当前编辑 Tab 的影响。
- 重新启用后，原有启用关系恢复在食客端可见；关系本身已停用的仍保持停用。

## 方案1批量建立关联

主流程采用四步向导。

### 第一步：选择商品

- 支持商品名称或编码搜索、商品分类筛选和跨分类多选。
- “选择本页”只选择当前已加载页；“选择全部筛选结果”选择服务端当前筛选条件命中的全部可选商品，包括尚未加载的分页。两者使用不同文案，不用含糊的“全选”。
- 选择全部筛选结果时，服务端按当前筛选条件创建稳定的商品查询快照并返回 `productSelectionToken`、命中数量和过期时间。客户端只保存 token 与排除的商品 ID，不展开保存所有商品 ID；进入预览和提交时都使用同一 token。token 过期、门店不匹配或相关商品状态变化时必须重新确认商品范围，不得静默纳入新商品。筛选条件变更后废弃旧 token 并重新选择。
- 手动多选和“选择本页”都保存明确商品 ID；切换搜索或分类时保留此前选择的 ID，从而支持跨分类累积选择，并在预览时再次校验商品状态。只有当前处于“选择全部筛选结果”token 模式时，筛选条件变化才废弃选择并要求重新确认。
- 商品行显示该商品已有多少调味关系；动作和 Option 尚未选择，因此此步骤不按动作预筛选商品。
- 商品停用或不可在 eMenu 销售时不可选择，并显示原因。
- 返回本步骤修改商品后，清空已选动作、Option、Option 默认价格、整个预览、候选关系移除、单关系价格覆盖和冲突决策，防止旧下游状态误用于新的商品集合。

### 第二步：选择动作

- 单选添加、少放、多放或不要。
- 顶部步骤条和后续页面始终显示当前商品范围与动作。
- 返回本步骤修改动作后，保留商品选择，清空已选 Option、Option 默认价格以及全部预览状态，包括候选关系移除、单关系价格覆盖和冲突决策。

### 第三步：选择 Option

- 从已启用公共调味库中多选。
- 支持名称或编码搜索。
- 每个所选 Option 可填写本批次候选关系使用的默认加价，默认 ¥0。
- 非“添加”动作的价格编辑默认收起，但仍可展开填写。
- 公共库为空时提供“前往公共调味库”，并保留商品和动作草稿；同一会话新增 Option 成功后，向导刷新并基于新的 `seasoningConfigVersion` 重建基础版本，重新校验商品选择和动作，再回到 Option 步骤。若商品快照已失效或校验不通过，则要求重新选择商品，不自动合并其他配置变化。
- 返回本步骤调整 Option 时保留商品和动作，但废弃整个旧预览，清空候选关系移除、单关系价格覆盖和冲突决策后重新生成候选关系。

### 第四步：预览并确认

系统将所选 Option 与商品展开为候选关系。3 个 Option × 18 个商品形成 54 条候选记录。预览支持：

- 删除个别候选关系。
- 覆盖单条候选关系，即单个 `(商品, 动作, Option)` 的 `priceDelta`；同一商品的不同 Option 可以保留不同价格。
- 按“新增、完全相同、有差异、关系已停用、不可用”筛选。

批量向导不提供跨商品统一排序，因为 `sortOrder` 的作用域是单个“商品 + 动作”。新关系固定追加到每个商品该动作下现有启用和停用关系之后，所选 Option 之间按公共 Option `sortOrder`、名称和稳定 ID 排列；已有关系的 `sortOrder` 不变。需要精调的商品在保存后通过单商品抽屉排序。因此，批量冲突比较不把向导计算出的追加位置视为用户覆盖值；既有关系的排序只保留原值。

冲突处理：

| 状态 | 处理 |
| --- | --- |
| 不存在 | 标记“新增”；状态为 `active`，排序按追加规则生成 |
| 已存在且为启用、价格与本次值相同 | 标记“已存在，将跳过”；保留原排序 |
| 已存在且为启用、价格与本次值不同 | 标记“有差异”，必须选择“保留原价格”或“使用本次价格”；保留原排序 |
| 已存在但关系已停用 | 标记“关系已停用”，必须选择“保持停用并跳过”或“重新启用”；重新启用时可同时选择保留原价格或使用本次价格，且保留原排序 |
| 显式 ID 选择中的 Option 或商品在向导期间被停用，或商品变为不可在 eMenu 销售 | 标记“不可用”，禁止提交该条；用户可移除该候选后继续 |
| 全筛选 token 选择中的商品集合或商品状态发生变化 | 整个 token 失效，返回商品步骤重新确认，不生成可局部移除的“不可用”候选 |

用户可以移除不可用记录后继续提交，也可以返回前一步修改选择。未解决的“有差异”“关系已停用”或“不可用”记录存在时，确认按钮不可用。

提交成功后显示明确摘要：

> 已新增 46 条，更新 5 条，跳过 3 条。

关闭或普通导航离开有修改的向导时必须确认放弃。“前往公共调味库”是显式的保存并续办例外：它暂存商品和动作草稿，不弹出放弃确认；返回时按前述版本刷新和重新校验规则继续。向导本身不会内嵌新增、改名或停用公共 Option。

## 方案2：商品优先的关系篮

### 商品选择

方案2首先展示一行三列的“组 / 类 / 菜”商品结构。桌面端三列同时可见：选择组后刷新类列，选择类后刷新菜列；组和类用于浏览，菜列使用复选框多选商品。商品选择跨组、跨类保留，顶部持续显示已选商品数量并可展开清单。停用商品或不可在 eMenu 销售的商品不可选并显示原因。首期只保存明确商品 ID，不提供“选择全部筛选结果”或查询快照模式；搜索、切换组和类均保留已勾选 ID，并在打开弹窗、预览和提交时再次校验。

菜品行同时显示方案2已保存关系数，并提供“查看/编辑”入口。单商品编辑复用 scheme-aware 商品抽屉，但请求必须携带 `SCHEME_2`；它可以编辑方案2既有关系的价格、状态、顺序和移除，不读取或修改方案1。多商品批量入口继续使用 Option 设置关系篮。

窄屏不压缩成横向滚动表格，而按“组 → 类 → 菜”逐层进入并提供面包屑返回。搜索直接匹配菜品名称或编码，结果仍显示所属组和类。点击“Option 设置”前必须至少选择一个可用商品。

### Option 设置弹窗

弹窗采用已确认的“分段选择 + 关系篮”结构，顶部固定显示已选商品数量和可展开商品清单，主体依次包含：

1. **动作**：单选添加、少放、多放或不要。
2. **Category**：单选一个已启用公共 Option Category，只用于过滤 Option；提供“全部”和“未分类”。切换 Category 保留此前已勾选 Option，弹窗在 Option 网格上方固定显示跨 Category 的“已选 Option”托盘，隐藏项也能看见并移除，避免不可见选择被误加入关系篮。停用 Category 下的启用 Option 仍可从“全部”中选择。
3. **Option**：在当前 Category 下多选启用 Option。
4. **价格**：单选免费、门店币种 1、2、3、4、5 或自定义非负金额。本次价格统一应用于当前勾选的所有 Option。
5. **加入关系篮**：按每个 Option 生成一条 `(动作, Option, priceDelta)` 草稿关系，商品集合不在此步骤展开。

加入关系篮后，保留已选商品，清空当前 Option 勾选；动作、Category 和价格保留，方便连续添加。用户可切换动作继续加入其他关系，例如先加入“添加 + 辣椒 + ¥1”，再加入“少放 + 盐 + 免费”。相同 `(动作, Option)` 重复加入时不产生重复项，而是用本次价格更新关系篮中的现有项并给出可感知提示。

关系篮按固定动作顺序分组，支持逐条修改价格、删除和键盘操作。关系篮为空时不能进入预览。关闭或切换方案 Tab 时若有未保存关系，必须确认放弃。新关系保存到每个商品相同动作的现有启用和停用关系之后，篮内同动作 Option 按公共 Option `sortOrder`、名称和稳定 ID 追加；既有关系顺序不变，后续可在方案2单商品抽屉精调。

### 方案2预览与保存

保存前，服务端将“已选商品 × 关系篮”展开为候选关系，所有候选固定写入 `SCHEME_2`。预览和冲突分类沿用方案1的新增、完全相同、有差异、关系已停用和不可用规则；价格覆盖作用于单条 `(方案2, 商品, 动作, Option)` 关系。未解决冲突不能保存，一次提交必须原子写入。

方案2预览请求必须包含 `schemeCode: "SCHEME_2"`、`expectedVersion`、明确商品 ID、关系篮项和冲突决策；提交使用服务端签发的预览 token。服务端拒绝缺失或非 `SCHEME_2` 的方案码，不能依据 Tab 静默补写或改写。保存方案2不会修改方案1关系；保存完成后显示新增、更新、重新启用和跳过数量。

## 启用方案切换

方案配置保存与 `activeSchemeCode` 切换是两种独立写操作。点击“切换启用方案”后展示当前启用方案、目标方案、目标方案有效商品数、有效关系数和同步影响；确认后服务端校验权限及 `expectedVersion`，原子更新 `activeSchemeCode`、递增 `seasoningConfigVersion` 并写审计日志。

影响摘要和切换请求必须基于同一个已持久化配置版本；页面存在关系篮、向导或抽屉脏草稿时，明确提示“未保存修改不会随启用生效”，并要求用户选择“返回保存”或“放弃草稿并继续”，不能把草稿计入影响数量。启用空方案时增加明确警告和二次确认，但不禁止切换。

切换需要独立权限 `seasoning.scheme.activate`；普通关系编辑权限不能隐式获得该能力。请求包含目标方案、`expectedVersion` 和客户端幂等键。目标已是当前启用方案时返回成功但不递增版本、不重复审计；相同幂等键重试返回同一结果。权限不足、版本冲突、同步前校验失败或事务失败时保持原 `activeSchemeCode` 不变。切换成功后，后台两个方案的数据均继续保留，终端快照只包含目标方案的有效关系。

## 食客端选择规则

- 只读取门店 `activeSchemeCode` 对应的关系，并展示商品、关联和公共 Option 均为启用状态的记录。
- 四种动作按固定顺序分组；组内按关联 `sortOrder` 排序，相同值再按公共 Option `sortOrder` 和名称稳定排序。
- 同一个动作下可以选择多个 Option；首期不设置统一数量上限。
- 同一份商品中，同一个 Option 的动作互斥。例如已选“少放辣椒”后选择“多放辣椒”，自动以最后一次选择替换前一次选择，并提供可感知的状态反馈。
- 不同 Option 之间不互斥，例如可以同时选择“少盐”和“不要葱”。
- `priceDelta = 0` 时不显示加价；大于零时使用门店币种格式显示并计入商品行价格。
- 加入购物车和提交订单时，保存动作编码、Option ID、Option 编码、名称快照、成交价格和排序快照。后续改名、调价、停用或删除关联不改写进行中及历史订单。

## 保存、同步与并发

### 草稿与保存

- 方案1批量向导、单商品抽屉和方案2关系篮均使用页面草稿；只有点击确认保存才写入对应方案。
- 一次保存中的新增、更新、启停和删除使用同一事务；任一校验失败时整批回滚。
- 服务端再次校验唯一性、引用状态、金额精度和版本号，不信任客户端预览结果。
- 全筛选商品选择的预览和提交必须携带同一 `productSelectionToken`。服务端在两个阶段都校验 token 的门店、过期时间、商品集合版本和排除 ID；失效时返回可识别错误并要求回到商品步骤重新选择。
- 成功后返回新增、更新、跳过数量以及新的门店配置版本。
- 所有关系读写请求必须显式携带 `schemeCode`，服务端不得依赖当前 Tab 或 `activeSchemeCode` 猜测编辑目标。

### 门店级同步

- 配置由门店本地服务器统一持久化，店内所有 eMenu 终端共用。
- 每次成功保存生成递增的 `seasoningConfigVersion`。
- 终端按现有本地配置同步机制比较版本并拉取完整快照；快照包含 `activeSchemeCode`，关系数组只包含当前启用方案。本设计不引入设备级差异包。
- 新快照完成校验后才替换终端当前配置。下载、解析或校验失败时继续使用上一份完整缓存，并记录可诊断错误。
- 终端首次启动且不存在有效缓存时，显示现有系统约定的配置不可用状态，不使用半份数据。

### 并发

- 编辑草稿记录打开时的配置版本。
- 保存时若版本已变化，服务端返回版本冲突，不静默覆盖。
- 界面提示“配置已被其他人更新”，允许用户刷新后重新执行或重新应用本次选择。
- 首期不实现自动三方合并。
- 方案保存和启用切换共用门店级 `seasoningConfigVersion`，任一成功写入都会使其他旧草稿版本失效，防止跨方案并发覆盖。

## 权限与审计

- 查看权限：访问总览、公共库和关系详情。
- 编辑权限：新增、更新、启停、移除和批量保存。
- 启用权限：仅 `seasoning.scheme.activate` 可切换门店当前启用方案；没有该权限时仍可在授权范围内维护两套配置，但不显示启用按钮。
- 无编辑权限时隐藏或禁用编辑入口，并保持筛选和查看能力。
- 公共 Option 与商品关联的新增、修改、停用、重新启用和移除均写操作日志，记录操作者、时间、对象、变更前后值和配置版本。

## 错误与空状态

| 场景 | 行为 |
| --- | --- |
| 公共库为空 | 引导先创建 Option |
| 没有商品 | 禁用批量建立，并说明需先维护菜单商品 |
| 搜索无结果 | 保留筛选条件并提供清空筛选 |
| 保存校验失败 | 保留草稿，定位到失败记录，不部分写入 |
| 配置版本冲突 | 阻止覆盖，提示刷新并重新核对 |
| 同步失败 | 后台显示失败状态；终端继续使用上一有效版本 |
| Option 被停用 | 禁止新关联；旧关系后台可见、食客端隐藏 |
| 商品被停用 | 保留关系、食客端隐藏；商品重新启用后按关系状态恢复 |
| 方案2为空 | 允许维护；启用时显示“终端将不显示任何调味关系”并二次确认 |
| 切换启用方案版本冲突 | 保持原启用方案不变，刷新影响摘要后重新确认 |
| Option Category 停用 | Category 快捷项隐藏；其中启用 Option 仍在“全部”中可选，两个方案的既有关系保持不变 |

## 组件与职责

实现应保持以下边界，避免把整个功能继续堆入现有 Shell 文件：

- **Shell 路由层**：继续拥有 eMenu 一级导航和页面挂载，只负责把调味路由交给调味模块。
- **调味页面模块**：页签、筛选、总览、空状态和页面级草稿守卫。
- **方案协调模块**：方案 Tab、当前启用方案状态、启用影响摘要和切换确认；不直接编辑关系。
- **公共库模块**：Option 与 Category 列表、编辑表单、归类、排序、停用和引用保护规则。
- **批量向导模块**：步骤状态、候选关系展开、冲突分类和提交摘要。
- **方案2商品选择模块**：组 / 类 / 菜三级浏览、跨分类商品多选和选择快照。
- **方案2关系篮模块**：动作、Category、Option、价格分段选择，草稿去重、逐条改价和批量预览。
- **商品维护模块**：四动作抽屉、关联编辑和排序。
- **领域模块**：动作常量、数据类型、唯一键、金额和互斥选择规则。
- **仓储/服务适配层**：列表读取、事务保存、版本冲突和终端同步契约。UI 不直接操作浏览器存储或拼装网络请求。

## 响应式与无障碍

- 桌面端使用聚合表格和右侧抽屉。
- 中等宽度下抽屉宽度不超过视口，表格允许列收敛但动作、Option 和操作始终可见。
- 窄屏下总览切换为分组列表，单商品维护改为全屏抽屉；不强制横向浏览巨型表格。
- 方案2桌面端以一行三列展示组 / 类 / 菜；窄屏改为逐层进入并保留面包屑和已选数量。
- 方案2 Option 设置弹窗在窄屏改为全屏：标题和已选商品摘要固定在顶部，动作/Category/Option/价格共享一个可滚动主体，关系篮可以折叠但已选条数始终可见，预览/保存操作固定在底部；各区域只能有一个主滚动容器，避免嵌套滚动失去焦点。
- 向导步骤可通过键盘前进和返回；多选项、拖动排序和关闭按钮均提供可访问名称与键盘替代操作。
- 方案切换使用 `tablist` / `tab` / `tabpanel` 语义及方向键切换；查看 Tab 与“当前启用方案”分别提供文本状态。动作与价格使用命名的 `radiogroup`，Category 使用单选语义，Option 使用带选中状态的复选框。
- 关系篮重复项价格更新、加入数量和冲突错误通过 `aria-live` 通知；删除篮项后焦点移动到下一项、上一项或“加入关系篮”按钮。预览失败时焦点移动到错误摘要，摘要链接到具体候选记录。
- 颜色不作为动作、状态或冲突的唯一表达方式。
- 焦点在弹窗或抽屉内正确约束，关闭后返回触发入口。

## 验收标准

1. `/emenu-local/seasoning-settings` 渲染真实调味工作台，不再显示占位卡。
2. 调味设置增加方案1、方案2两个一级内容 Tab，不改变现有五个 eMenu 一级导航；方案1内部保留“调味关联”和“公共调味库”子页签。
3. 可以维护两方案共享的公共 Option 和 Category；编码门店内唯一；系统“未分类”受保护；有关联或历史引用的 Option/Category 只能停用，不能直接删除。
4. 批量建立严格按“商品 → 动作 → Option → 预览确认”执行。修改商品时清空动作、Option、默认价格和全部预览状态；修改动作时保留商品但清空 Option、默认价格和全部预览状态；修改 Option 时保留商品和动作并重建预览。
5. 商品步骤支持手动跨分类多选、只覆盖当前已加载页的“选择本页”，以及覆盖未加载分页并允许排除个别商品的“选择全部筛选结果”。手动和本页选择跨筛选保留明确 ID；只有全筛选 token 模式在搜索或分类变化后需要重新确认选择范围。
6. “选择全部筛选结果”使用服务端商品查询快照 token；商品新增、状态变化、token 过期或门店不匹配会使整个 token 失效并返回商品步骤。显式 ID 模式中的状态变化显示为可移除的不可用候选。
7. 预览正确展开笛卡尔候选关系，区分新增、相同、有差异、关系已停用和不可用记录；同一商品的不同 Option 可以使用不同关系价格。
8. 未解决的冲突不能提交；停用关系支持“保持停用并跳过”和“重新启用”，且分别覆盖相同价格与不同价格；成功后显示新增、更新和跳过数量。
9. 同一 `(方案, 商品, 动作, Option)` 不产生重复关系；同一 Option 可以关联同一商品的多个动作，两个方案的关系互不覆盖。
10. 单商品抽屉显式按 `schemeCode` 读取和保存，可分别维护两个方案中添加、少放、多放、不要四个动作的 Option、价格、状态、顺序和移除，任一修改不影响另一方案。
11. 食客端对同一 Option 的多个动作执行互斥替换，不同 Option 可以同时选择。
12. 价格按关联记录生效；¥0 不显示加价；订单保存名称和成交价格快照。
13. 保存为原子事务；校验失败不产生部分写入，草稿仍可修正。
14. 配置版本冲突不会静默覆盖其他会话的修改；从公共库新增 Option 返回向导时会更新基础版本并重新校验，失败则要求重新选择商品。
15. 保存成功产生新的门店配置版本；同步失败的终端继续使用上一份有效完整缓存。
16. 商品或 Option 停用后食客端隐藏，关系和历史订单仍可解释；重新启用遵循各自关系状态。
17. 查看与编辑权限正确控制入口，关键变更具有操作日志。
18. 中英文、桌面和窄屏均可完成主要流程；键盘焦点、状态文本和排序替代操作可用。
19. TypeScript、结构验证和浏览器主流程测试通过，控制台无新增错误。
20. 现有关系全部迁入方案1，方案2初始为空；切换方案 Tab 不改变 `activeSchemeCode`。
21. 方案2可通过组 / 类 / 菜三列跨分类多选商品，并在 Option 设置弹窗累计多个动作、多个 Option 和不同价格的关系篮。
22. Category 只过滤 Option；一次选定价格应用于当前多选 Option，加入关系篮后可以逐条改价或删除；重复动作 + Option 更新价格而不重复新增。
23. 方案2预览将商品集合与关系篮展开并只写入 `SCHEME_2`；保存后方案1数据保持不变。
24. 门店一次只启用一个方案。启用切换与配置保存分离，空方案切换有二次警告，成功后终端快照只包含启用方案。
25. 升级事务幂等地创建“未分类”、回填方案和 Category、保留历史关系字段并默认启用方案1；失败整店回滚，升级期间终端持续获得原方案1配置。
26. 方案2只提交明确商品 ID；预览和提交显式携带 `SCHEME_2`，服务端拒绝缺失或非法方案码。新关系使用稳定追加顺序，已保存方案2关系可通过 scheme-aware 抽屉继续维护。
27. 切换启用方案只基于已持久化数据；脏草稿不会被计入或隐式生效。无启用权限、版本冲突和失败请求保持原方案不变，幂等重试不重复递增版本或审计。
28. 停用共享 Option 的确认按两个方案分别显示影响，并标明当前启用方案；Category 切换保留跨分类已选 Option 且始终可见、可移除。
29. 方案 Tab、动作、价格、Option、关系篮和冲突摘要具有明确键盘、焦点及读屏语义；方案2弹窗在窄屏使用单主滚动区和固定操作区。

## 测试策略

- **仓储集成测试**：原子事务、方案隔离、方案2价格/状态/顺序/移除不影响方案1、停用引用保护、配置版本递增、并发版本冲突和回滚；迁移默认启用方案1、字段保留、未分类回填、唯一索引替换、幂等重跑、失败回滚和滚动部署兼容；商品查询快照的创建、排除、过期和门店隔离；全筛选选择后商品新增或状态变化使 token 整体失效；显式 ID 选择中的状态变化生成不可用候选；公共库新增 Option 后向导基础版本刷新与重新校验。

## 视觉方向

沿用 eMenu 本地配置 Shell 已确认的浅灰背景、白色一体化工作区、轻描边、低阴影、圆角和蓝色强调色。动作使用标签和明确文字区分；不依赖颜色单独表达语义。总览保持信息密度，但不使用装饰性统计卡或多层卡片嵌套。

视觉伴侣中的确认结果为：

- 方案1主流程为“商品 → 动作 → Option”。
- 方案2采用参考图方向的“动作、Category、Option、价格”分段面板，并使用已确认的 A“分段选择 + 关系篮”。
- 两个方案独立持久化，通过方案 Tab 切换编辑，通过单独的门店级开关决定终端生效方案。
- 总览以“动作 + Option”聚合，不采用全量商品矩阵。
- 保留右侧单商品四动作维护抽屉。
- 批量入口和单商品入口编辑同一份原子关联数据，不形成两套配置。
