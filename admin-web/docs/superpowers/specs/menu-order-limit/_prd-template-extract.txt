[2] 第一部分：总体架构与核心口径
[] 采用“统一规则模型 + 统一判定引擎 + 服务端最终裁决”的架构。
[] Plain Text```mermaidflowchart LR    A["后台规则设计器"] --> B["规则管理 API"]    B --> C["门店规则存储"]    C --> D["统一限购判定引擎"]    E["POS / Kiosk / eMenu / SDI"] --> F["客户端预校验"]    F --> D    D -->|通过| G["加入购物车或提交订单"]    D -->|超限| H["服务员密码授权"]    H --> I["授权放行凭证"]    I --> D    D --> J["规则命中与授权审计"]```
[] 核心原则：
[] 后台、模拟器、客户端和服务端共用同一套规则 DTO 与计算语义。
[] 客户端预校验用于及时禁用商品、展示剩余额度。
[] 服务端在加入购物车或提交订单时做最终校验，客户端结果不能替代服务端。
[] “按人限购”正式更名为“按人数限购”，不区分具体食客。
[] 按人数限额计算：
[] Plain Text实际限额 = 配置人均限额 × 有效就餐人数
[] 分类规则统计分类内全部商品的数量总和。
[] 菜品规则按每个商品分别统计。
[] 每轮规则只统计当前轮。
[] 多轮规则根据当前轮命中的轮次区间取对应限额，各轮独立统计。
[] 与轮次无关规则统计订单生命周期内全部轮次。
[] 未配置表示不限制；显式配置 0 表示禁止下单。
[] 本次操作导致超限时，不直接写入购物车或订单，而是进入授权流程。
[] 授权范围支持：
[] 本次操作
[] 当前轮
[] 当前订单
[] 多条规则同时命中时采用 AND 语义；没有有效授权时，任意一条不满足即拒绝。
[] 授权只能放行已明确命中的规则和对象，不能成为无范围的全局绕过开关。
[] 所有授权记录必须包含员工、门店、订单、规则、商品、超限数量、授权范围和时间。
[2] 第二部分：12 种场景的统一规则模型
[] 定义：
[] N：有效就餐人数。
[] L：后台为当前人数区间、轮次区间、分类或菜品配置的数量。
[] 按订单实际上限：Limit = L。
[] 按人数实际上限：Limit = L × N。
[] 已用数量：已成功下单数量＋当前购物车待提交数量。
[] 允许增加条件：Used + Δ <= Limit。
[] 点击图片可查看完整电子表格
[3] 分类规则示例
[] 分类 A 包含 a、b、c，按人数每轮配置 L = 2，有效人数 N = 4：
[] Plain Text分类 A 当前轮实际上限 = 2 × 4 = 8 份
[] 允许 a×8、a×3+b×3+c×2 等任意组合。达到 8 份后，只限制分类 A；其他分类不受影响。

[] Plain Texta：1份/人 → 4人订单最多4份b：2份/人 → 4人订单最多8份c：3份/人 → 4人订单最多12份
[] a 达到上限后只限制 a，不连带限制 b、c。
[3] 多轮示例
[] 分类 A 按订单多轮配置：
[] Plain Text第1轮：3份第2轮：2份第3轮：1份第4轮及以后：0份
[] 每轮使用自己的数量池。第四轮配置为 0，表示分类 A 从第四轮开始禁止下单，但可通过服务员授权放行。

[] Plain Textundefined / 未配置：规则不覆盖该对象0：明确禁止正整数：允许的最大份数

[2] 第三部分：服务员密码授权与临时放行

[3] 三种授权范围
[] 点击图片可查看完整电子表格
[] 授权不能默认放行所有菜单限制。例如分类 A 超限后授权，只放行：
[] Plain Text当前订单 + 命中的规则 + 分类A + 选定授权范围
[] 分类 B、其他商品以及其他未授权规则仍需正常校验。
[3] 授权流程
[] 顾客或员工增加商品。
[] 规则引擎返回一个或多个超限结果。
[] 客户端拒绝写入，并展示：
[] 规则名称
[] 商品或分类
[] 当前统计数量
[] 规则限额
[] 本次增加数量
[] 超出数量
[] 服务员选择授权范围。
[] 输入员工密码。
[] 服务端校验员工状态、门店范围和权限。
[] 服务端签发放行凭证。
[] 系统携带凭证重新执行原操作。
[] 规则引擎重新校验；凭证匹配后放行。
[] 写入订单并记录授权审计。
[3] 多规则同时命中
[] 一次操作可能同时命中：
[] 分类总量规则。
[] 单品数量规则。
[] 每轮规则。
[] 与轮次无关规则。
[] 授权弹窗应合并展示全部命中项。服务员确认后，凭证包含明确的规则 ID 列表；未包含的规则仍然阻止操作。这样可以一次输入密码处理同一次操作的多个冲突，但不会扩大授权范围。
[3] 放行凭证模型
[] 凭证至少绑定：
[] Plain TextmerchantIdstoreIdorderIdruleIdsruleVersiontargetKeysroundNoscopeoperationIdauthorizedByauthorizedAtexpiresAt
[] 安全要求：
[] 密码只提交给服务端验证，不存入浏览器或订单明文。
[] 凭证由服务端签名，客户端不能自行构造。
[] “本次操作”使用幂等 operationId，避免网络重试重复消费。
[] 当前轮凭证必须绑定 roundNo。
[] 当前订单凭证只能用于原订单。
[] 规则版本变化后旧凭证失效。
[] 授权仅绕过数量限制，不绕过售罄、停售、年龄限制、支付限制等其他业务规则。
[3] 权限建议
[] 授权能力按角色拆分：
[] order_limit.authorize.once

[2] 第六部分：统计边界与订单生命周期
[3] 轮次定义
[] “轮次”以订单成功提交批次为边界：
[] 新开订单时 currentRound = 1。
[] 当前购物车属于当前轮。
[] 当前轮至少有一个商品成功提交后，该轮完成。
[] 下一次开始点单时进入下一轮。
[] 提交失败、授权取消或网络失败不增加轮次。
[] 同一提交请求重试必须保持原轮次和幂等请求号。
[] 统计方式：
[] Plain Text每轮：当前轮已提交数量 + 当前购物车数量多轮：同上，但限额由当前轮命中的轮次区间决定与轮次无关：全部历史轮次有效数量 + 当前购物车数量

[3] 人数变化

[] Plain Text包含儿童：adultCount + childCount排除儿童：adultCount

[] 人数减少：重新计算限额。

[] 已存在当前轮或当前订单授权时，授权仍只覆盖原规则和目标。

[] 读取最新已用数量。
[] 重新执行规则判定。
[] 通过后原子写入订单与限额使用记录。
[] 版本冲突时客户端刷新订单并重新校验。
[] 客户端显示的“剩余可点数量”只是提示，不能作为最终准入依据。
