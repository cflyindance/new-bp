# eMenu 调味系统示例 Option 默认分类补充设计

## 1. 背景与目标

新建的调味数据库已经把系统示例 Option 分配到“香辛料、基础调味、酱料”。旧门店数据库升级分类功能时，现有 Option 会统一进入“未分类”，导致“添加 Option”弹窗中的三个默认分类没有可选数据。

本次增加一次幂等的数据补充：仅识别系统示例 Option，并在它仍处于“未分类”时按照固定编码写入默认分类。页面结构、Option 选择交互、门店自建 Option 和已完成的人工分类均不改变。

## 2. 采用方案

采用固定 Option 编码映射，不使用名称关键词推断，也不重建整套调味数据。

固定编码比名称稳定，不受中英文名称修改影响；限制为“当前仍处于未分类”可以保护门店人工配置；在数据库标准化阶段执行可同时覆盖旧数据库和已完成分类升级但尚未手工整理的数据。

## 3. 默认映射

| 默认分类 | 系统示例 Option 编码 |
| --- | --- |
| 香辛料 | `CILANTRO`、`SCALLION`、`GARLIC`、`CHILI`、`BLACK_PEPPER`、`GINGER`、`ONION`、`CUMIN` |
| 基础调味 | `PEANUT`、`SALT`、`SUGAR`、`VINEGAR`、`SESAME` |
| 酱料 | `SOY_SAUCE`、`SESAME_OIL`、`MUSTARD`、`MAYO`、`KETCHUP`、`HOT_SAUCE`、`CHEESE` |

编码比较使用标准化后的大写值。无法识别的编码继续保留在“未分类”。

## 4. 数据处理规则

数据库加载时沿用现有分类标准化流程，按以下顺序执行：

1. 创建缺失的三个默认分类与系统“未分类”。
2. 把分类引用缺失或无效的 Option 归入“未分类”。
3. 遍历当前位于“未分类”的 Option；编码命中固定映射时，将其 `categoryId` 更新为目标默认分类。
4. 其他 Option 不做任何修改。

仅以下条件同时满足时允许回填：

- Option 当前分类为系统“未分类”，或旧数据在同一次标准化中刚被归入“未分类”。
- Option 编码命中固定系统示例映射。
- 目标默认分类存在。

以下数据不得被移动：

- 已属于任意有效分类的 Option，包括门店手工创建的分类。
- 编码未命中的门店自建 Option。
- 门店自建 Option 即使名称与系统示例相同，但编码不同。

Option 的启用状态、名称、价格、排序以及商品动作关联均保持不变。

## 5. 幂等性与审计

分类创建、无效引用修复和系统示例回填属于同一次分类标准化事务。只有实际发生数据变化时：

- 配置版本整体提升一次。
- 写入一条现有 `migrate_option_categories` 审计记录。
- 持久化数据库一次。

第二次及后续加载时，由于系统示例 Option 已位于有效分类，不再修改数据，不重复提升版本，也不重复写入审计。

本次不新增人工触发按钮、不新增 API，也不允许通过该迁移覆盖人工分类。

## 6. 失败与兼容处理

- 目标默认分类缺失时，标准化流程应先创建该分类，再执行回填。
- Option 缺少编码、编码为空或编码未知时，保持在“未分类”，数据库仍可正常加载。
- 若一个旧库包含重复编码，只要对应记录均处于“未分类”，均按相同映射回填；本次不承担重复数据清理。
- 数据库写入失败时沿用现有加载/持久化错误处理，不在前端制造部分成功状态。

## 7. 验收与测试

自动化验证至少覆盖：

1. 无分类字段的旧数据库升级后，`CILANTRO`、`SALT`、`SOY_SAUCE` 分别进入三个默认分类。
2. 全部固定系统示例编码均进入表格规定的分类。
3. 未知编码的门店自建 Option 保留在“未分类”。
4. 已手工放入其他有效分类的系统编码 Option 不被移动。
5. Option 状态、排序及动作关联在回填前后不变。
6. 第一次回填只提升一次版本并只写一条迁移审计；第二次加载版本和审计数量不变。
7. 新建数据库的分类结果与旧数据库回填结果一致。
8. “添加 Option”弹窗加载后，三个默认分类均展示对应 Option，“未分类”只展示未命中的数据。

## 8. 非目标

- 不根据 Option 名称自动猜测分类。
- 不自动归类门店后续新建的 Option。
- 不增加批量移动分类或自动整理入口。
- 不调整“类 + Option”选择器的视觉与交互。
