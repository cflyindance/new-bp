# TipOut 当前员工全场景测试数据设计

状态：A 方案已由用户书面确认；按当前会话分阶段执行。仅用于本地演示与自动测试，不接入真实支付。

## 目标与数据边界

使用当前员工目录中的员工 ID、所属门店、角色，不创建虚构员工、不修改员工档案。按当前门店读取全部员工，而非仅取当前页面筛选出的员工。人员在各自门店生成数据，不能串店或靠姓名合并同名员工。

默认清单展示本地今天向前一个月（含今天）。底层按固定日历日期、门店 ID、员工 ID 和场景版本计算，不以“距今天几天”作为随机种子，因此刷新、跨天及增删其他员工都不改变已有日期的数据。按稳定员工种子偏移轮换八种基础组合，任何连续一个月均覆盖；已被正式快照占用的日期只展示历史结果，不以场景覆盖。

## 统一数据源

建立只读场景提供器，考勤、员工原始小费、员工订单及销售额、小费池来源金额从同一员工日事实派生。汇总、明细及员工每日页面使用同一提供器；不再分别生成同一业务事实。按规则计算金额仍复用现有分配引擎，不预先伪造成功结果。

每条事实包含门店、员工 ID、日期、场景编号、打卡片段、原始打卡工时、POS 修正后工时、订单明细与数量、销售额、小费来源及金额。无订单但有小费的场景明确标注为直接上报小费，不捏造对应订单；有订单无小费时订单小费为 0。小费池引用同一来源，不能为每条规则重复生成新的来源金额。

扩展用例叠加在基础场景上，不挤掉八种基础组合：

- 考勤：单段完整、多段完整、缺下班卡（只取有效片段）、原始 8 小时/POS 修正 10 小时。
- 上限：在隔离测试规则中固定上限 5 小时，分别输入 4/5/8 小时，预期采用 4/5/5 小时；原始打卡工时仍展示原值。不修改用户现有规则以凑出场景。
- 分配：单池、多池、不同角色及权重；多规则读取相同原始工时，各规则独立应用上限。未打卡是员工事实，不创建不打卡规则。
- 金额：零来源、0.01 金额、多人分配尾差、贡献入池和从池分得；断言金额非负、舍入和汇总遵守当前引擎契约，不改变规则算法。
- 整日：全部未打卡但有订单/小费，与未营业（考勤/订单/小费全无）分开。前者不能因有业务数据而让未打卡员工参与；后者入池为 0 且禁止分配。

## 流程状态测试隔离

未分配、自动分配成功、已分配待发放、编辑未确认、重新确认成功/失败、已发放锁定等流程通过独立浏览器上下文和真实操作产生。对存储失败、考勤读取失败、跨页面重复提交等进行测试注入，不混入正常演示日期，也不向当前浏览器写入假发放记录。

隔离用例只复制当前员工及规则到测试上下文，自动测试销毁后不影响用户浏览器。保存前后核对原有分配与发放存储未被场景初始化修改；不提供静默清空、覆盖快照或重置按钮。

## 场景清单与入口

日期汇总增加低强调的“测试场景清单”入口，打开只读清单，可查看当前门店最近一个月的员工/日期/场景编号、考勤、订单数、原始小费、原始/有效工时及预期断言，并导出 CSV。清单明确标记“演示数据”；有已保存快照的日期标记“已有快照，以历史结果为准”，不能保证原快照等于本次生成的新场景。

多人场景清单按日期倒序、员工排序；不改变日期汇总现有筛选条件。未被现有规则覆盖的员工照常列出，并注明未参与规则，不能捏造从池分得。

## 验证与交付

1. 每个当前员工在连续一个月内覆盖 B01–B08；稳定性、同名员工隔离、不同门店隔离、月底及跨年区间均自动测试。
2. 三个页面同一员工日事实一致，小费池来源可追溯到员工事实；清单与页面输入一致。
3. 完整考勤、异常片段、POS 修正与上限口径分别核对；未打卡员工始终不因有订单而获得分配。
4. 自动分配、草稿、发放锁定及失败路径在隔离上下文回归，当前浏览器已有快照和发放数据不被初始化更改。
5. 区分“基础数据覆盖”和“规则执行覆盖”：现有规则未配置的分配方式仅在隔离测试中覆盖，不能声称当前门店业务已启用全部方式。
6. 提供覆盖率报告，列出已覆盖、因规则不适用而跳过、未验证项目。“全部场景”限于本设计列出的当前功能，不包含未来退款、真实 Payroll 支付或部分发放。

## 实现风险

当前考勤演示 API 按姓名与日期取值，需要增加门店/员工 ID 上下文，并逐一接入调用方；旧接口仅为未接入场景的兼容入口，不能在新版场景中造成串店。旧数据不迁移；新数据只影响未确认预览和用户明确执行的更新/重新确认。需要为统一数据源接入增加跨页面回归。
