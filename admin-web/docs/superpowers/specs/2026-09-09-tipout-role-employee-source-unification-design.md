# 小费规则角色与员工数据源统一设计

日期：2026-09-09

## 目标

小费规则编辑、分配明细和员工对账统一使用“角色与员工”模块的数据，移除小费模块内部独立维护的角色与员工硬编码名单。规则中的接收方只关联当前门店真实存在的角色和员工；引用失效时阻止继续分配，直到用户修正规则。

本次同时为 Golden Dragon 演示门店补齐默认规则所需的 Busser、Runner、Host 员工，使“不打卡 + 按工时占比 + 手动补录工时”的演示链路完整可用。

## 唯一数据源

新增小费模块共享的花名册目录能力，供规则编辑、分配明细和分配汇总共同使用。

### 角色

角色来源与“角色与员工”页面保持一致：

- 系统角色列表；
- `tipout-employee-role-options-v1` 中的自定义角色；
- 排除 `tipout-employee-role-hidden-system-v1` 中已隐藏的系统角色。

角色名称经过 trim 后作为当前稳定键。不得在小费模块中另设角色常量列表作为页面选项来源。

### 员工

员工唯一来源为 `tipout-employees-roster-v1`。目录输出至少包含：

```js
{
  id: "稳定花名册 ID",
  name: "员工姓名",
  role: "角色名称",
  store: "规范化门店名称",
  active: true
}
```

门店匹配复用现有 Golden Dragon → 上海陆家嘴店、Sakura → 广州天河店的别名规则。员工关联优先使用稳定 `id`；姓名仅用于显示和旧数据兼容。

### 稳定员工 ID 与花名册迁移

“角色与员工”现有新增员工逻辑继续生成并持久化 `roster-${Date.now()}-${randomSuffix}` ID。共享目录读取旧花名册时执行一次幂等规范化：

- 缺少 ID 的员工生成 `roster-legacy-${stableHash(store + "|" + role + "|" + name)}-${ordinal}` 并回写花名册；`ordinal` 是相同规范化门店、角色和姓名在原数组中的从 1 开始序号。
- 重复 ID 保留第一次出现，后续记录按上述 legacy 规则生成新 ID 并回写。
- 已有唯一 ID 原样保留。
- 迁移不改变员工顺序、姓名、角色、门店及业务字段，并触发一次现有 `tipout-roster-updated` 事件。

所有页面使用共享目录返回的员工 ID，不得自行按姓名生成另一套 ID。

### 统一门店规范化

共享目录唯一暴露 `canonicalRosterStoreName(storeName)`。规则门店读取、花名册默认员工写入、旧规则迁移、引用失效校验、分配明细解析和员工对账查询全部先经过该函数。任何页面不得自行复制 Golden Dragon / 上海陆家嘴店等别名表。

## Golden Dragon 默认员工

初始化“角色与员工”演示数据时，为 Golden Dragon 对应的规范门店“上海陆家嘴店”幂等补齐：

| ID | 姓名 | 角色 | 小费类型 |
|---|---|---|---|
| `roster-tipout-golden-busser-carlos-lopez` | Carlos Lopez | Busser | receive |
| `roster-tipout-golden-runner-daniel-ortiz` | Daniel Ortiz | Runner | receive |
| `roster-tipout-golden-host-rachel-scott` | Rachel Scott | Host | receive |

默认工资字段沿用“角色与员工”的演示员工默认结构，金额字段可为 0。若同 ID 已存在，或同一规范门店下已存在相同姓名与角色的员工，则不追加，不覆盖用户数据。

Busser、Runner、Host 已属于系统角色，只保证它们未被小费模块另行重复创建；若用户在“角色与员工”中主动隐藏对应系统角色，则规则引用进入失效状态。

## 规则数据结构与兼容

### 新规则与编辑后的规则

接收方继续保留 `roles` 以兼容现有计算逻辑，并增加员工稳定引用：

```js
{
  roles: ["Busser"],
  pct: 50,
  employeeRefs: [
    { employeeId: "roster-tipout-golden-busser-carlos-lopez", name: "Carlos Lopez" }
  ]
}
```

- 角色选择器只展示共享角色目录中的有效角色。
- 员工选择器按当前规则门店及已选角色实时筛选。
- 保存时写入 `employeeRefs`；显示时按 `employeeId` 获取最新姓名和角色。
- 用户选择角色但未单独勾选员工时，含义仍为该门店该角色下所有有效员工，保持现有按角色规则能力。

### 旧规则

- 只有 `roles`：继续解释为对应角色下全部有效员工，不强制写入 `employeeRefs`。
- 旧字段中存在员工姓名但没有 ID：编辑页按当前门店 + 姓名 + 角色唯一匹配；唯一匹配时转换为 `employeeRefs`，无法唯一匹配时标记失效并要求用户重新选择。
- 不在后台静默批量改写历史规则；只在用户保存编辑结果时落盘新引用结构。

### 手动工时的稳定员工关联

`TipOutManualHours` 的标准记录新增可选 `employeeId`，新记录必须同时保存 `employeeId` 和当前 `employeeName`：

```js
{
  ruleId: "5",
  dateKey: "2026-01-01",
  employeeId: "roster-tipout-golden-runner-daniel-ortiz",
  employeeName: "Daniel Ortiz",
  hours: 6
}
```

新记录主键为 `ruleId + "|" + dateKey + "|" + employeeId`。旧记录没有 `employeeId` 时继续使用旧姓名主键。仓储的 `get`、`seed` 与 `listForEmployee` 接受 `{ employeeId, name, legacyNames }` 员工引用：先按 ID 查找；未找到时按当前姓名及 `employeeRefs` 保存的历史姓名快照唯一匹配旧记录。唯一匹配后，为该记录补写 employeeId 并更新为当前姓名；多条旧记录产生歧义时不自动迁移，并在规则或对账中提示引用异常。员工改名后仍可通过 employeeId 找回历史补录记录。

## 规则失效与阻断

以下任一情况使规则进入“引用失效”状态：

- 接收方角色已被隐藏或删除；
- 指定员工已删除、停用、移出当前门店，或角色不再匹配；
- 旧姓名引用无法唯一映射；
- 接收方角色在当前门店没有任何有效员工。

规则列表和编辑页展示明确的“引用失效”提示及具体缺失项。失效规则：

- 可以打开和编辑；
- 不允许保存为仍然失效的状态；
- 不允许参与新的小费分配；
- 不删除或重算已保存的历史分配结果。

## 分配明细

共享目录提供唯一的 `resolveReceiverEmployees(rule, storeName)` 解析器。分配明细按当前门店规则的接收方调用该解析器：

- 有 `employeeRefs` 时只使用有效的指定员工；
- 没有 `employeeRefs` 时使用接收方角色下全部有效员工；
- 同一员工在同一接收方中按员工 ID 去重；
- 不再使用 `roleEmployees` 硬编码映射。

Golden Dragon 默认规则 `5` 在 2026-01-01 对符合接收方范围且考勤为“未打卡”的员工，通过 `TipOutManualHours.seed` 幂等补录 `6 h`。手动工时记录的 `employeeName` 沿用当前仓储兼容字段；生成记录前由稳定员工 ID 解析最新姓名。已有工时记录（包括 `0 h`）不覆盖。

## 员工对账

员工对账列表的员工范围为当前门店全部有效小费规则接收方的并集。必须复用分配明细相同的 `resolveReceiverEmployees(rule, storeName)`，不得再次实现角色展开或员工过滤逻辑：

- 按员工 ID 去重；
- 同一员工参与多条规则时汇总全部相关规则结果；
- 不属于任何接收方的员工不展示；
- 失效规则不参与新的对账结果生成，但已有历史快照仍可只读查看。

员工对账明细通过 `TipOutManualHours.listForEmployee(dateKey, { employeeId, name, legacyNames })` 读取补录工时。因此 2026-01-01 默认员工的未打卡行显示 `6 h` 与“录入”标签，上下班时间仍为 `—`。

## 同步与刷新

“角色与员工”保存角色或员工后继续触发现有花名册更新事件；小费规则编辑、分配明细和汇总页面在重新进入或收到更新事件后重新读取目录。无需复制数据到第二个小费专用存储。

## 非目标

- 不修改小费池金额、扣除、接收比例或按工时占比算法。
- 不自动创建打卡记录、班次或上下班时间。
- 不把小费规则中临时输入的新名称反向创建为角色或员工；角色和员工必须在“角色与员工”中维护。
- 不批量重算或覆盖历史分配结果。

## 验收标准

1. Golden Dragon 的角色与员工列表出现 Carlos Lopez、Daniel Ortiz、Rachel Scott，重复初始化不会重复新增。
2. 小费规则中的角色选项与“角色与员工”有效角色一致；员工选项只包含当前门店、所选角色下的有效员工。
3. 默认规则 `5` 能关联上述三名接收方员工；分配明细不再读取硬编码 `roleEmployees`。
4. 2026-01-01 中符合“未打卡”的默认接收方员工显示默认 `6 h`，员工对账显示同一补录值与“录入”标签。
5. 员工对账列表只展示当前门店有效规则接收方涉及的员工，并按员工 ID 去重。
6. 隐藏接收方角色、停用或删除指定员工后，规则显示“引用失效”并阻止新的分配，修复引用后恢复。
7. 旧规则按角色继续工作；旧姓名引用可唯一匹配时在保存时升级，不可唯一匹配时要求重新选择。
8. 已有规则、员工、手动工时和历史分配结果不会被默认数据覆盖或删除。
9. 缺失或重复员工 ID 的旧花名册只迁移一次；刷新后 ID 稳定，员工顺序和业务字段不变。
10. 员工改名后仍可通过 employeeId 读取改名前的手动工时；无 ID 旧工时在唯一匹配时升级，歧义时不静默合并。
11. Golden Dragon 与上海陆家嘴店在规则编辑、默认员工、失效校验、分配和对账中被识别为同一门店。
