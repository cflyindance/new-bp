# 品牌—门店统一演示数据设计

> 日期：2026-09-24  
> 状态：已确认，待实现计划  
> 适用范围：商家后台演示环境中的组织、员工、商品、订单、营销、财务及门店经营辅助数据

## 1. 背景与目标

当前项目已经在 `src/config/enterprise-merchant-store.ts`、`src/config/merchant-chain-brand-sync.ts` 和 `src/auth/session-scope.ts` 中建立了部分集团、品牌、门店主数据与 Scope 关系，但员工、商品、订单、营销、财务等业务模块仍存在各自维护演示种子、门店名单或 localStorage 数据的情况。这会造成品牌切换后业务数据范围不一致、跨模块实体无法关联，以及财务汇总与订单明细无法相互验证。

本方案建立一套统一演示场景数据源，使所有业务模块基于同一套集团—品牌—门店体系生成数据，并满足以下目标：

- 品牌视角可以稳定展示同一品牌下的多家门店。
- 品牌提供统一业务模板，门店继承模板并允许有限差异覆盖。
- 员工、商品、订单、营销、支付与财务之间使用稳定 ID 建立可追溯关系。
- 时间型数据围绕当天滚动生成，保证演示页面始终有近期内容。
- 同一天、同一数据版本重复初始化得到相同结果。
- 新版本上线时直接重置旧业务演示数据，不迁移用户对旧演示数据的修改。

## 2. 非目标

- 不在本次改造中重写现有业务页面或统一所有页面组件。
- 不把演示仓库升级为生产后端、离线数据库或通用状态管理框架。
- 不迁移旧演示业务数据中的用户修改。
- 不改变登录状态、语言、主题、导航布局等纯会话或界面偏好。
- 不要求首个提交一次性接完所有页面；允许按下文阶段逐步替换，但每个已接入领域必须通过一致性校验。

## 3. 方案选择

采用“统一场景种子 + 分模块适配器”。

统一场景仓库是演示实体和关联关系的唯一事实源。现有模块不直接依赖一个巨型展示对象，而是通过领域适配器读取自己当前需要的数据结构。这种方式可以保持现有页面接口和交互逻辑，降低一次性重写风险，并允许按领域分阶段接入。

不采用以下方案：

- 全量重写为单一大型状态对象：边界不清，改造面和回归风险过大。
- 仅统一品牌、门店 ID：不能保证订单、员工、商品、营销与财务真正一致。

## 4. 总体架构

数据生成链路为：

```text
组织主数据
  → 品牌业务模板
  → 门店差异覆盖
  → 门店最终目录与人员
  → 经营事件（订单、排班、考勤、活动核销、支付、退款）
  → 派生视图（财务、薪资、小费、营销效果、经营汇总）
  → 各模块适配器
```

建议拆分为以下独立边界：

1. **场景定义层**：声明演示集团、品牌、门店、品牌模板及门店覆盖项。
2. **确定性生成层**：以数据版本、业务日期和实体 ID 为随机种子，生成近期经营事件。
3. **规范化场景仓库**：保存统一实体及引用关系，提供按集团、品牌、门店和日期查询的接口。
4. **领域派生层**：从经营事件计算财务、薪资、营销效果等可复算数据。
5. **模块适配层**：将统一模型转换为现有模块接口，隔离页面与场景内部结构。
6. **版本与重置层**：检测种子版本，清理列入清单的旧业务存储键并重新生成。
7. **一致性校验层**：检查引用完整性、Scope 隔离与金额守恒。

各边界通过显式类型和只读查询接口通信。页面不得直接读取场景内部存储结构，也不得自行复制品牌或门店清单。

## 5. 核心数据模型

### 5.1 组织主数据

组织实体沿用并规范化现有 M 平台模型：

- `Group`：集团。
- `Brand`：经营品牌，以 `merchantId` 作为当前兼容标识。
- `Region`：区域，归属集团或品牌上下文。
- `Store`：门店，必须且只归属一个品牌，并保留集团、区域关系。

组织主数据必须作为所有 Scope 选择器和业务数据的来源。禁止业务模块维护自己的品牌、区域、门店枚举。现有 `enterprise-merchant-store` 可作为初始组织事实源，统一场景只引用其稳定 ID，不再创建第二套组织树。

每个演示品牌预设 2–4 家门店，以覆盖聚合、筛选、跨店对比和单店空状态。

### 5.2 品牌模板与门店覆盖

品牌模板包含：

- 商品分类、商品、规格和菜单结构。
- 品牌基础价格与税务分类。
- 品牌级营销活动、优惠规则和素材引用。
- 可共享的岗位模板和经营参数。

门店覆盖仅保存相对品牌模板的差异：

- 售价调整。
- 商品上下架和库存。
- 营业时间。
- 门店专属活动。
- 门店级配置值。

读取门店最终目录时执行 `品牌模板 + 门店覆盖` 合并。门店编辑写入覆盖层，不反向修改品牌模板。品牌模板更新后，未被覆盖的字段自动继承新版值。

### 5.3 员工与排班

员工必须归属具体门店，并同时保留可推导的品牌与集团关系。岗位、排班、考勤、休息加班、薪资和小费均引用同一员工 ID。一个员工如需在多店工作，通过显式的门店任职或班次关系表达，不能复制为多个无关联员工。

### 5.4 商品与菜单

商品使用品牌级稳定 ID；门店菜单项使用品牌商品 ID 加门店可售状态、价格和库存覆盖。订单项必须引用订单发生时的商品 ID，并保存成交快照字段，以便商品后续变更后仍可解释历史订单。

### 5.5 订单、营销与支付

每笔订单至少关联：

- 集团、品牌、门店。
- 下单时间与业务日期。
- 服务员工或收银员工。
- 商品明细和成交快照。
- 可选营销活动或优惠券核销。
- 小计、折扣、税费、小费、退款及应付金额。
- 一笔或多笔支付记录。

营销核销必须引用有效活动，并同时出现在订单折扣和营销效果中。支付、退款和结算由订单事件派生，不得由财务模块另行生成无来源流水。

### 5.6 财务、薪资与经营汇总

以下数据均由统一事件派生：

- 营业收入、折扣、税费、小费和退款。
- 支付渠道流水与收银审计记录。
- 结算批次及净收入。
- 工时、工资和小费分配。
- 营销曝光、核销、带动订单与优惠成本。

品牌汇总必须等于其门店汇总之和；集团汇总必须等于其品牌汇总之和。货币金额统一使用最小货币单位的整数，展示层再格式化，避免浮点误差。

## 6. 确定性时间与数据生成

初始化器接受以下输入：

- `scenarioVersion`：种子结构与内容版本。
- `anchorDate`：本地业务日期，默认当天。
- `scenarioId`：演示场景标识。

随机值必须来自可复现的伪随机生成器，种子由 `scenarioVersion + anchorDate + entityId + generatorNamespace` 构成。禁止在领域生成器中直接使用不可控的 `Math.random()`。

生成包含 `anchorDate` 在内的最近 30 个本地业务日，即 `anchorDate - 29 天` 至 `anchorDate`。固定实体 ID（品牌、门店、员工、商品、活动）不随日期变化；订单、考勤、支付等事件 ID 由业务日期和稳定序号构成。相同输入应生成字节级等价的规范化数据；跨日初始化仅滚动时间窗口及相应事件。

各门店数据需要有受控差异，例如客流量、客单价、热销商品、人员规模和活动参与度，以便品牌视角下的跨店比较具有意义。差异由显式门店画像或稳定参数控制，而非散落在页面代码中。

## 7. 存储、版本与重置

统一场景仓库维护独立的元数据：

- 当前 `scenarioVersion`。
- 当前 `scenarioId`。
- 最近生成的 `anchorDate`。
- 规范化数据或可重建缓存。

启动时出现以下任一情况即重建场景：

- 未找到统一场景。
- `scenarioVersion` 不一致。
- `anchorDate` 已变化，需要滚动近期时间窗口。
- 数据校验失败且可通过重建恢复。

首次启用统一场景或版本升级时，清除明确登记的旧业务演示存储键。清理清单由各领域适配器声明，禁止用前缀模糊删除全部 localStorage。登录凭证、语言、主题、导航布局、视角选择等不在清理范围内。

页面后续产生的演示编辑写入统一场景的运行时覆盖层。运行时覆盖分为两类：稳定实体覆盖以实体 ID 保存，在 `anchorDate` 滚动后继续应用；时间型事件覆盖以稳定事件 ID 保存，只要事件仍位于新的 30 日窗口内就重新应用，事件滚出窗口后随之丢弃。当天刷新不应无条件清除同版本覆盖；只有版本升级、用户显式重置或不可恢复的数据损坏才执行全量业务重置。

## 8. Scope 与查询语义

所有适配器接受统一 Scope：集团、品牌、门店及可选日期范围。

- 门店视角：只返回当前门店数据。
- 品牌多门店视角：品牌必选；未选具体门店时聚合品牌全部授权门店。
- 集团视角：按授权品牌、区域和门店过滤后聚合。
- 权限过滤必须先于聚合，不能先生成全量结果再只隐藏名称。
- Scope 中出现不属于当前品牌的门店时视为无效组合，收敛到空门店选择或授权默认值，不得泄漏其他品牌数据。

现有顶栏、页内门店选择器和 iframe 桥接仍可保留，但选项必须来自统一组织主数据，业务查询必须使用同一个有效 Scope 解析结果。

## 9. 模块接入范围

### 9.1 团队

员工、岗位、排班、考勤、休息加班、薪资和小费接入统一员工与门店关系。TipOut/Payroll 等内嵌或兼容页面通过适配器及现有桥接格式读取数据。

### 9.2 商品

分类、商品、规格、菜单、门店价格、库存和上下架状态接入品牌继承模型。品牌编辑作用于模板；门店编辑作用于覆盖。

### 9.3 订单

订单列表、订单明细、退款和相关经营汇总从统一订单事件读取。订单必须关联有效门店、商品成交快照、员工、营销核销和支付记录。

### 9.4 营销

广告、优惠券、活动、会员触达及效果数据使用统一品牌活动和门店覆盖；核销与带动订单由订单关联派生。

### 9.5 财务

支付记录、收银审计、结算、收入汇总、退款、工资和小费支出从订单、支付、考勤和薪资规则派生。

### 9.6 经营辅助

硬件、门店配置、部署等已有明确门店归属的数据统一引用相同门店 ID。它们可以保留独立领域状态，但不得维护第二套门店主数据。

## 10. 分阶段实施边界

该目标涉及多个领域，实施计划必须按可独立验收的阶段拆分，避免一次性替换全部模块：

1. **基础阶段**：统一类型、场景定义、确定性生成器、仓库、版本重置和一致性校验；接管所有品牌/门店选项。
2. **商品与订单阶段**：接入品牌模板、门店覆盖、订单与支付，先形成可验证的核心经营闭环。
3. **团队阶段**：接入员工、排班、考勤、薪资与小费，并关联订单服务员工。
4. **营销阶段**：接入活动、优惠券、广告和订单核销。
5. **财务阶段**：用统一事件替换独立财务种子，完成逐笔与汇总守恒。
6. **经营辅助与清理阶段**：统一硬件、配置等门店引用，删除已无消费者的旧种子与兼容逻辑。

每个阶段只迁移登记过的模块和存储键；未迁移模块继续使用兼容适配，但不得引入新的品牌或门店常量。阶段完成标准包含代码接入、自动化校验和对应页面联调。

## 11. 错误处理与可观测性

- 生成阶段发现重复 ID、孤立引用、错误品牌归属或金额不守恒时，视为场景构建失败。
- 开发环境输出可定位到实体 ID 和校验规则的错误，并使自动化校验失败。
- 浏览器运行时首次发现可恢复损坏时，清理统一业务场景并重建一次。
- 同一启动周期重建后仍失败，不得无限循环；保留诊断信息并向页面返回安全空数据或明确错误态。
- 适配器不得静默补造未知品牌、门店、商品或员工。
- 场景元数据记录版本和锚点日期，便于复现问题。

## 12. 验收标准

### 12.1 组织与隔离

- 品牌切换后，只出现该品牌下的门店、员工、商品、订单、营销和财务数据。
- 同一门店在所有模块中的名称、ID、品牌和区域归属一致。
- 单店、品牌多门店、集团三种视角均按权限裁剪，且无跨品牌数据泄漏。

### 12.2 跨领域一致性

- 订单商品存在于该门店合并后的菜单中。
- 订单员工归属该店，或具有该店的显式跨店任职关系。
- 优惠核销关联有效活动，并同时反映在订单折扣、营销效果和财务净收入中。
- 每笔订单满足 `应付 = 小计 - 折扣 + 税费 + 小费 - 退款调整`，具体符号约定由统一计算函数定义。
- 支付与退款净额和订单已结算金额一致。
- 排班、考勤、工资和小费使用同一员工 ID。
- 品牌汇总等于旗下门店汇总之和，集团汇总等于旗下品牌汇总之和。

### 12.3 稳定性与重置

- 同一天、同一版本、同一场景重复初始化得到相同结果。
- 日期变化后时间窗口滚动，稳定实体 ID 不变。
- 种子版本变化后，登记的旧业务演示数据被重置并重新生成。
- 登录、语言、主题和导航等非业务偏好不受重置影响。

### 12.4 演示完整性

- 每个已接入模块至少覆盖正常数据、边界数据和可展示空状态。
- 每个品牌有多门店数据，门店之间存在可解释的经营差异。
- 列表、筛选、图表和汇总在包含当天的最近 30 个本地业务日范围内均有稳定样本。

## 13. 测试策略

### 13.1 单元测试

- 品牌模板与门店覆盖合并规则。
- 稳定伪随机及日期窗口。
- 稳定实体 ID 与时间型事件 ID。
- 金额、小费、工资、退款和结算计算。
- 版本检测与精确存储键清理。

### 13.2 跨领域契约测试

- 全部外键可解析且归属关系正确。
- 订单—商品—员工—营销—支付—财务链路完整。
- 门店、品牌和集团聚合守恒。
- 不同 Scope 查询结果互不泄漏。
- 每个适配器输出符合现有模块所需结构。

### 13.3 页面联调测试

- 在单店、品牌多门店、集团视角切换 Scope。
- 逐一验证团队、商品、订单、营销、财务页面的数据范围。
- 验证内嵌页面在 Scope 变化后刷新到同一门店数据。
- 验证版本升级后的重置行为和非业务偏好保留。

## 14. 实现约束

- 新代码不得新增业务模块私有的品牌或门店静态名单。
- 金额以最小货币单位整数存储；日期使用明确的本地业务日期工具，避免直接混用 UTC 字符串切片。
- 统一模型与各模块展示模型分离，适配器保持单向转换。
- 生成器为纯函数或可注入时钟与随机源，确保测试可重复。
- 对现有 `vendor/emenu-new` 源码如有修改，必须遵守项目级构建发布规则，从项目根目录执行 `npm run build:emenu-new-embed -- --skip-install` 并验证嵌入产物。

## 15. 完成定义

当所有登记范围内的业务模块均从统一场景或其适配器读取数据，不再维护独立品牌/门店名单；所有跨领域一致性、Scope 隔离、确定性生成和版本重置测试通过；关键页面完成品牌和门店切换联调后，本项目才视为完成。
