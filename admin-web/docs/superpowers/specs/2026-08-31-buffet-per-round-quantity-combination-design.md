# 自助餐每轮组合数量规则设计

> 状态：方案已确认，待用户审阅书面规范
> 日期：2026-08-31
> 适用范围：前厅管理中心 / 自助餐规则
> 权威关系：本文是《前厅管理中心「自助餐规则」独立模块设计》和《自助餐规则“菜品集”限购对象设计》的规范性扩展。涉及每轮总量、指定对象上限及相同菜品上限的组合配置时，以本文为准。

## 1. 设计结论

采用“一条规则内配置主限购与附加约束”的方案。

规则类型页现有三个维度保持不变，不新增“限制方式”或其他规则类型字段：

1. 限购主体：按桌/订单限购、按人数限购；
2. 额度周期：沿用当前模块已有选项；
3. 限购对象：按菜品、按分类、按菜品集。

当额度周期为“每轮”时，在现有“限购数量”步骤内提供三个可组合的数量区块：

1. 每轮下单菜品总数；
2. 指定对象最多下单；
3. 每轮相同菜品最多下单。

一条规则至少启用一个数量区块。启用多个区块时全部按逻辑“并且”执行，不采用覆盖关系。规则在页面和生命周期中仍是一条业务规则，不拆分成用户可见的关联子规则。

## 2. 适用场景

本文同时满足两组业务方案：

- 分类方案：每轮总量 + 指定菜品/指定分类上限 + 相同菜品上限；
- 菜品集方案：每轮总量 + 指定菜品/指定菜品集上限 + 相同菜品上限。

| 业务表达 | 限购主体 | 额度周期 | 限购对象 |
|---|---|---|---|
| 每轮指定分类最多 | 按桌/订单 | 每轮 | 按分类 |
| 每人每轮指定分类最多 | 按人数 | 每轮 | 按分类 |
| 每轮指定菜品集最多 | 按桌/订单 | 每轮 | 按菜品集 |
| 每人每轮指定菜品集最多 | 按人数 | 每轮 | 按菜品集 |
| 每轮指定菜品最多 | 按桌/订单 | 每轮 | 按菜品 |
| 每人每轮指定菜品最多 | 按人数 | 每轮 | 按菜品 |

总量和相同菜品区块仅在“每轮”周期中出现。每单/整单累计和分轮次规则继续沿用现有数量矩阵。

## 3. 计算口径

设 `N` 为有效就餐人数，`Q_total` 为当前轮全部有效菜品数量，`Q_dish(d)` 为当前轮菜单身份 `d` 的数量，`Q_category(c)` 为分类合计，`Q_set(s)` 为菜品集合计。

按桌/订单限购时，配置值直接作为整桌共享额度；按人数限购时，配置值乘 `N`，仍由整桌共享，不识别具体食客：

```text
按桌/订单：Effective(value) = value
按人数：Effective(value) = value × N
```

`N` 的权威来源是订单的“有效就餐人数”字段，儿童是否计入沿用规则中的有效人数计算口径。创建第一轮时，按门店、日期、活动周期、营业时段、会员和启用状态锁定本订单的候选规则集及菜单快照；人数区间不在此时淘汰候选规则。每次加菜、改量和提交轮次前读取最新订单版本的 `N`，并在已锁定候选规则集中重新选择覆盖当前 `N` 的人数区间单元格。订单进行中发布或启用的新规则不加入该订单快照。

每条按人数规则的人数区间必须从 1 连续覆盖到 `supportedPartySizeMax`，不得断档或重叠。`N` 在该范围内却找不到唯一单元格时返回 `PARTY_RANGE_NOT_COVERED` 并拒绝数量操作；`N > supportedPartySizeMax` 返回 `PARTY_SIZE_ABOVE_SUPPORTED_MAX`。人数变更后：

- 已提交历史轮次不追溯撤销；
- 未提交当前轮按新 `N` 重新校验；
- 人数下降导致当前量超限时，后续增加数量被拒绝，允许减量、退菜或通过对应数量规则授权；
- 人数上升导致最低数量提高时，仅在提交当前轮时检查；
- 已有授权按批准时记录的绝对数量阈值判断，不因人数变化自动提高阈值。

## 4. 现有业务流程中的页面设计

步骤保持不变：

```text
规则类型 → 场景配置 → 商品配置与限购数量 → 超限授权 → 生效范围 → 确认发布
```

### 4.1 规则类型与场景配置

- 规则类型保持现有三个维度及交互，不增加卡片、字段或步骤。
- 预览仍显示“限购主体 × 额度周期 × 限购对象”。
- 按桌/订单不显示人数区间；每轮使用固定配置值。
- 按人数继续使用当前人数区间；每个区间保存人均配置值。
- 本文能力固定按每轮重新统计，不增加轮次区间。

### 4.2 商品配置

继续按门店独立保存商品范围：

- 按分类：选择正式菜单分类；每个分类是独立共享数量池。
- 按菜品：选择具体菜品；每个菜品独立配置上限。
- 按菜品集：每家门店一个菜品集，至少 2 个有效菜品，允许跨产线，全部成员共享额度。

商品范围只服务“指定对象最多下单”区块，不缩小总量和相同菜品的统计范围。

### 4.3 限购数量

页面顶部展示三个顺序固定的规则级区块开关；同一条规则的所有门店使用相同启用组合。切换门店后，仅切换各区块的数量单元格和商品范围。一条规则不得出现门店 A 启用总量、门店 B 关闭总量的状态。

#### A. 每轮下单菜品总数

区块可启用或关闭。启用后提供“最少下单”和“最多下单”：两者至少填写一个；同时填写时必须 `Min <= Max`；`0` 是有效配置，空值表示未配置。

```text
按桌/订单：Min <= Q_total <= Max
按人数：Min × N <= Q_total <= Max × N
```

`Q_total` 统计当前轮该门店所有有效菜品，不受所选对象范围限制。

#### B. 指定对象最多下单

区块可启用或关闭，并沿用当前商品选择和数量矩阵：

- 分类：每个已选分类分别配置一个共享上限；
- 菜品：每个已选菜品分别配置独立上限；
- 菜品集：全部成员配置一个跨产线共享上限；
- 只提供最多，不提供最少。

```text
按桌/订单：Q_object <= L
按人数：Q_object <= L × N
```

关闭时商品范围可保留为草稿信息，但发布不要求该区块的数量矩阵；重新启用时恢复原配置。切换限购对象仍二次确认并清空不兼容配置。

#### C. 每轮相同菜品最多下单

区块可启用或关闭。启用后，每个门店、每个人数区间配置统一最大值：

```text
按桌/订单：任意 Q_dish(d) <= L
按人数：任意 Q_dish(d) <= L × N
```

该区块作用于当前轮全部有效菜品。菜品身份为 `storeId + productLineId + dishId`；相同 `dishId` 位于不同产线时分别累计。

### 4.4 后续步骤

- 继续支持“本次操作 / 当前轮 / 当前订单”三种服务员密码授权。
- 授权对象固定到“来源业务规则 ID + 统计对象键”，不以区块级授权覆盖同区块的其他分类、菜品或菜品集。一次操作命中多个对象或多条规则时，服务员必须明确勾选要放行的每个失败项，未勾选项继续阻止操作。
- “本次操作”授权键为 `ruleId + 完整运行时约束键 + operationId`，仅放行该原子操作。
- “当前轮”授权键为 `ruleId + 完整运行时约束键`，其中包含实际 `roundId`，仅放行该轮的同一统计对象。
- “当前订单”授权键为 `ruleId + 去除 roundId 的静态对象键 + orderId`，可在订单后续轮次命中同一统计对象；其 `approvedFinalQuantity` 是每轮绝对阈值，各轮分别累计和判断，不是跨轮整单累计阈值。
- 三种授权均不自动覆盖其他规则、其他统计对象或下一订单。
- 每条授权记录必须保存 `approvedFinalQuantity`，即批准后该来源规则对该统计对象允许达到的绝对数量。授权有效期内只有 `finalQuantity <= approvedFinalQuantity` 才可放行；超过阈值必须重新授权。人数下降不会提高已批准绝对阈值。
- 同一规范键由多条原始规则共同限制时不得先合并后授权；逐条计算每个来源规则的有效上限。对某条规则存在有效授权时，以该规则的 `approvedFinalQuantity` 替代其计算上限；没有授权时使用原计算上限。最终允许量仍取各来源规则当前有效上限中的最小值。
- 授权后的数量进入真实累计；再次增加数量时，只有仍处于有效授权范围且未超过批准阈值的同一失败项可继续放行。
- 授权可绕过三个区块中的最大上限；总量最低不能用数量授权绕过。
- 生效门店必须完成对应门店的组合数量配置。
- 确认页按区块展示启用状态和摘要，不新增规则类型维度。

## 5. 组合执行

同一规则内及不同规则间的所有命中约束全部执行：

```text
每轮总量范围 AND 指定对象上限 AND 相同菜品上限
```

总量范围合并：

```text
EffectiveMin = max(所有命中的有效下限)
EffectiveMax = min(所有命中的有效上限)
EffectiveMin <= Q_total <= EffectiveMax
```

只有统计左侧完全相同的上限才能取最小值。发布判重使用静态约束键：

```text
总量：storeId | period | roundRangeIndex | total
菜品：storeId | period | roundRangeIndex | dish | productLineId | dishId
分类：storeId | period | roundRangeIndex | category | productLineId | categoryId
菜品集：storeId | period | roundRangeIndex | dish_set | ruleId
相同菜品：storeId | period | roundRangeIndex | same_dish | productLineId | dishId
```

本文每轮组合规则固定使用 `roundRangeIndex = 0`。运行时将静态键中的周期槽位替换为订单的实际 `roundId`，其余对象身份保持一致；发布判重只使用静态键，运行时累计和授权使用运行时键。

同一规范键的对象上限合并：

```text
最终上限 = min(固定每轮上限, 人均上限 × N, 其他命中上限)
```

不同规范键之间不得归并成一个标量；分类、菜品集、单菜品、总量和相同菜品约束各自保留，并按逻辑“并且”分别校验。菜品集约束键包含规则 ID，因此不同菜品集即使成员部分重叠也不会误合并；成员菜品仍可同时命中各自的单品、分类和相同菜品约束。

例如每轮总数 2～8、肉类最多 5、相同菜品最多 2。“五花肉 2 + 牛肉 2 + 羊肉 1 + 蔬菜 3”允许；“五花肉 3 + 牛肉 1”因相同菜品超限而拒绝。菜品集方案只需将肉类替换为菜品集成员合计。

## 6. 校验时机

| 操作 | 总量最多 | 指定对象上限 | 相同菜品上限 | 总量最少 |
|---|---:|---:|---:|---:|
| 加菜、批量加菜、增加数量 | 是 | 是 | 是 | 否 |
| 减菜、退菜、取消未提交明细 | 重算但不阻止 | 重算但不阻止 | 重算但不阻止 | 否 |
| 提交/结束当前轮 | 是 | 是 | 是 | 是 |
| 进入下一轮 | 先提交上一轮 | 先提交上一轮 | 先提交上一轮 | 是 |
| 结账且有未提交当前轮 | 是 | 是 | 是 | 是 |
| 取消/作废当前轮 | 否 | 否 | 否 | 否 |

空轮不触发最低数量。当前轮存在有效菜品并尝试提交时必须达到最低数量。批量操作整批原子校验。

## 7. 冲突与可满足性

草稿允许保存不完整或冲突配置；发布、启用和运行时硬校验：

1. 一条规则至少启用一个数量区块；
2. 总量区块至少配置一侧，且双侧满足 `Min <= Max`；
3. 指定对象区块启用时，生效门店必须有有效商品范围和完整上限；
4. 菜品集至少包含 2 个去重后的有效菜单身份；
5. 相同菜品区块启用时，生效门店和人数区间必须配置上限；
6. 同门店、同主体、同周期、同对象且生效范围有交集的重复规则禁止发布；
7. 不同计算口径可以叠加；
8. 对门店支持的全部人数值验证合并后的最低、最高和对象容量存在整数可行解。

适用范围交集至少包含门店、人数区间、日期、活动周期、营业时段、会员范围和启用状态。诊断必须指出门店、人数场景、约束区块和参与冲突的规则。

### 7.1 重复规则与历史兼容

重复规则必须同时满足：模块、门店、生效范围、主体、周期、规范约束键及统计对象相同。分类按实际 `productLineId + categoryId` 判断；菜品按 `productLineId + dishId` 判断；菜品集不以 `targetType` 相同直接判重，而是对同口径且生效范围重叠的成员身份交集执行菜品集重叠校验。不同分类、不同菜品或无成员交集的菜品集不得误判为重复。

发布本文能力之后，历史已启用的 v1/v2 规则继续运行，不因新校验自动失效。历史规则编辑后重新发布或从禁用状态重新启用时执行新校验；若冲突，允许继续保留禁用记录，但必须修正后才能启用。新建规则始终执行新校验。

### 7.2 有限整数可满足性模型

每个门店以发布候选菜单快照建立有限候选身份集合 `D`。身份键为 `storeId + productLineId + dishId`；分类成员来自同一快照的分类归属；菜品集成员是快照中仍有效的所选身份，跨产线身份分别进入 `D`。停售、删除或失效商品不进入新发布的候选集合。

门店配置提供权威整数 `supportedPartySizeMax`，取值范围为 `1..200`，随规则快照固化；原型未配置时规范化为 `99`。静态校验对 `N = 1..supportedPartySizeMax` 逐值枚举，并仅检查适用人数区间覆盖的值。超出 200 的门店配置不得发布；运行时 `N` 超过快照值时返回 `PARTY_SIZE_ABOVE_SUPPORTED_MAX`，不得套用开放区间继续执行。

对每个候选身份 `d` 建立非负整数变量 `x_d`：总量为 `Σx_d`，单品/相同菜品为 `x_d`，分类和菜品集为其成员变量之和。所有命中上下限共同组成有限整数约束，必须得到确定的有解/无解结果；实现可使用整数规划、最大流或等价有界算法，不得用简单上限求和替代。没有对象上限的身份在存在总量最大值时按该最大值截断；不存在总量最大值时，只需证明可达到有效最低值。

进行中订单继续使用锁定菜单/规则快照统计历史身份。动态售罄或停售不会移除已累计数量。运行时令 `C_d` 为当前轮菜单身份 `d` 已有的有效数量（包含已经加入但后来停售的数量），令 `a_d` 为当前仍允许追加的非负整数数量；提交前可达状态为 `x_d = C_d + a_d`。

运行时必须按以下顺序处理：

1. 先使用每条来源规则的原上限或有效授权的 `approvedFinalQuantity` 检查实际 `C_d`；
2. 如果 `C_d` 违反未授权上限，返回可减菜/可授权的具体失败项，允许用户减少未提交数量或对最大值申请授权，不得直接判为只能取消当前轮；
3. 只有当前数量已满足全部未授权上限、已授权项也不超过批准阈值后，才计算总量最低可达性；
4. 最低可达性使用 `Σ(C_d + a_d)`，并让 `a_d` 同时满足剩余全部上限；
5. 当前未提交且允许撤销的数量可由用户先减菜形成新的 `C_d`，但撤销量不作为证明最低数量可达的正向容量；
6. 仅当无解原因只剩“总量最低高于当前数量与可追加容量”，才进入最低数量不可达分支，此时数量授权不能绕过，只允许具备权限的员工取消/作废当前轮。

## 8. 数据模型

不增加规则类型维度。仓库 envelope 继续使用 `schemaVersion: 1`；使用组合数量能力的规则使用规则级 `schemaVersion: 3`。旧规则按仅启用“指定对象最多下单”读取，不因查看自动升级。

```ts
type LimitCell = { configured: boolean; value: number | null };
type TotalBoundCell = {
  minConfigured: boolean;
  min: number | null;
  maxConfigured: boolean;
  max: number | null;
};
type QuantityPolicyV3 = {
  roundTotal: { enabled: boolean };
  targetMax: { enabled: boolean };
  sameDishMax: { enabled: boolean };
};
type BuffetRuleV3 = {
  schemaVersion: 3;
  subject: "order" | "party_size";
  period: "order_lifetime" | "per_round" | "multi_round";
  targetType: "dish" | "category" | "dish_set";
  partyRanges: Range[];
  roundRanges: Range[];
  quantityPolicy: QuantityPolicyV3;
  storeConfigs: Record<string, {
    structureByLine: Record<string, unknown[]>;
    productLines: string[];
    targetIds: string[];
    limits: Record<string, LimitCell>;
    dishSetMembers: DishSetMember[];
    dishSetLimits: Record<string, LimitCell>;
    totalBounds: Record<string, TotalBoundCell>;
    sameDishLimits: Record<string, LimitCell>;
    supportedPartySizeMax: number;
  }>;
};
```

- 总量、相同菜品和菜品集共享上限使用键 `partyRangeIndex|roundRangeIndex`；
- 分类/菜品对象上限沿用四段键 `partyRangeIndex|roundRangeIndex|productLineId|targetId`；
- `order` 使用 `partyRangeIndex = 0`，本文每轮组合能力使用 `roundRangeIndex = 0`；
- 编译器可生成独立运行时约束项，但必须共享业务规则 ID、发布版本、启禁用状态和授权审计上下文。

所有配置数量必须是 `0..999999` 的整数；`N` 必须是大于 0 的整数，`supportedPartySizeMax` 必须是 `1..200` 的整数。`configured = true` 时值必须为非空整数，`configured = false` 时序列化值必须归一化为 `null`。未配置的最小值合并时视为负无穷，未配置的最大值视为正无穷，但启用区块的完整性仍按本规范单独校验。

### 8.1 切换与序列化规则

- 切换限购对象：二次确认后清空商品范围、对象数量矩阵和菜品集成员；总量与相同菜品单元格保留。
- 从“每轮”切换到其他周期：若总量或相同菜品已启用，必须二次确认；确认后关闭两个区块但保留其单元格作为不可执行草稿数据，发布载荷忽略它们；切回每轮可恢复。
- 切换限购主体或修改人数区间：二次确认后按新的场景矩阵重建数量单元格；能按相同区间键匹配的值保留，删除区间的孤儿单元格从发布载荷移除。
- 删除配置门店：二次确认后移除该门店全部商品范围和三个区块的数量单元格。
- `period !== per_round` 时，序列化校验强制 `roundTotal.enabled = false` 且 `sameDishMax.enabled = false`。

规则版本只升级不降级：v1/v2 规则仅编辑、保存原对象上限时保持原版本；首次保存任一新增区块为启用状态，或保存新增区块的非空单元格时升级为 v3。v3 即使后来关闭新增区块也保持 v3，避免不同保存路径产生版本摆动。只读加载绝不写回升级。

## 9. 兼容性与生命周期

- 现有按菜品、按分类、按菜品集规则行为不变。
- v1/v2 规则默认仅启用 `targetMax`；用户实际保存组合区块后才升级 v3。
- 复制时复制三个数量区块及每店配置，并重新校验商品和冲突。
- 禁用、启用、删除和发布作用于完整业务规则，不能单独操作内部约束区块。
- 授权后的超量数量继续进入实际累计。

## 10. 验收标准

1. 规则类型页三个维度的选项不新增、不改名。
2. 每轮规则可在限购数量步骤组合启用总量、指定对象和相同菜品区块。
3. 分类成员共享分类额度；菜品集成员跨产线共享一个额度。
4. 总量和相同菜品统计全部有效菜品，不受已选对象范围限制。
5. 按人数时三个区块均按配置值乘有效人数，不建立食客计数器。
6. 所有约束同时通过，并按最大下限、最小上限合并。
7. 总量最低只在提交或结束非空当前轮时检查。
8. 冲突或无可行解允许保存草稿，但阻止发布、启用和当前轮提交。
9. 批量下单原子校验，失败时不部分写入。
10. 数量授权不能绕过总量最低及非数量限制。
