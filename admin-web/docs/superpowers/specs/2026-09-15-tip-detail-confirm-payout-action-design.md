# 小费分配明细确认已发放入口设计

## 目标

在“小费分配明细”中补充与“日期分配汇总”一致的发放确认入口。当天已经完成分配且尚未发放时，用户可直接在明细页确认员工小费已经发放；确认后立即更新发放状态并将当天分配结果切换为不可修改的只读快照。

## 已确认方案

采用方案 A：复用日期分配汇总已有的发放确认弹框语义和 `TipOutDateState` 发放领域能力，不建立第二套发放状态或独立存储。

明细页只新增入口、弹框承载和页面状态刷新；发放快照校验、幂等请求、审计记录与锁定仍由现有领域逻辑负责。

## 按钮位置与可见性

在明细页底部固定操作栏中，将“确认已发放”放在“重新确认分配”左侧。两个按钮处于同一操作分组：

1. “确认已发放”为普通次级按钮。
2. “重新确认分配”为现有主按钮。
3. 按钮间距沿用当前操作栏组件规范。

| 营业状态 | 分配状态 | 发放状态 | 确认已发放 | 确认/重新确认分配 |
| --- | --- | --- | --- | --- |
| 未营业 | 无需分配 | 无需发放 | 不展示 | 现有确认分配控件行为保持不变，不在本次改动范围 |
| 正常营业 | 未分配 | 待发放 | 不展示 | 展示“确认分配” |
| 正常营业 | 已分配 | 待发放 | 展示 | 展示“重新确认分配” |
| 正常营业 | 已分配 | 已发放 | 不展示 | 不展示；页面进入只读锁定态 |
| 正常营业 | 已分配 | 待发放且 `locked=true` | 不展示 | 不展示；页面进入保护性只读状态 |
| 任意 | 分配/发放数据异常 | 异常锁定 | 不展示 | 不展示；按现有保护性只读逻辑处理 |

按钮可见性必须由当前门店和日期对应的领域状态决定，不只依赖页面文案或已分配日期索引。仅当 `allocationStatus=allocated`、`payoutStatus=pending` 且 `locked=false` 时展示。`locked` 直接读取 `TipOutDateState.inspect(...)` 的领域结果，视图不得自行推导第二套锁定状态。

## 确认弹框

点击“确认已发放”后复用日期汇总现有确认弹框的信息结构与警告语义，展示：

- 门店；
- 营业日期；
- 已分配金额；
- 本次分配涉及的去重员工人数；
- 警告：“确认该日期的小费已全部发放？确认后分配结果将锁定，无法修改或取消。”

弹框底部提供“取消”和“确认已发放”。打开后焦点进入确认按钮；未提交时支持遮罩点击、关闭按钮和 Escape 关闭。普通取消或关闭后焦点返回明细页“确认已发放”按钮。

提交开始后，确认、取消、关闭按钮、遮罩关闭和 Escape 均不可再次触发，直到本次请求结算，避免弹框消失后异步结果再次改变页面。确认按钮显示提交中状态。

若打开弹框时无法取得有效确认快照，弹框不打开，并展示现有领域错误，例如“请先完成当天小费分配”或“发放快照不可用”。

## 发放数据流

1. 用户在已分配、待发放的明细页点击“确认已发放”。
2. 页面通过 `TipOutDateState.ensureSnapshot(store, date)` 取得或补齐不可变快照元数据。
3. 页面保存本次所见的 `snapshotId`、`snapshotVersion`、`snapshotHash`，并生成唯一 `requestId`。
4. 用户在弹框中确认后，调用现有 `TipOutDateState.confirmPayout(...)`。
5. 领域层在互斥锁内重新读取快照并校验 ID、版本和摘要；一致且尚未发放时才写入发放记录。
6. 成功后关闭弹框并重新渲染明细页面。
7. 明细页进入“已发放 · 分配结果已锁定”只读状态；日期分配汇总通过同一发放状态存储和通知机制同步显示“已发放”。

本次不得直接操作发放存储键，也不得复制一套弱化版校验。日期汇总和明细页必须调用同一公共领域接口。

### requestId 生命周期与提交对账

- 每次成功打开确认弹框代表一次确认意图，只生成一个 `requestId`。
- 该弹框内首次提交、响应异常后的状态核对以及允许重试时，始终复用同一个 `requestId`。
- 只有关闭或作废当前弹框、重新读取最新状态与快照并再次打开后，才生成新的 `requestId`。
- 任意提交异常都不能直接假定“未写入”。页面必须先重新读取 `TipOutDateState.inspect(store, date)`：
  - 已发放：视为首次请求或并发请求已经成功，关闭弹框并进入只读态，不覆盖原确认人和确认时间；
  - 仍待发放且快照 ID、版本、摘要均未变化：保留弹框并恢复操作，允许使用原 `requestId` 重试；
  - 仍待发放但快照已变化：关闭并作废弹框，提示“分配结果已更新，请刷新后重新确认”，要求重新打开以捕获新快照；
  - 异常锁定：关闭弹框并进入保护性只读状态。

## 成功后的页面状态

确认成功后：

- 显示确认发放时的冻结分配快照；
- 显示确认时间和确认人；
- 隐藏“更新小费数据”、规则名称筛选、“确认已发放”和“重新确认分配”；
- 禁止修改员工、角色、工时、比例、金额及增删行；
- 仍允许返回汇总以及现有只读查看能力；
- 日期汇总中的发放状态同步为“已发放”。

领域守卫 `assertDateWritable` 继续作为最终安全边界。即使通过程序直接调用编辑或重新分配处理函数，已发放日期也必须拒绝写入。

## 并发、重复操作与错误处理

| 场景 | 处理 | 用户反馈 |
| --- | --- | --- |
| 弹框打开后分配快照被重新确认 | 拒绝发放，不写入记录 | “分配结果已更新，请刷新后重新确认” |
| 其他标签页已经确认发放 | 保持已发放记录，不覆盖确认人和时间 | “该日期小费已确认发放”，随后刷新为只读状态 |
| 用户双击确认按钮 | 提交期间禁用按钮；相同 `requestId` 幂等 | 只生成一条发放记录 |
| 发放提交异常 | 先调用 `inspect` 对账，再按已发放、快照未变、快照已变、异常锁定四种结果处理 | 仅在快照未变且仍待发放时展示领域错误并允许重试 |
| 快照缺失、损坏或摘要不一致 | fail closed，不允许发放或重新分配 | 展示“发放快照不可用”等保护性错误 |
| 页面收到同日期状态通知 | 重新读取当前状态并渲染 | 自动切换按钮或只读状态 |

跨标签通知只处理与当前门店和日期一致的消息：

- 通知显示已经发放时，立即关闭并作废当前弹框，进入只读态；焦点移到可聚焦的“已发放 · 分配结果已锁定”提示区，并通过状态区域播报变化。
- 通知显示快照变化但仍待发放时，立即关闭并作废旧弹框，提示“分配结果已更新，请刷新后重新确认”；焦点返回仍存在的“确认已发放”按钮。
- 其他门店或日期的通知不得影响当前弹框。
- 普通取消才使用“焦点返回触发按钮”规则；确认成功或跨标签已发放后，触发按钮已经消失，焦点必须落到锁定提示区。

跨标签状态变更的优先级高于本地正在进行的提交。若提交期间收到同门店、同日期的快照变更或已发放通知，页面必须立即作废当前确认意图并按最新领域状态关闭弹框、切换只读态或提示重新确认。该请求随后到达的成功或失败回调均视为迟到回调，不得恢复旧弹框、重新启用旧控件、覆盖页面状态或覆盖确认人和确认时间；回调只能再次调用 `inspect`，并保持与最新领域状态一致的渲染结果。

## 代码边界

预计调整范围：

- `src/team/tips/templates/details.html`：新增明细页“确认已发放”按钮和复用语义的确认弹框承载结构。
- `src/team/tips/programs/details.js.txt`：按钮状态同步、弹框打开/关闭、提交、成功刷新、跨标签状态刷新。
- `src/team/tips/tips-page.css`：仅在现有操作栏样式不足时补充按钮分组或弹框样式。
- `scripts/verify-team-tips-native-views.mjs` 或新增聚焦验证脚本：锁定结构和行为契约。

不修改：

- 发放记录结构；
- `TipOutDateState.confirmPayout` 的业务语义；
- 日期汇总现有确认发放行为；
- 已发放不可撤销规则。

## 验收标准

1. 正常营业、已分配、待发放日期的明细页，在“重新确认分配”左侧展示“确认已发放”。
2. 未分配、未营业、已发放或异常锁定状态均不展示该按钮。
3. 点击按钮展示与日期汇总一致的信息：门店、日期、已分配金额、员工人数和不可修改警告。
4. 取消或关闭弹框不改变任何状态，焦点返回触发按钮。
5. 确认成功后只产生一条发放记录，页面立即切换为已发放只读状态。
6. 返回日期分配汇总后，同一天发放状态为“已发放”。
7. 已发放后无法更新小费、修改员工/工时/比例、重新确认或取消分配。
8. 快照并发变化、重复确认和存储失败均不产生半成功状态。
9. 刷新页面后已发放状态、确认人、确认时间和冻结结果保持不变。
10. 现有日期汇总确认发放、分配、重新分配及未营业拦截回归通过。
11. A 标签打开弹框、B 标签重新确认分配后，A 的旧弹框自动失效，旧快照不可发放且不产生发放记录。
12. A 标签打开弹框、B 标签确认发放后，A 自动进入只读态，确认人和时间与 B 一致且不被覆盖。
13. 提交期间所有关闭入口不可用；失败后控件恢复，并以重新读取到的领域状态决定重试、作废或只读。
14. 模拟“领域写入成功但页面收到响应异常”后重试，最终仍只有一条发放记录，确认人和时间不被覆盖。
15. 已发放后直接调用编辑、增删行、更新数据和重新分配处理函数，均被 `assertDateWritable` 拒绝。
16. 普通取消后焦点返回触发按钮；成功或跨标签切换只读后，焦点落在仍存在的锁定提示区。
17. A 已进入提交中时，B 重新确认分配导致快照变化；A 的请求随后返回时，页面不回退、不重开旧弹框，也不允许旧快照完成发放。
18. A 已进入提交中时，B 已确认发放；A 的请求随后返回时，A 保持已发放只读态，且确认人和确认时间始终采用 B 已写入的领域记录。
