# 员工分配汇总结果优先设计

## 背景与目标

员工分配汇总当前在顶部展示“分配前、扣除、分配获得、实际获得”四项金额。这套结构完整呈现计算过程，但不能最快回答店长的首要问题：在所选门店和日期范围内，每位员工最终获得多少小费，以及是否还有员工需要处理。

本次调整采用“结果优先”方案。页面首先突出员工最终获得金额和处理进度；扣除与获得仍作为计算依据保留，但不再占用顶部核心指标。业务计算、已确认分配结果和员工明细数据不因本次展示调整而改变。

## 页面信息架构

门店与日期范围继续决定整个页面的数据范围。员工搜索、角色筛选和状态筛选作用于员工列表，顶部指标同步按当前筛选后的员工集合重新统计。

页面从上到下分为：

1. 门店与日期范围。
2. 员工搜索、角色筛选和状态筛选。
3. 结果优先的四项概览指标。
4. 每位员工一行的分配汇总列表。
5. 与当前范围一致的导出操作。

## 顶部概览指标

顶部四项指标调整为：

| 指标 | 定义 |
| --- | --- |
| 员工人数 | 当前门店、日期范围和列表筛选条件下，参与相关小费规则的唯一员工数 |
| 最终获得合计 | 当前筛选员工在已确认分配日期中的“最终获得”合计 |
| 已完成 | 范围内所有相关日期均已确认分配、且不存在数据异常的员工数 |
| 待处理 | 存在未确认分配日期的员工数；异常员工不重复计入此项 |

“最终获得合计”下方需要提供弱提示“仅统计已确认且校验通过的分配结果”。当范围内没有任何可计入的已确认结果时显示 `—`，不能显示 `$0.00`；存在已确认且校验通过的零金额结果时显示 `$0.00`。

异常员工通过列表状态明确呈现。“待处理”指标在异常人数大于零时固定展示次级文案“另有异常 N 人”；异常人数为零时不展示该文案，不新增第五张卡片。任一员工只归入一种状态，因此始终满足“员工人数 = 已完成 + 待处理 + 异常”。

## 员工列表

员工跨多个日期、角色或小费池出现时，仍以员工唯一 ID 聚合为一行。姓名不是聚合主键。角色使用“角色与员工”统一数据源，并以去重后的角色标签展示。

列表字段为：

| 字段 | 展示与口径 |
| --- | --- |
| 员工 | 头像或姓名缩写、员工姓名 |
| 角色 | 当前范围内参与分配的去重角色标签 |
| 班次 | 当前范围内参与计算的班次数合计 |
| 工时 | 打卡工时与有效手动补录工时的合计 |
| 原有小费 | 员工在已确认分配日期中的分配前金额合计 |
| 净调整 | `分配获得 - 扣除`；正数绿色、负数红色、零值使用默认文字色 |
| 最终获得 | `原有小费 + 净调整`，使用加粗等视觉方式作为本行主结果 |
| 状态 | 已完成、待处理或异常 |
| 操作 | 进入员工逐日分配明细 |

列表不直接展示独立的“扣除”和“分配获得”列。两项完整构成继续在员工明细中展示，避免总览横向字段过多，同时确保核算过程可追溯。

如果员工只有部分日期完成分配，原有小费、净调整和最终获得仅累计已确认且校验通过的日期，状态显示“待处理”，最终获得旁显示弱提示“已确认部分”，避免用户误认该值为完整周期结果。

如果员工任一已确认分配明细发生金额守恒失败、金额缺失或金额不可解析，则该员工的原有小费、净调整和最终获得统一显示 `—`，状态显示“异常”，整名员工从顶部最终获得合计中排除。页面不拼接“可信部分”金额，以免把不完整结果误作可结算金额。导出中对应金额单元格留空，并通过状态与异常原因列说明具体问题。

未分配日期的数据不进入上述金额合计。已确认日期中的真实零金额必须显示 `$0.00`，没有可用结果时显示 `—`。

## 金额口径与守恒

- 原有小费：员工在周期内各已确认日期、各有效小费池的分配前金额合计。
- 扣除：员工作为扣除方实际扣出的金额合计。数据层保持正数语义，界面以红色表达流出。
- 分配获得：员工作为接收方实际获得的金额合计。界面以绿色表达流入。
- 净调整：`分配获得 - 扣除`。
- 最终获得：`原有小费 - 扣除 + 分配获得`，等价于 `原有小费 + 净调整`。
- 顶部最终获得合计必须等于当前筛选列表中所有员工最终获得的合计。
- 同一员工参与多个角色或小费池时按员工唯一 ID 汇总各明细结果，不能重复计人或重复计费。
- 手动补录工时参与按工时规则的计算；汇总金额只读取已确认分配结果，不在汇总页重新计算历史分配。
- 金额聚合沿用现有已确认分配结果的货币最小单位和舍入规则。每条已持久化明细先按既有规则得到整数分，再按员工和页面范围汇总整数分，最后格式化为两位小数；顶部合计直接汇总相同的员工整数分。验收比较使用整数分，不能对格式化后的字符串或浮点数再次求和。

## 状态规则

状态只保留三个互斥结果：

- 已完成：当前范围内所有与员工相关的日期均已确认分配，且不存在异常。
- 待处理：至少存在一个相关日期尚未确认分配，且不存在异常。
- 异常：存在工时缺失、员工或角色失效、规则失效、金额校验失败等会阻止确认分配的问题。

优先级为“异常 > 待处理 > 已完成”。异常标签旁展示异常原因数量；进入明细后定位到第一个异常日期。待处理状态进入明细后定位到第一个未确认日期。

员工的“相关日期”定义为所选日期范围内满足以下任一条件的自然日：该日的持久化分配结果或草稿中存在该员工唯一 ID 的扣除方/接收方明细；或该日尚未确认分配，但当前有效规则根据所选门店、员工有效期和统一角色/员工数据能够将该员工解析为扣除方或接收方。没有任何相关日期的员工不进入列表和员工人数。相关日期集合必须由共享聚合逻辑一次生成，顶部计数、列表状态、明细定位和导出均复用同一集合。

异常提示不反向修改既有分配结果。本汇总页只读取并展示现有规则校验与确认阻断结果，不新增或改变确认分配的阻断逻辑。角色、员工或规则失效时，如果既有分配流程已产生阻断状态，则汇总页将员工标记为异常；历史已确认结果仍可查看和导出。

## 排序、筛选与导航

- 默认按最终获得从高到低排列；没有已确认金额的员工排在有金额员工之后。
- 员工、工时、最终获得列支持点击表头切换升序与倒序，并清晰展示当前方向。
- 员工搜索按姓名匹配；角色筛选来源于统一角色数据；状态筛选包含全部状态、已完成、待处理和异常。
- 筛选结果改变时，同步刷新列表与顶部四项指标。
- 点击员工整行或操作入口进入员工分配明细，并继承门店、日期范围和员工唯一 ID。
- 从明细返回后，恢复原筛选、排序和滚动位置。

## 导出

员工分配汇总的“导出结果”导出当前门店、日期范围和筛选条件下的全部员工结果，不受当前滚动位置或分页限制。导出顺序与页面当前排序一致。

导出字段至少包含员工、角色、班次、工时、原有小费、扣除、分配获得、净调整、最终获得、状态和异常原因。页面可以合并展示净调整，导出仍保留扣除和分配获得两个独立字段，满足核算需求。

## 空状态与错误处理

- 当前范围没有相关员工时，展示明确空状态，不显示全为零的概览误导用户。
- 页面数据加载失败时保留筛选条件，概览和列表显示统一错误状态并提供重试入口。
- 某个员工的部分明细无法解析时，不静默丢弃；将该员工标记为异常，页面金额显示 `—`，导出金额留空，并在明细和导出中给出原因。
- 金额守恒校验失败时，整名员工的金额不并入最终获得合计。

## 范围边界

本次不修改小费规则、分配算法、确认分配、取消分配、手动工时录入或员工与角色主数据的业务逻辑。只调整员工分配汇总的信息结构、聚合呈现、筛选排序、状态表达、导航恢复与导出口径。

## 验收标准

1. 顶部展示员工人数、最终获得合计、已完成和待处理，不再展示过程型的分配前、扣除和分配获得概览卡。
2. 列表每个员工唯一一行，跨角色和小费池不会产生重复员工或重复金额。
3. 对校验通过的员工，最终获得满足 `原有小费 - 扣除 + 分配获得`；顶部合计等于筛选后所有非异常员工的底层整数分之和，异常行金额显示 `—` 并排除。
4. 未分配结果使用 `—`，已确认零金额使用 `$0.00`。
5. 部分完成员工显示已确认部分金额和待处理状态，不把部分金额误作完整周期结果。
6. 异常优先于待处理，并能从状态入口定位首个问题日期；员工人数始终等于已完成、待处理与异常人数之和。
7. 搜索、角色筛选、状态筛选和排序都同步更新概览及列表。
8. 进入员工明细继承上下文，返回后恢复筛选、排序与滚动位置。
9. 导出范围、数据口径和排序与当前页面状态一致，并包含独立的扣除与分配获得字段；异常员工金额留空且包含异常原因。
10. 既有分配规则、计算结果、确认分配、取消分配和手动工时逻辑保持不变。
