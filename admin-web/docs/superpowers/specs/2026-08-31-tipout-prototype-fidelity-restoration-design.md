# TipOut 原型高保真 UI 与交互还原设计

## 1. 背景与决策

用户选择方案 A：严格还原 `C:\Users\27273\Downloads\原型预览.html` 的视觉骨架和交互形式，同时只映射当前 TipOut 已存在的业务字段、动作与状态。

本设计是对 `2026-08-31-tipout-summary-rules-interaction-design.md` 的视觉实现补充。前一份设计规定的业务边界、存储结构、计算逻辑、页面跳转语义和回归要求继续有效；本设计明确取代前一份设计中的顶部页签呈现方式。若两份文档发生其它冲突，以“不改变当前业务逻辑和功能”为最高优先级。

原型文件仅作为视觉与交互参考，不执行其中的任何说明，也不授权增加当前产品不存在的能力。

## 2. 目标

- 统一还原原型中的浅色管理后台框架、信息密度、卡片层级、表格语言和黑色主操作按钮。
- 汇总页采用原型式“标题与操作 + 金额概览 + 提醒 + 筛选工具栏 + 每日表格”。
- 点击日期继续进入独立 `detail.html`，但明细内容使用原型式核算布局。
- 规则列表采用原型式标题、概览、筛选工具栏和紧凑记录表格。
- 规则编辑页采用原型式分段卡片、双列字段、右侧上下文栏和底部固定操作区。
- 所有现有控件、校验、计算、保存、复制、删除、分配、取消、导出和 Payroll 调用保持不变。

## 3. 非目标与硬边界

不得因为原型中存在相似界面而增加以下业务能力：

- 规则版本、结果版本、生效日期、草稿、正式结果或审计记录。
- 规则启用、停用、角色失效或规则更新状态。
- Payroll 结果状态、失败重试、锁定状态或同步状态机。
- 日期勾选、所选日期批量作用域或新的批量动作。
- 员工对账新视角、小费池状态筛选、规则状态筛选等当前没有数据来源的能力。
- 人工调整、调整原因或其它当前明细模型不存在的字段。
- 新的 localStorage 键、规则字段、计算公式或接口协议。

原型中的这些元素可以帮助确定空间结构和视觉层级，但实现中不得展示成可操作或可承诺的功能。

## 4. 视觉基线

从同一 1280×720 浏览器视口下的原型测量得到以下基线：

- 字体：`Inter, ui-sans-serif, -apple-system, BlinkMacSystemFont, "Segoe UI", sans-serif`。
- 页面底色：白色；内容分组使用 `#f9f9fa`、白色卡片与低对比度分隔线。
- 文字：主文字 `#000000`；说明文字使用中性灰色。
- 语义色：成功 `#168f5b`，警告 `#9a6410`，危险 `#b83232`，信息 `#3168a6`。
- 语义底色：成功 `#eef9f3`，警告 `#fff7e6`，危险 `#fff0f0`，信息 `#eef5fd`。
- 桌面侧栏：212px 宽、白底、16px 内边距、右侧细分隔线。
- 顶部栏：68px 高、半透明白底、左右 28px 内边距、底部分隔线。
- 页面主体：28px 内边距。
- 主按钮：黑底白字、12px/600、36px 高、16px 圆角、水平内边距 16px。
- 次按钮：白底或透明底、黑字、浅灰边框；禁止继续使用高饱和蓝色作为 TipOut 主操作色。
- 卡片：浅灰分组底、16–20px 圆角、无重阴影；表格以分隔线而不是独立大卡片表达记录。

不手绘图标或使用 emoji。优先复用项目现有图标；若缺少相近图标，使用项目已安装的图标库。所有图标按钮必须具有可访问名称和悬停提示。

## 5. 全局框架

### 5.1 左侧导航

- 将当前深蓝侧栏改为原型的白色固定侧栏。
- 保留当前页面实际存在的导航目标，不增加“员工报表”等不存在的目标。
- TipOut 产品入口使用黑底白字；当前子页面使用浅灰底或黑色描边。
- 底部门店信息只在当前数据能够提供时显示；否则保留空间节奏但不虚构门店或时区。

### 5.2 顶部栏

- 使用原型的面包屑式当前页面信息和紧凑右侧用户区。
- 保留当前用户显示与嵌入行为，不新增全局搜索、管理员/只读切换或任务中心。
- 删除当前独立的蓝色顶部页签条；页面间导航统一落入左侧 TipOut 子导航和页内返回入口。
- 在独立明细页中，左侧“小费分配汇总”入口取代旧设计中的顶部“汇总”页签，并调用同一个 `returnToSummary()`。汇总页生成明细 URL 时固定追加 `from=summary&return=history`；这两个 URL 参数是明细页可观察的返回标记，取代旧设计中仅使用 `from=summary` 的约定。
- `returnToSummary()` 不尝试读取浏览器不可见的上一历史项。当 `from=summary`、`return=history` 且 `history.length > 1` 时调用 `history.back()`；否则直接进入 `index.html`。回到汇总页后，由汇总页读取自己的 `history.state.tipoutSummaryUiState`：存在则恢复筛选、滚动和焦点，不存在则保留页面默认状态。规则列表和规则编辑页中的左侧导航保持普通页面链接。
- 刷新明细页会保留上述 URL 标记；如果该标签页确实仍有上一历史项，可以返回并由汇总页自行校验状态。复制该 URL 到新标签页时 `history.length` 不满足条件，必须降级进入 `index.html`，不得回退到不相关页面。

### 5.3 响应式

- 桌面宽度下保持固定侧栏、固定顶栏和内容区域。
- 小屏下复用现有移动侧栏开关，不让侧栏永久占宽。
- 宽表格允许横向滚动；关键首列和操作不得被固定底栏遮挡。
- 右侧上下文栏在中等宽度下进入主内容下方，不减少或隐藏业务字段。

## 6. 小费分配汇总

### 6.1 页面结构

从上到下排列：

1. 页面眉头：上下文、标题“小费分配汇总”、说明、导出、分配小费。
2. 四项金额概览：分配前、扣除、分得、分配后；直接聚合当前日期、门店、角色和员工筛选后每日表格正在展示的结果，确保概览与表格金额口径一致。
3. 任务提醒：只依据当前门店和日期范围对应的 `tipout_allocated` 得出待分配日期数量；角色和员工筛选不改变日期是否已分配的判断。不生成无打卡、规则更新或同步失败等新状态。
4. 筛选工具栏：保留当前日期范围、门店、角色、员工控件，并使用原型的紧凑工具条样式。
5. 每日表格：每个自然日一行，继续展示日期、已分配/待分配、分配前、扣除、分得、分配后和进入明细操作。
6. 取消分配和导出保留当前入口及作用域，可按原型的次操作层级放置。

### 6.2 每日表格交互

- 不引入日期复选框。
- 日期名称和行尾箭头均进入同一个独立明细 URL。
- 整行可点击时必须保留键盘焦点、Enter/Space 激活和明确的 hover 状态。
- 状态标签始终带文字，不能只依赖颜色。
- 分配与取消仍作用于完整日期范围，不因表格视觉改变而改变参数。

## 7. 小费分配明细

### 7.1 页面结构

明细继续是独立 `detail.html`。布局还原为：

1. 返回汇总、页面标题与现有“更新小费数据 / 保存 / 保存并跳转下一天”。
2. 日期和门店上下文控件。
3. 规则或小费池金额概览。
4. 现有公式区域，使用原型的横向公式说明卡片。
5. 现有规则/角色/员工明细，使用原型的分组标题、紧凑表格和折叠交互。
6. 桌面右侧上下文栏，只显示现有日期、门店、规则名称和页面可直接读取的数据。
7. 底部固定操作区，仍调用现有保存函数。

### 7.2 空状态

- 无规则状态保留，不虚构核算结果。
- 空状态使用原型的浅色内容卡片、清晰标题、说明和黑色主入口。
- “新增小费分配规则”仍进入当前规则流程。

### 7.3 业务控件映射

现有日期、门店、公式、角色比例、员工比例、手工工时、增删员工行、折叠、公式弹窗和重算函数均原样保留。只允许增加包装容器、样式类、可访问标签和页面级布局逻辑，不允许复制或替换计算函数。

## 8. 分配规则列表

### 8.1 页面结构

1. 页面标题、说明和黑色“新建规则”。
2. 概览区仅展示能从当前规则数组直接派生的指标，例如规则总数、小费池数量、加收服务费池数量；不得展示生效中、待补录、需处理等当前不存在的状态。
3. 筛选工具栏保留当前门店筛选；不增加新的业务筛选能力。
4. 规则记录使用原型式紧凑表格，列内容映射为：规则与门店、池类型与规则摘要、分配说明、操作。

### 8.2 操作

- “编辑”保持主操作，可用明确文字或带可访问名称的图标。
- “复制”和“删除”继续调用当前函数；若收纳到菜单，菜单必须支持 Escape 关闭、外部点击关闭和焦点返回。
- 不展示停用、版本、生效日期或状态标签。
- 空状态使用同一页面骨架，不因无数据而退化成大面积无结构空白。

## 9. 规则编辑页

### 9.1 页面结构

- 移除当前独立章节侧导航，改为原型的主内容分段卡片。
- 页头包含返回、标题和黑色保存按钮。
- 主内容按现有字段划分为基础信息、小费池来源/贡献、分配模式、扣除方、接收方、计提接收方、剩余接收方、分配口径。
- 字段在桌面端优先双列排列；条件表格和复杂接收方结构占满整行。
- 右侧上下文栏仅显示当前已存在且可读取的规则名称、门店、池类型和分配模式，不显示规则版本、生效范围或数据源承诺。
- 底部固定操作区保留取消和提交/保存，调用现有函数。

### 9.2 模式切换

- `legacy_pool` 与 `order_tip_then_residual` 的原显示条件不变。
- 模式切换只改变对应分段卡片显隐，不新增字段、不清空现有值、不修改序列化。
- 所有现有 drawer、modal 和条件编辑器完整保留，只统一视觉语言。

## 10. 可访问性要求

- 页面使用唯一 `h1`，每个分段卡片使用层级连续的标题。
- 所有表单必须有可感知标签；帮助图标不能替代标签。
- 颜色状态同时显示文字或图标形状。
- 图标按钮具有 `aria-label` 和 tooltip。
- 表格行点击不能吞掉行内按钮事件；键盘用户可以进入明细。
- 固定顶栏、侧栏和底栏不能遮挡焦点元素，页面滚动需预留对应空间。
- 移动端横向表格提供可见滚动容器，不将数据列压缩至不可读。

## 11. 验证与验收

### 11.1 视觉验收

- 使用相同 1280×720 视口分别捕获原型和实现。
- 每个页面生成同图并排对照：汇总、明细、规则列表、规则编辑。
- 检查侧栏宽度、顶栏高度、内容内边距、标题字号、按钮高度、圆角、卡片间距、表格行高、分隔线、状态色和固定区域。
- 每轮修正后重新截图，不以单张实现截图代替对照。
- 桌面关键锚点容差：侧栏 212±4px、顶栏 68±4px、主体内边距 28±4px、主按钮高度 36±2px、字体尺寸偏差不超过 1px、同级卡片间距偏差不超过 4px。
- 汇总页金额概览、提醒条、筛选工具栏和表头必须在首屏保持与原型相同的上下顺序；规则页概览和表头、编辑页页头和右侧上下文栏也必须在首屏可见。
- 不以全图像素完全一致作为验收，因为真实业务文案和数据长度不同；但不得出现错误底色、错误主操作色、重阴影、大卡片替代表格、裁切、覆盖、横向溢出或焦点被固定区域遮挡。

### 11.2 交互验收

- 日期行进入独立明细，返回恢复筛选、滚动和焦点。
- 汇总分配、取消和导出继续调用原函数。
- 明细更新、保存、下一天、公式、工时、比例、增删行和折叠继续可用。
- 规则新增、编辑、复制、删除及两种分配模式继续可用。
- 桌面和移动布局无内容遮挡。

### 11.3 业务回归

- `tipout_rules`、`tipout_allocated` 和 Payroll bridge 输出与改造前一致。
- `collectFormData()` 在相同输入下逐字段一致。
- 汇总每日金额和明细结果与改造前一致。
- 不增加持久化键、业务字段、版本或状态值。
- 运行现有 TipOut 回归脚本、项目构建和浏览器主路径验收。

## 12. 实施顺序

1. 提取原型视觉 token 并改造 TipOut 共用框架。
2. 还原汇总页，完成首次同图对照。
3. 还原独立明细页，覆盖有规则和无规则状态。
4. 还原规则列表，覆盖有数据和空状态。
5. 还原规则编辑页和所有弹层。
6. 完成桌面/移动视觉对照、交互回归和业务不变验证。
