# 前厅设置 POS 通知分组合并设计

## 背景

前厅管理中心的“设置”当前将 POS 员工端通知拆成两个相邻分组：

- “POS 通知总控”：员工端通知类型（`seq 331`）、新单语音播报（`seq 332`）。
- “订单消息提醒”：新订单提醒（`seq 638`）、追单提醒（`seq 639`）、指定菜品提醒（`seq 637`）。

这些功能都属于店内员工接收订单及相关消息的配置。分为两个三级设置分组会增加理解和查找成本，因此统一到“订单消息提醒”。

## 目标

- 删除“POS 通知总控”设置分组。
- 将其中两个功能迁入“订单消息提醒”。
- 保持现有功能编号、控件行为、适用产线和已保存配置不变。
- 兼容指向旧分组的站内链接及已保存链接。
- 同步所有生成源、运行时配置和项目文档，避免导航、平台预设树与实际页面不一致。

## 非目标

- 不合并五个功能各自的数据结构或开关。
- 不修改员工端通知类型的可选类别。
- 不修改新单语音播报及三种订单提醒的适用产线。
- 不改变通知触发、消息发送或语音播报的业务逻辑。
- 不迁移或重写现有本地存储数据。
- 不调整前厅设置中的其他分组。

## 用户界面

前厅管理中心 → 设置 → 员工端设置中，原“POS 通知总控”和“订单消息提醒”两个相邻分组只保留“订单消息提醒”；员工端的其他设置分组不受影响。

“订单消息提醒”按以下顺序展示五个功能：

1. 员工端通知类型（`seq 331`）
2. 新单语音播报（`seq 332`）
3. 新订单提醒（`seq 638`）
4. 追单提醒（`seq 639`）
5. 指定菜品提醒（`seq 637`）

各功能继续使用现有控件：

- `331` 保留员工端通知类型多选界面。
- `332` 保留按产线选择的新单语音播报界面。
- `638`、`639`、`637` 保留主开关和适用产线多选界面。

合并只改变导航归属和排列，不在组内增加新的二级标题或重复说明。

## 分组与导航契约

- 合并后的规范分组键继续使用 `foh-pos-order-alerts`。
- `foh-pos-order-alerts` 的功能顺序固定为 `[331, 332, 638, 639, 637]`。
- `foh-pos-notification-control` 不再作为可见分组出现在：
  - 前厅设置侧栏与分段导航；
  - 模块设置目录的 `groupOrder`；
  - 平台预设四级导航树；
  - 分组标题及生成文档。
- 原始目录分组 `notification-basics` 映射到 `foh-pos-order-alerts`，与现有 `staff-order-alerts`、`order-pickup-messages` 一起归入同一规范分组。
- 访问 `#/operations/queue-call/settings?group=foh-pos-notification-control` 时，兼容解析为 `foh-pos-order-alerts`，页面选中“订单消息提醒”，而不是落到空页面或默认分组。
- 项目内所有指向“POS 通知总控”的说明和链接改为指向“订单消息提醒”。

## 数据兼容

五个功能继续使用原有 `seq` 作为身份标识，不更改设置控件的数据读写实现或存储键。

- `331`、`332` 的既有设置值在合并后直接由原控件读取。
- `637`、`638`、`639` 的主开关与适用产线数据保持原样。
- 不执行一次性数据迁移，不复制存储值，也不引入新的回退优先级。
- 旧分组键只作为导航兼容别名，不成为新的数据命名空间。

因此，用户升级后看到的开关、多选项及产线选择应与升级前一致，仅所在分组发生变化。

## 生成源与运行时同步

实现必须修改规范生成源，再重新生成或同步派生产物，不能只手改生成文件。涉及范围包括：

- 前厅分组及顺序定义；
- 原始分组到规范分组的映射；
- 产线范围种子与生成后的运行时范围表；
- 模块设置目录、侧栏分段和平台预设树；
- 分组说明入口及旧链接兼容；
- 前厅设置设计文档及导航说明中的分组名称。

删除旧分组相关的专用空说明函数或调用时，不影响合并后“订单消息提醒”的现有渲染入口；该入口的首项从 `seq 638` 调整为 `seq 331`（若仍需组首说明判定）。

## 异常与边界行为

- 当查询参数中的分组键恰好为旧规范键 `foh-pos-notification-control` 时，必须归一化到 `foh-pos-order-alerts`，不得渲染空设置页。其他未知或未来分组键继续沿用现有回退行为，不得一律跳转到“订单消息提醒”。
- 若目录数据中仍出现旧原始分组名，应通过规范映射归入 `foh-pos-order-alerts`，不得重新生成“POS 通知总控”。
- 搜索结果、平台预设和权限导航引用同一规范分组键，避免一个功能在不同入口显示在不同分组。
- 五个功能中任一功能因版本或产线范围被过滤时，其余功能保持上述相对顺序。

## 验收标准

1. 前厅管理中心 → 设置中不再显示“POS 通知总控”。
2. “订单消息提醒”显示且仅显示 `331`、`332`、`638`、`639`、`637`，顺序与设计一致。
3. 五个功能的标题、说明、控件形态、可选产线和交互行为与合并前一致。
4. 合并前保存的五项配置在合并后仍正确回填。
5. 修改任一功能后，仅写入该功能原有的存储键。
6. 访问旧 `group=foh-pos-notification-control` 链接会打开并选中“订单消息提醒”。
7. 页面内说明不再引导用户前往“POS 通知总控”。
8. 设置侧栏、搜索结果、权限导航、平台预设树和生成文档均只使用“订单消息提醒”。
9. 分组生成、产线范围、平台预设树及相关项目校验全部通过。
10. 生产构建通过，并在浏览器中验证桌面布局、旧链接兼容和配置回填。

## 测试方案

- 增加或调整分组映射校验，断言旧分组不存在且新分组顺序为 `[331, 332, 638, 639, 637]`。
- 调整平台预设树校验，断言五项功能均位于 `foh-pos-order-alerts`。
- 验证原始分组别名均归一化到新规范分组。
- 验证旧查询参数被归一化并选中新分组。
- 对五个功能分别预置现有存储值，确认页面回填不变；交互后确认仍写入原存储键。
- 运行相关生成/一致性校验、TypeScript 检查和生产构建。
- 浏览器验证旧分组消失、合并顺序、各控件展开/切换及刷新后的配置保持。

## 风险与回滚

主要风险是只更新部分生成层，导致侧栏、搜索、平台预设或运行时页面仍出现旧分组。通过从规范生成源修改并运行现有一致性校验控制风险。

若需要回滚，恢复原分组映射、分组顺序和链接目标即可。由于本设计不改存储键和数据结构，回滚不需要数据修复。
