# 前厅管理中心「自助餐规则」独立模块设计

> 状态：已确认  
> 日期：2026-08-28  
> 适用范围：前厅管理中心 / 自助餐规则

## 1. 背景

现有“菜单下单限制”支持按订单/按人数、每轮/多轮/与轮次无关、按分类/按菜品组合形成的 12 种数量与频次场景。自助餐业务需要更聚焦的规则模型：

- 按桌/订单限购只表达整个订单的固定最大数量，不配置人数和轮次；
- 需要按人数或轮次控制时使用按人数限购，整单共享额度为 `L × N`；
- 按人数规则支持按有效就餐人数配置人数区间；
- 保留按人数每单、每轮和分轮次三种额度周期。

为避免改变现有菜单下单限制规则、数据和门店行为，新增独立“自助餐规则”模块。新模块在页面样式和操作流程上参照菜单下单限制，但拥有独立路由、数据空间、规则类型和发布快照。

## 2. 目标与非目标

### 2.1 目标

- 在前厅管理中心“菜单下单限制”下方新增“自助餐规则”导航。
- 复用现有规则列表和固定 6 步编辑向导的视觉、布局和交互模式。
- 自助餐规则仅开放 8 种已确认的规则组合。
- 按桌/订单规则固定统计整个订单，不展示人数和轮次输入。
- 按人数规则使用 `L × 当前订单有效人数`，不追踪具体食客。
- 自助餐规则与菜单下单限制的数据、草稿、发布、列表偏好和恢复状态完全隔离。
- 保持现有菜单下单限制行为和数据不变。

### 2.2 非目标

- 不迁移、转换或清理现有菜单下单限制规则。
- 不修改菜单下单限制现有 12 场景模型。
- 不支持具体食客或座位级的独立额度。
- 不支持具体食客维度的独立额度；人数区间只用于按订单有效人数选择人均限额档位。
- 不支持固定“每桌每轮上限”或固定“每桌分轮次上限”。
- 不恢复旧的后置门店选择页面。

## 3. 导航与模块边界

前厅管理中心导航顺序：

```text
菜单下单限制
自助餐规则
```

确定路由契约：

```text
列表页：buffet-rule.html
规则编辑：buffet-rule-editor.html
发布确认：buffet-rule-publish-confirm.html
```

现有菜单下单限制继续使用：

```text
order-limit.html
order-limit-rule-editor.html
order-limit-publish-confirm.html
```

所有返回、编辑、复制、查看和发布跳转必须从当前模块配置读取，不得在共享引擎中写死 `order-limit*.html`。

主应用必须新增稳定导航节点 `foh-buffet-rules`，其 iframe 入口固定为 `dist/Configuration center/buffet-rule.html?embedded=1`。编辑页和发布页透传 `embedded=1`、`mode`、`draftId`、`ruleId` 等既有查询参数；全屏打开时只去除 `embedded`，不得改变资源路径或数据空间。

## 4. 共享引擎与独立配置

采用“共享引擎＋独立配置、路由和数据空间”方案。

共享能力包括：

- 规则列表结构和列设置；
- 新增、编辑、复制和只读查看；
- 固定 6 步向导；
- 商品选择与已选商品预览；
- 门店独立的商品范围和数量配置；
- 数量批量应用与批量删除；
- 超限授权；
- 生效范围；
- 草稿保存、恢复与原子发布；
- 通用确认框、错误态和提示反馈。

共享引擎通过模块配置运行：

```text
moduleId
pageTitle
routes
storageKeys
allowedSubjects
allowedPeriodsBySubject
quantityFormula
stepLabels
quantityColumnLabels
conflictPolicy
```

配置档：

```text
MENU_ORDER_LIMIT_PROFILE
BUFFET_RULE_PROFILE
```

`MENU_ORDER_LIMIT_PROFILE` 保持现状；`BUFFET_RULE_PROFILE` 只开放本设计定义的 8 种组合。

## 5. 数据隔离与发布存储

### 5.1 权威存储表

| 模块 | Storage | 完整键 | 值与读写方 |
| --- | --- | --- | --- |
| 菜单下单限制正式规则 | `localStorage` | `restaurantRules` | 既有规则数组；仅 `MENU_ORDER_LIMIT_PROFILE` 读写 |
| 菜单下单限制恢复副本 | `sessionStorage` | `restaurantRuleRecovery:{draftId}` | 既有编辑恢复数据；仅既有编辑器读写 |
| 自助餐规则数据仓 | `localStorage` | `buffet-rule:repository:v1` | `BUFFET_RULE_PROFILE` 独占的版本化 envelope |
| 自助餐编辑恢复副本 | `sessionStorage` | `buffet-rule:recovery:v1:{draftId}` | 单个草稿的临时恢复数据 |
| 自助餐列表列偏好 | `localStorage` | `buffet-rule:rule-list-columns:v1` | 列显示与顺序 |
| 自助餐列表筛选 | `sessionStorage` | `buffet-rule:rule-list-filters:v1` | 当前标签页筛选状态 |

`MENU_ORDER_LIMIT_PROFILE` 必须继续使用 `restaurantRules` 和 `restaurantRuleRecovery:{draftId}` 等现有键，并完整保留自身既有兼容迁移、normalizer 和写回行为。任何由 `BUFFET_RULE_PROFILE` 发起的流程不得读取、迁移、补字段或写入菜单键；自助餐模块初始化时不得扫描或复制菜单下单限制数据。

### 5.2 自助餐仓库与原子发布

自助餐正式规则、草稿、不可变发布版本和当前版本指针必须位于同一个 envelope 中：

```text
{
  schemaVersion: 1,
  revision: number,
  rules: StoredRule[],
  drafts: Draft[],
  snapshots: Record<snapshotId, PublishedSnapshot>,
  currentSnapshotId: string | null
}
```

一次发布先在内存中完成校验并构造完整新 envelope，随后只调用一次 `localStorage.setItem` 覆盖 `buffet-rule:repository:v1`。写入失败时旧值保持权威，列表和运行时继续读取 `currentSnapshotId` 指向的上一完整快照。损坏 JSON、未知 `schemaVersion` 或指针缺失时不得自动覆盖：列表进入只读错误态，编辑器提供返回和导出诊断，不向任何存储写回。

`StoredRule` 是完整作者态，至少包含规则 ID、状态、创建/更新信息、完整 `authoringConfig`（含未生效门店、主动排除门店、完整选品、数量矩阵、授权与条件）及 `publishedSnapshotVersion`。列表摘要只能从 `StoredRule` 派生，不得作为权威数据；运行快照是按生效范围裁剪和编译后的运行态。编辑与复制始终读取 `StoredRule.authoringConfig`。

正式规则状态机：

```text
新建/复制草稿 --发布--> active 正式规则 + 新快照
正式规则 --编辑--> 带 sourceRuleId 的派生草稿
派生草稿 --发布--> 替换 sourceRuleId 对应规则并保留源状态 + 新快照
正式规则 --复制--> 无 sourceRuleId 的新草稿
active --禁用--> disabled（不得被冲突阻止，生成移除该规则的新快照）
disabled --启用--> active（完整校验与冲突检查通过后生成新快照）
正式规则 --删除--> 删除规则 + 新快照
```

快照包含 `snapshotId`、单调递增 `version`、`createdAt` 和完整可运行规则集；至少保留当前版本和上一完整版本。运行时只读取 `currentSnapshotId` 对应的不可变快照，列表读取 envelope 中的 `rules` 与 `drafts`。恢复副本仅用于编辑器崩溃恢复，不属于发布事务。

所有 envelope writer 必须通过同一模块级互斥锁（浏览器环境优先使用 Web Locks，降级实现须具备带过期时间的 owner token）写入：锁内重新读取最新 envelope，核对调用方 `expectedRevision`，按草稿/规则 ID 合并不相交变更，再令 `revision + 1` 并一次写入。若同一草稿/规则已变化，或发布所基于的规则集版本已变化，则拒绝并提示刷新/合并，禁止静默 last-write-wins。自动保存、发布、启停和删除都服从该协议。

### 5.3 模块适用与运行时隔离

两个模块按订单业务模式二选一，不共同计算：

- `orderMode = buffet` 且存在有效 `buffetSessionId`：只运行当前自助餐快照；
- `orderMode = standard`：只运行菜单下单限制；
- `orderMode` 缺失、未知，或标记为 buffet 但缺少 `buffetSessionId`：阻止下单并要求修复订单业务模式，不降级到另一模块；
- 首次加入菜品后锁定 `orderMode`，订单中途不得切换；确需变更必须取消原订单并创建新订单。

因此同商品可在两模块分别配置且不做跨模块冲突。同一订单永远只有一个模块的规则、授权凭证和计数上下文参与原子校验。

硬隔离要求：

- 自助餐列表不得读取菜单下单限制规则；
- 自助餐新增、编辑、复制、删除和启停不得写入菜单下单限制存储；
- 两个模块的相同商品和分类不做跨模块冲突判断；
- 两个模块的恢复草稿、列表列偏好和筛选状态不得共用；
- 自助餐发布只生成自助餐规则快照；
- 菜单下单限制发布只生成菜单下单限制快照。

## 6. 规则模型

### 6.1 核心字段

```text
subject: order | party_size

period:
  order_lifetime
  per_round
  multi_round

targetType:
  category | dish
```

约束：

- `subject = order` 时，`period` 强制为 `order_lifetime`；
- `subject = party_size` 时，允许 `order_lifetime`、`per_round`、`multi_round`；
- `subject = party_size` 时保存并编辑 `partyRanges`，以当前订单有效人数 `N` 命中唯一人数区间；
- `partyRanges` 从 1 人开始、连续、不重叠，最后一档开放至更高人数；
- `subject = order` 时 `partyRanges` 固定为 `[{ min: 1, max: null }]`，只作为共享数量键的底层占位，页面不展示；
- 只有 `multi_round` 展示并保存 `roundRanges`。

人数区间和轮次区间使用同一边界契约：至少一段；`min` 为大于 0 的整数；`max` 为不小于 `min` 的整数或 `null`；区间为闭区间 `[min, max]`，`null` 表示无上界；第一段 `min = 1`；下一段 `min = 上一段.max + 1`；仅最后一段可且必须 `max = null`。

规则必须携带 `schemaVersion: 1`。加载时执行幂等 normalizer，但仅作用于内存；非法数据不得自动写回。字段切换规则如下：

| 操作 | 数据处理 |
| --- | --- |
| 切换 `subject` 或 `period` | 用户确认后清空数量矩阵，保留门店与所选商品；取消确认则完整恢复旧主体、周期、区间和数量 |
| 切换为 `subject = order` | 强制设置 `partyRanges = [{ min: 1, max: null }]` |
| 切换为 `subject = party_size` | 以上述单段作为初始可编辑人数区间 |
| 切换为 `multi_round` | 无合法轮次区间时初始化 `roundRanges = [{ min: 1, max: null }]` |
| 切换 `targetType` | 用户确认后清空所选商品及数量矩阵 |
| 修改已有 `roundRanges` | 用户确认后清空数量矩阵 |
| 修改已有 `partyRanges` | 用户确认后清空数量矩阵 |
| 从 `multi_round` 切换为其他周期 | 用户确认后立即移除 `roundRanges` |

列表遇到非法规则时显示“数据异常”且禁用启用/发布；查看为只读诊断；编辑进入修复模式；复制必须先通过结构校验。任何异常处理不得污染原存储。

### 6.2 八种合法组合

| 限购主体 | 额度周期 | 对象 | 有效限额 | 统计范围 |
| --- | --- | --- | --- | --- |
| 按桌/订单 | 整个订单 | 菜品 | `L` | 当前订单全部轮次、当前菜品 |
| 按桌/订单 | 整个订单 | 分类 | `L` | 当前订单全部轮次、当前分类合计 |
| 按人数 | 每单 | 菜品 | `L × N` | 当前订单全部轮次、当前菜品 |
| 按人数 | 每单 | 分类 | `L × N` | 当前订单全部轮次、当前分类合计 |
| 按人数 | 每轮 | 菜品 | `L × N` | 当前订单当前轮、当前菜品 |
| 按人数 | 每轮 | 分类 | `L × N` | 当前订单当前轮、当前分类合计 |
| 按人数 | 分轮次 | 菜品 | 当前轮次的 `L × N` | 当前订单当前轮、当前菜品 |
| 按人数 | 分轮次 | 分类 | 当前轮次的 `L × N` | 当前订单当前轮、当前分类合计 |

其中：

- `L` 为当前有效人数区间，以及分轮次时当前轮次区间，共同确定的每人限购数量；
- `N` 为当前订单有效人数；
- 按人数规则形成整单共享额度，不区分具体食客。

### 6.3 非法组合

以下组合不得由页面产生，加载异常数据时也必须校验失败：

- 按桌/订单＋每轮＋按菜品；
- 按桌/订单＋每轮＋按分类；
- 按桌/订单＋分轮次＋按菜品；
- 按桌/订单＋分轮次＋按分类。

## 7. 固定 6 步向导

采用用户确认的固定 6 步方案：

1. 规则类型
2. 场景配置
3. 限购数量
4. 超限授权
5. 生效范围
6. 确认发布

### 7.1 第 1 步：规则类型

选择“按桌/订单限购”后：

- 自动将周期固定为“整单累计”；
- 不展示统计周期选择；
- 只选择按分类或按菜品；
- 规则预览显示“按桌/订单 × 整单累计 × 按分类/按菜品”。

选择“按人数限购”后：

- 展示额度周期：每单、每轮、分轮次；
- 再选择按分类或按菜品；
- 说明整单额度为“每人限额 × 当前订单有效人数”。

儿童是否计入有效人数沿用现有计算口径配置。

### 7.2 第 2 步：场景配置

按桌/订单：

> 当前规则按整个订单累计，无需配置人数和轮次。

按人数＋每单：

- 展示人数区间配置；
- 整单共享额度＝命中人数区间的每人限额 × 当前订单有效人数。

按人数＋每轮：

- 展示人数区间配置；
- 每轮重新计算共享额度＝命中人数区间的每人限额 × 当前订单有效人数；
- 不展示轮次区间，每一轮使用同一套人数区间限额。

按人数＋分轮次：

- 展示人数区间配置；
- 展示轮次区间配置；
- 人数和轮次区间分别连续、不重叠，并开放覆盖后续人数或轮次；
- 数量配置由“人数区间 × 轮次区间”共同确定。

只有按桌/订单模式的第 2 步仅显示摘要说明和“下一步”；三种按人数模式均展示人数区间，分轮次模式额外展示轮次区间。

### 7.3 第 3 步：限购数量

数量列根据规则类型显示：

| 规则 | 数量列文案 |
| --- | --- |
| 按桌/订单 | 整单上限 |
| 按人数＋每单 | 每人每单上限 |
| 按人数＋每轮 | 每人每轮上限 |
| 按人数＋分轮次 | 每人上限 |

按桌/订单模式不展示人数场景筛选。三种按人数模式均展示人数区间筛选和人数矩阵；只有按人数＋分轮次额外展示轮次筛选，形成“门店 × 人数区间 × 轮次区间 × 产线 × 分类/菜品”的数量矩阵。每单和每轮模式内部使用单一轮次维度，不展示轮次筛选。

数量语义：

- 空值：未配置；
- `0`：禁止下单；
- 正整数：对应整单固定上限或每人上限；
- 不接受负数、小数和非数字。

主体或周期变化且已经配置数量时，沿用现有确认框。确认后清空数量配置，但保留已选门店和商品；取消则恢复原选择。

### 7.4 第 4～6 步

超限授权、生效范围和确认发布的结构与菜单下单限制一致：

- 授权范围支持本次操作、当前轮、当前订单；
- 生效门店在第 5 步选择；
- 不恢复后置门店选择页；
- 第 6 步展示自助餐规则计算方式、商品范围、数量完成度、门店和授权范围；
- 发布采用原子发布语义。

生效范围以菜单下单限制现行 `Conditions` 契约为规范性基线，字段覆盖参与门店、日期区间、活动周期 `activityCycle`、`daysOfWeek`、`daysOfMonth`、营业时段（含跨午夜）、会员等级和儿童是否计入有效人数。匹配使用门店时区；日期按门店营业日边界判断，跨午夜时段归属其开始营业日；运行时以提交操作时的订单与会员快照判断。自助餐模块复制字段结构和校验器，但存储值仍位于自助餐规则 envelope 内。

授权凭证至少绑定：`ruleRefs`（规则 ID 与版本）、门店、订单、`operationId`、请求摘要、`roundNo`、授权范围和员工权限。一次请求命中的每条超限规则都必须被凭证覆盖；未覆盖的任一规则继续阻止。本次操作凭证在成功提交后消费，当前轮凭证在换轮或关单时失效，当前订单凭证在关单或任一相关规则版本变化时失效。选择“当前轮”必须取得可靠 `roundNo`；缺失时该范围不可用，但仍可选择本次操作或当前订单，若没有其他允许范围则硬拒绝。授权后数量仍计入 `Used`，授权只绕过额度，不绕过人数/轮次缺失、售罄、停售、生效范围或其他业务校验，并必须记录审计。

## 8. 列表页与通用操作

自助餐规则列表参照菜单下单限制，支持：

- 新增规则；
- 编辑草稿或正式规则；
- 复制规则；
- 点击规则名称只读查看；
- 启用、禁用和删除；
- 筛选、列设置和分页；
- 展示门店、商品范围、计算策略、授权和状态。

列表页文案使用“自助餐规则”，不得出现“菜单下单限制规则”的返回标题或存储提示。

### 8.1 步骤页全屏承载

自助餐规则完全参照菜单下单限制的 iframe 全屏承载方式：

- `buffet-rule-editor.html` 与 `buffet-rule-publish-confirm.html` 属于全屏步骤页；新增、编辑、复制、查看和继续草稿进入上述页面时均统一全屏。
- `buffet-rule.html` 是列表页；iframe 返回列表页后立即解除全屏并恢复原内容区布局。
- 全屏由外层商家后台控制，不使用浏览器 Fullscreen API，不产生权限提示。
- 全屏 iframe 使用与菜单下单限制相同的固定定位、视口宽高、最高业务层级、背景色和无边框样式。
- 进入全屏时保存并锁定外层 `html`、`body` 的滚动状态；退出全屏、离开自助餐导航、iframe 卸载或页面重新挂载时必须恢复原值。
- 同一时刻最多允许一个规则 iframe 全屏；切换模块时先释放旧全屏状态。
- 全屏控制器应由菜单下单限制与自助餐规则共享，两个模块仅配置各自的步骤页集合、列表页名称和 iframe 选择器，不复制状态机。
- 页面识别采用 fail-safe 分类：editor/publish 集合进入或保持全屏；列表页退出；任何未知页、空白页、错误页、跨域页或无法读取 URL 的情况均安全退出。
- 共享控制器持有唯一 `ownerFrame` 和 `ownerToken`。只有当前 owner 可以恢复全局滚动状态；非 owner 的退出事件只清理自身样式。新 owner 接管时原子释放旧 owner，再保存全局原始状态并加锁。
- `enter`、`exit` 和 `teardown` 必须幂等。绑定接口返回 teardown；外层模块卸载、导航切换和重挂载必须显式调用 teardown，移除 load 等事件监听和绑定标记，使旧 iframe 的迟到事件失效。
- 进入全屏前逐项保存将被修改的 iframe `position/inset/width/height/z-index/background/border` 内联值、`html/body overflow` 及 `scrollX/scrollY`。退出、异常和 teardown 时逐项恢复；原先不存在的属性才删除，并保持外层滚动位置不变。

## 9. 冲突与叠加规则

冲突检查是表驱动纯函数，输入至少包含：模块、门店 ID、产线 ID、对象类型、对象 ID、`subject`、`period`、日期区间、活动周期、星期/月日条件、营业时段、会员范围、状态、草稿 ID、规则 ID 和 `sourceRuleId`。对象在不同产线的商品身份不同，冲突键包含产线 ID；同一分类跨产线也分别判断。

判定顺序：

1. 只查询 `buffet-rule` 模块，不跨模块；
2. 排除当前草稿自身及编辑来源 `sourceRuleId`；
3. 草稿和 `disabled` 正式规则不参与硬冲突，`active` 规则参与；
4. 门店、产线、对象类型和对象 ID 必须相同；
5. 日期区间与日历复现条件存在共同可满足日期，且营业时段和会员范围均有交集时，才继续判断口径；daily/weekly/monthly 组合必须按实际日历求交，不以活动类型字符串是否相同代替；
6. 按下表判断允许叠加或冲突。

口径枚举为 `order_lifetime`、`party_order_lifetime`、`party_per_round`、`party_multi_round`。

| 已有口径 × 候选口径 | 整单固定 | 每人每单 | 每人每轮 | 每人分轮次 |
| --- | --- | --- | --- | --- |
| 整单固定 | 冲突 | 允许 | 允许 | 允许 |
| 每人每单 | 允许 | 冲突 | 允许 | 允许 |
| 每人每轮 | 允许 | 允许 | 冲突 | 冲突 |
| 每人分轮次 | 允许 | 允许 | 冲突 | 冲突 |

分类规则和分类下单菜品规则因对象类型不同允许叠加；运行时两条规则分别计算并取更严格结果。

### 9.1 允许叠加

- 按桌/订单整单上限＋按人数每单；
- 按桌/订单整单上限＋按人数每轮；
- 按桌/订单整单上限＋按人数分轮次；
- 按人数每单＋按人数每轮；
- 按人数每单＋按人数分轮次；
- 分类合计规则＋分类下单个菜品规则。

### 9.2 禁止重复或冲突

- 同一对象重复配置按桌/订单整单上限；
- 同一对象重复配置按人数每单；
- 同一对象重复配置按人数每轮；
- 同一对象重复配置按人数分轮次；
- 同一对象同时配置按人数每轮和按人数分轮次；
- 分轮次规则内部区间重叠；
- 同一规则内重复选择同门店、同对象。

草稿只要求结构可持久化：候选冲突键完整时显示非阻塞提示，不阻止自动保存或离开。发布为 `active` 以及从 `disabled` 启用时执行同一套硬冲突检查；编辑发布排除自身与 `sourceRuleId`。编辑 `disabled` 规则并继续保持禁用时只做结构校验，不因当前冲突而阻止保存；禁用 active 规则也不做冲突阻断。服务员授权不能绕过规则配置冲突。本期不提供历史版本恢复入口。

## 10. 运行时计算

对每条命中规则分别计算：

```text
按桌/订单：EffectiveLimit = L
按人数＋每单：p = matchPartyRange(N)，L = limit[p, singletonRound]，EffectiveLimit = L × N
按人数＋每轮：p = matchPartyRange(N)，L = limit[p, singletonRound]，EffectiveLimit = L × N；Used 按当前轮统计
按人数＋分轮次：p = matchPartyRange(N)，r = matchRoundRange(roundNo)，L = limit[p, r]，EffectiveLimit = L × N
```

任一所需维度不能唯一命中时阻止应用规则，不得回退到第一档或默认值。

一次用户操作先将所有新增明细（包含套餐展开后的受控子项）按每条命中规则聚合为 `Q_i`，再整体校验：

```text
Used_i + Q_i <= EffectiveLimit_i
```

针对单个候选菜品的追加提示可显示：

```text
最终可追加数量 = max(0, min_i(EffectiveLimit_i - Used_i))
```

该标量只用于单项追加提示，不适用于含多个菜品的批量请求。批量请求只以每条规则的 `Used_i + Q_i <= EffectiveLimit_i` 作为权威准入条件，例如分类剩余 3、菜品 A 剩余 1、B 剩余 2 时允许原子追加 A1+B2。无命中规则时不限制。所有命中规则同时通过后，整批明细与计数使用同一订单版本原子提交；任一失败则整批不写入。请求携带唯一 `operationId`，服务端/目标运行时按 `operationId` 幂等；订单版本冲突时刷新 `Used` 后重试校验，禁止逐行提交绕过分类合计。

统计范围：

- 整单：当前订单全部轮次；
- 每轮/分轮次：当前订单当前轮；
- 分类：分类下所有命中菜品合计；
- 菜品：当前菜品累计。

`Used` 包含当前订单中已存在的购物车待提交、已提交和已送厨有效数量，也包含经过授权提交的超量；`Q_i` 只包含尚未进入本次 `Used_i` 快照的新增量，购物车提交不得重复计算同一明细。取消、退菜或作废成功后释放对应数量，失败或待审批时不释放。套餐按菜单下单限制现行子项展开/计数策略执行，并在提交前形成稳定快照。分类归属采用订单明细加入时绑定的已发布菜单分类快照，后续改分类不追溯改变历史计数。

### 10.1 命中与计数上下文

- 只有 `currentSnapshotId` 中状态为 `active` 的已发布规则参与计算；
- `N` 必须是当前订单的正整数有效人数；儿童排除后为 `0` 视为人数缺失并阻止按人数规则；
- 按人数规则的 `N` 必须且只能命中一个 `partyRanges` 区间，否则视为规则数据异常并阻止应用；
- 分轮次规则的 `roundNo` 必须且只能命中一个 `roundRanges` 区间，否则视为规则数据异常并阻止应用；
- 按桌/订单的累计键始终使用 `orderId`，不使用 `tableId`；
- 转桌不重置，合并订单按目标订单重新聚合，拆单随明细迁移计数，关单后重开沿用原 `orderId` 才延续计数，新订单号则重新开始；
- 每轮和分轮次使用提交时订单上的 `roundNo`；
- 门店、会员、人数、轮次和规则版本均以该次操作校验快照为准。

## 11. 人数与轮次异常处理

### 11.1 有效人数

- 按人数规则使用当前订单有效人数；
- 有效人数先选择对应人数区间，再使用该区间配置的 `L` 计算共享额度；
- 儿童计入规则沿用现有配置；
- 人数改变后，下次点单重新计算；
- 历史数量超过新限额时不撤销历史菜品，但禁止继续增加；
- 无法取得有效人数时阻止下单，不得默认为 1；
- 数量授权不能绕过有效人数缺失。
- 有效人数必须为正整数；儿童排除后为 `0` 按缺失处理。

### 11.2 轮次

- 每轮和分轮次依赖可靠的订单轮次；
- 分轮次的当前轮必须且只能命中一个区间；
- 无法取得轮次时阻止应用轮次规则；
- `0` 表示当前轮禁止继续下单该对象。

## 12. 保存与发布校验

自动保存和“保存草稿”允许业务字段不完整，只要 JSON、`schemaVersion` 和已存在字段结构合法；冲突仅提示，不硬阻断。保存失败时保留 `sessionStorage` 恢复副本、显示明确错误并阻止无提示关闭。新建/复制发布、active 规则编辑发布以及 disabled 规则启用必须全部通过：

1. 主体、周期和对象属于 8 种合法组合；
2. 按人数规则的人数区间连续、不重叠且覆盖后续人数；分轮次规则的轮次区间连续、不重叠且覆盖后续轮次；
3. 至少一家门店拥有已选择商品；
4. 生效门店的商品和数量配置完整；
5. 数量为 `0` 或正整数；
6. 不存在模块内重复或冲突规则；
7. 授权和生效范围配置合法；
8. 发布快照只包含自助餐规则数据。

数量矩阵沿用共享引擎键 `partyIndex|roundIndex|productLineId|targetId`，并位于对应门店的 `storeConfigs[storeId].limits`。按桌/订单派生 `1 × 1` 单元；按人数每单/每轮派生 `partyRanges.length × 1` 单元；按人数分轮次派生 `partyRanges.length × roundRanges.length` 单元。每个生效门店、产线和已选分类/菜品的全部笛卡尔积单元都必须 `configured = true`，其中 `0` 算已配置；缺少任一单元即阻止发布或启用。区间变化确认后清空并剪枝旧索引单元，不得把旧索引数量静默映射到新档位。

### 12.1 既有 v1 数据兼容

- 既有合法单段 `partyRanges = [{ min: 1, max: null }]` 直接解释为覆盖全部有效人数的一档，原人数索引、数量键和 `L` 保持不变，新运行时结果仍为 `L × N`。
- 加载兼容数据不修改 repository revision，不重写作者态规则或恢复副本，不生成新快照，也不使既有授权失效。
- 既有草稿与 `sessionStorage` 恢复副本继续按单段人数区间进入编辑，用户可主动增加区间。
- 缺失 `partyRanges` 的既有按人数 v1 规则仅在内存 normalizer 中补为单段 `[1, ∞)`；非法但非缺失的区间视为数据异常，必须由用户修复，均不得自动写回。
- 已发布快照继续按其发布时的单段数量键运行；只有用户编辑并重新发布后才产生包含多人数档的新快照。

发布按 §5.2 的单 envelope 协议执行：先完成全部校验和内存构造，再一次覆盖权威键。任何校验或写入失败均不得改变当前快照、正式规则或删除草稿。发布成功后才清理对应恢复副本；编辑发布以 `sourceRuleId` 替换原规则并保留源状态，复制发布创建新 active 规则 ID。disabled 规则编辑发布只需结构与字段合法，运行快照仍不包含它；其后启用时再执行完整性与冲突校验。
