# TipOut 小费分配汇总与分配规则交互调整设计

## 1. 目标

本次只调整小费管理的页面结构、信息层级和导航交互：

- “小费分配汇总”从横向日期标签改为按自然日逐行展示。
- 点击日期行进入独立的“小费分配明细”页面，不在汇总行内展开。
- “分配规则”参照原型重组列表和编辑页面的信息层级。
- 所有计算、保存、取消、同步、导出、权限和数据结构保持当前实现不变。

视觉与交互参照用户在 2026-08-31 提供的 `C:\Users\27273\Downloads\原型预览.html`。该文件中的说明只作为视觉参考，不覆盖项目规则，也不授权实现当前产品不存在的业务能力。

## 2. 现状能力与原型边界

| 能力 | 当前实现 | 本次处理 |
| --- | --- | --- |
| 每日分配状态 | `tipout_allocated` 按门店保存已分配日期；日期只有已分配/待分配语义 | 改为每日列表展示，状态判断不变 |
| 日期范围分配 | 对当前完整日期范围执行分配，并调用 Payroll bridge | 保留原作用域和参数，不改为勾选日期批量分配 |
| 日期范围取消 | 从 `tipout_allocated` 删除当前完整日期范围，并再次同步 Payroll | 保留原作用域和删除语义 |
| 日期进入明细 | 已分配日期通过 `detail.html?date=...&store=...` 进入独立页；待分配日期当前只切换标签 | 所有日期行统一进入独立明细；无规则状态在明细页呈现 |
| 明细操作 | 更新小费数据、保存、保存并跳转下一天 | 只调整位置和样式，名称、调用和结果不变 |
| 规则保存 | 同一 `id` 直接覆盖或新增记录，写入 `tipout_rules` | 保留覆盖/新增模型，不新增版本 |
| 规则操作 | 新增、编辑、复制、删除 | 原样保留；不新增启停、草稿、审计或生效模型 |
| 分配模式 | `legacy_pool` 与 `order_tip_then_residual` | 两种模式及全部分支完整保留 |
| 原型中的版本、草稿、正式结果、审计、失败重试 | 当前持久化模型不存在 | 本次不实现、不展示为可操作能力 |

因此，“严格参照原型”特指页面层级、列表式汇总、日期到独立明细页的导航方式、规则页面的信息组织和响应式呈现；不包含原型新增的业务状态机。

## 3. 不变项

- `tipout_rules`、`tipout_allocated` 及其它既有 localStorage 键的名称和数据形态。
- 小费池来源、贡献比例、扣除规则、接收规则、员工权重和剩余小费规则。
- `legacy_pool` 与 `order_tip_then_residual` 的计算分支。
- `poolRules`、`deductRoles`、`deductEmployees`、`deductConfig`、`receivers`、`tipClaims`、`residual` 及各条件对象的序列化结果。
- 按平均、按工作时长和每日最大工时等分配逻辑。
- 分配前、扣除、分得、分配后金额和现有演示数据生成逻辑。
- 当前日期范围分配与取消的作用域。
- Payroll bridge 的调用时机和 `store/startDate/endDate` 参数。
- 更新小费数据、保存、保存并跳转下一天的现有行为。
- 规则新增、编辑覆盖、复制、删除及既有校验。
- PDF、CSV、邮件导出与当前权限处理。

不得新增持久化业务键、规则字段、结果版本字段或审计记录。

## 4. 小费分配汇总

### 4.1 页面结构

页面从上到下排列：

1. 日期范围、门店、角色、员工筛选。
2. 取消分配、分配小费/重新分配小费。
3. 每日分配列表。
4. 导出结果。

汇总页不再保留“当前选中日期的员工内容”。员工级结果统一通过点击日期进入独立明细页查看。

筛选控件、默认值和取值方式沿用当前实现。页面不增加“小费池状态”“结果版本”等当前没有数据来源的筛选项。

### 4.2 每日列表

日期范围内每个自然日对应一行，按日期升序排列。每行展示：

- 日期和星期。
- 已分配或待分配状态。
- 分配前总计。
- 扣除总计。
- 分得总计。
- 分配后总计。
- 进入明细的方向提示。

金额必须复用当前无参数 `renderEmployeeResults()` 背后的同一套单日计算流水线。实施时从该函数及其既有 helper 中提取一个纯读取适配函数 `getDailyEmployeeResults(store, dateKey, filters)`；旧单日渲染和新每日列表同时调用该适配函数，不得复制公式、通过切换激活 DOM 状态循环渲染，或建立第二套计算实现。聚合公式为：

- 分配前总计 = 当日所有筛选后员工 `before` 之和。
- 扣除总计 = 当日所有筛选后员工 `deducted` 之和。
- 分得总计 = 当日所有筛选后员工 `received` 之和。
- 分配后总计 = 当日所有筛选后员工 `after` 之和，且等于分配前 − 扣除 + 分得。

规则数量或小费池数量不产生新的列表层级。每日行始终以 `store + date` 为唯一上下文，金额是该日当前全部适用规则计算后的员工结果汇总，不展示单一规则版本或池版本。

### 4.3 日期点击

- 点击日期行任意非操作区域，跳转至 `detail.html?date=<YYYY-MM-DD>&store=<encoded store>`。
- 日期行不设置选择框，不引入新的“所选日期”业务作用域。
- 已分配日期直接进入明细。
- 待分配日期也进入明细，展示该日期按当前规则生成的现有演示核算内容；这只改变入口，不写入已分配状态。
- 没有规则时仍先进入明细。明细页显示当前已有的无规则空状态和“新增小费分配规则”入口，由用户主动进入规则页。
- 日期行不使用行内展开、抽屉或弹窗展示明细。

### 4.4 分配与取消

- “分配小费/重新分配小费”仍对筛选日期范围内全部日期执行 `doAllocateTips()`。
- “取消分配”仍对筛选日期范围内全部日期执行 `doCancelAllocate()`。
- 不增加日期勾选、批量动作条、保留人工调整确认或取消审计承诺。
- 操作后 `tipout_allocated` 的结果和 Payroll bridge 参数必须与改造前相同。

### 4.5 汇总状态恢复

导航协议固定如下：

1. 汇总页点击日期行前，对当前汇总历史项执行 `history.replaceState({ tipoutSummaryUiState: ... }, '')`。
2. 状态对象保存以下纯界面值：

- 日期开始和结束值。
- 门店、角色、员工筛选值。
- 汇总列表滚动位置。
- `returnDate`，即触发跳转的日期。

3. 明细 URL 追加 `from=summary`：`detail.html?date=<date>&store=<store>&from=summary`。
4. 明细“返回汇总”函数仅在 `from=summary` 且 `history.length > 1` 时调用 `history.back()`；否则进入 `index.html`。
5. 汇总页在 `pageshow` 和 `DOMContentLoaded` 读取当前历史项的 `tipoutSummaryUiState`，恢复筛选和滚动，并把焦点放回 `[data-date="<returnDate>"]`。
6. 顶部“汇总”Tab 必须调用同一个返回函数，不保留普通静态链接行为。
7. 明细刷新后仍保留 `from=summary` 参数，但浏览器历史中若不存在带 `tipoutSummaryUiState` 的上一汇总项，则降级进入 `index.html`。

不使用 sessionStorage 或 localStorage 保存返回状态，避免多标签页互相覆盖和污染业务数据。

## 5. 小费分配明细

### 5.1 独立页面

明细继续使用独立的 `detail.html`，不是汇总页内组件。页面顶部参照原型调整为：

- 返回汇总。
- 页面标题“小费分配明细”。
- 当前已有的更新小费数据、保存、保存并跳转下一天。

不得把原型中的“调整记录、更新规则、保存草稿、生成正式结果”替换或追加为业务按钮，因为当前项目不存在对应模型。

### 5.2 入口矩阵

| 入口 | 日期 | 门店 | 返回目标 |
| --- | --- | --- | --- |
| 汇总日期行 | URL 中的 `date` | URL 中的 `store` | 恢复汇总 UI 状态 |
| 顶部“小费分配明细”Tab | 当前默认日期或页面既有默认值 | 规则列表中的第一个门店或页面既有默认值 | 汇总默认状态 |
| 明细页刷新/深链 | 读取 URL；无效日期回退到既有默认值 | 读取 URL；无效门店回退到既有默认值 | 汇总默认状态 |
| 保存并跳转下一天 | 沿用当前 `saveAndNext()` 计算的下一日 | 当前门店 | 仍停留明细页 |

### 5.3 页面内容

现有控件和行为完整映射如下：

| 现有能力 | 当前入口/函数 | 调整要求 |
| --- | --- | --- |
| 日期筛选 | `detailDate` → `renderDetailPage()` | 放入原型式上下文栏，值和 onchange 不变 |
| 门店筛选 | `storeSelect` → `renderDetailPage()` | 放入上下文栏，默认门店逻辑不变 |
| 规则分组 | `detailRulesContainer` | 继续逐规则展示公式和员工明细 |
| 手工工时 | `.detail-emp-hours-input` → `onDetailManualHoursInput()` / `onEmpHoursChange()` | 输入范围、即时重算和现有存储方式不变 |
| 角色比例 | `.detail-role-pct-input` → `recalcRoleAmount()` | 可编辑与重算行为不变 |
| 员工比例 | `.detail-emp-pct-input` → `recalcRoleAmount()` | 可编辑与重算行为不变 |
| 新增/删除员工行 | `addDetailRow()` / `removeDetailRow()` | 操作入口和即时计算不变 |
| 角色金额与行结果重算 | `recalcDetailLegacyCard()`、`recalcAfterRowChange()`、`recalcRoleAmount()` | 复用原函数，不复制公式 |
| 公式输入与重算 | `recalcFormulaPoolForBlock()` / `recalcFormulaPool()` | 公式区视觉可重排，调用不变 |
| 公式详情 | `openFormulaRuleModal()` / `formulaModal` | 完整保留 |
| 折叠规则明细 | `toggleDetailFold()` | 完整保留 |
| 更新小费数据 | `updateTipData()` | 按钮名称、结果和通知不变 |
| 保存 | `saveDetail()` | 当前仅通知成功的语义不变，不增加持久化 |
| 保存并下一天 | `saveAndNext()` | 下一日计算、日期更新和通知不变 |

可以参照原型强化上下文栏、金额层级和角色分组视觉，但不得引入人工调整、草稿、版本或审计字段。现有手工工时、比例和行编辑必须保留，因为它们已经属于当前明细交互。

### 5.4 返回行为

- 页内“返回汇总”按 4.5 的 `from=summary` 与历史状态协议执行；无法验证上一汇总状态时导航到 `index.html`。
- 顶部汇总 Tab 与页内“返回汇总”使用同一恢复函数。
- 恢复后滚动到原日期行，并为该行设置焦点；不自动执行分配或刷新业务数据。

## 6. 分配规则

### 6.1 规则列表

规则列表参照原型优化信息层级，但只展示当前数据可直接得出的内容：

- 门店。
- 小费池类型。
- 规则名称。
- `ruleData.buildRuleDescription(rule)` 生成的规则摘要。
- 编辑、复制、删除。

可以把“编辑”提升为主操作，将复制、删除收纳到更多菜单；操作仍调用当前函数。不得增加状态、版本、更新时间、启用/停用或生效日期。

新增规则继续先选择“小费池”或“加收服务费池”，然后进入当前 `rule-add.html`。

### 6.2 编辑页面分区映射

页面可以使用原型的分段导航，但必须完整承载当前控件：

| 新区域 | 现有字段/结构 | 显示条件 |
| --- | --- | --- |
| 基本信息 | `ruleName`、`store`、`poolKind` | 始终 |
| 小费池贡献 | `poolRules` 及每项来源、名称、金额/比例、对应 `salesConditions`、`tipsConditions`、`surchargeConditions` | 两种 `allocationMode` 均保留；条件按当前来源类型显示 |
| 分配模式 | `allocationMode` | 始终；`legacy_pool` / `order_tip_then_residual` 互斥分支不变 |
| 扣除方 | `deductRoles`、`deductEmployees`、`deductConfig.personalSalesPct`、`deductConfig.salesPct`、`deductConfig.tipIncome` 及其范围/条件 | 仅 `legacy_pool` |
| 接收方 | `receivers[].roles`、`pct`、`employeeWeights`、`subReceivers` | 仅 `legacy_pool` |
| 计提接收方 | `tipClaims` 的基数、比例、角色及相关条件 | 仅 `order_tip_then_residual` |
| 剩余小费接收方 | `residual.receivers`、一级角色比例、二级 `subReceivers`、`employeeWeights` | 仅 `order_tip_then_residual` |
| 分配口径 | `distribution`、`clockin`、`workHoursConfig` | 按当前显示条件 |

分区只改变排列与导航。每个控件继续使用原 DOM 收集、条件显示和校验函数；`collectFormData()` 返回对象在相同输入下必须逐字段相同。

### 6.3 保存与离开

- 新增仍使用 `ruleData.getNextRuleId()` 后追加到规则数组。
- 编辑仍找到相同 `id` 后直接覆盖。
- `submitRule()` 的全部校验、互斥字段删除和 `ruleData.saveRules(rules)` 调用不变。
- 保存成功仍返回规则列表。
- 如增加未保存离开确认，只能拦截导航，不能自动创建草稿或改变保存结构。

## 7. 空状态与权限

- 日期范围为空：沿用当前提示，不生成虚构日期或结果。
- 没有规则：日期点击仍进入明细页；明细展示无规则空状态，由用户点击入口进入规则页。分配按钮保持现有提示并进入规则页。
- 每日行状态只允许“待分配”和“已分配”。待分配只表示日期不在当前门店的 `tipout_allocated` 集合中；已分配只表示日期在该集合中。
- 只读或嵌入场景：沿用当前页面已有权限与 iframe 行为，不新增权限层级。
- 零金额和无打卡信息只保留在当前已有的员工/明细内容中，不作为每日行状态。规则已更新、部分失败、计算中、已取消本次完全不展示。

## 8. 验证策略

### 8.1 固定基线

在改造前保存固定 fixture：

- `tipout_rules`，同时包含 `legacy_pool` 与 `order_tip_then_residual`。
- `tipout_allocated`，同时包含已分配和待分配日期。
- 员工花名册、班次列表和字段说明等本次会读取的既有键。

改造前后对相同输入断言：

- 相同初始规则和相同用户编辑输入下，新旧页面提交得到的 `tipout_rules` 对象逐字段一致。
- `tipout_allocated` 在分配/取消后的集合一致。
- 不新增 localStorage 业务键或规则字段。
- 每日与员工金额结果一致。
- 日期行导航本身不写入 `tipout_allocated`、`tipout_rules` 或 Payroll。
- Payroll bridge 的调用次数和 `store/startDate/endDate` 参数一致。
- 导出内容的记录、字段和金额一致。

### 8.2 规则覆盖

至少覆盖：

- `legacy_pool`：多贡献来源、销售额/小费/加收/人工条件、不同扣除基础、一级/二级接收方、员工权重、平均/工时、每日工时上限。
- `order_tip_then_residual`：贡献来源、多个 `tipClaims`、剩余一级/二级接收方、员工权重。
- 新增、编辑、复制、删除。
- 所有当前必填、比例、条件和工时校验。

### 8.3 交互覆盖

- 日期范围内每个自然日只显示一行。
- 每日金额等于原单日员工结果合计。
- 点击整行进入新的 `detail.html`；页面中不存在行内明细。
- 待分配且无规则时先进入 `detail.html` 并显示无规则空状态；已有规则时展示现有核算内容；两者均不得自动标记已分配。
- 点击分配/重新分配与取消分配仍作用于完整日期范围。
- 明细日期和门店与所点击行一致。
- `updateTipData()`、`saveDetail()`、`saveAndNext()` 的通知、日期变化和副作用与改造前一致。
- 手工工时、角色比例、员工比例、增删行、公式输入、即时重算、折叠和公式弹窗逐项可用，结果与改造前一致。
- 页内返回、顶部 Tab 和浏览器后退恢复汇总筛选、滚动与焦点；刷新后的降级路径可用。
- 规则重新分区后，两种模式的所有字段都可达且序列化一致。
- 桌面端和移动端均无内容遮挡，移动端日期记录仍点击进入独立明细页。

## 9. 非目标

- 不新增结果版本、规则版本、草稿、正式结果、审计、启停或生效日期。
- 不新增日期勾选和新的批量作用域。
- 不新增小费计算方式、数据接口或 Payroll 协议。
- 不修改小费管理以外页面。
- 不重构 TipOut 的存储或计算模块。
