# 小费管理默认手动工时演示数据设计

日期：2026-09-09

## 背景与目标

当前员工对账已经可以展示“不打卡”规则下从小费分配明细补录的工时，但 Golden Dragon 演示门店缺少完整的默认演示数据链。本次补齐默认规则与 2026-01-01 的补录数据，使规则列表、小费分配明细和员工对账使用同一份数据。

本次只增加默认演示数据与数据读取联动，不修改小费池计算公式、角色分配算法或已有分配结果。

## 默认小费规则

在 `ruleData.js` 的默认规则中新增一条独立规则，保留现有 Sakura 规则不变。

- 配置来源：复制现有“Tip Pool — 多角色分配（不打卡按工时）”。
- 门店：`Golden Dragon Chinese Kitchen - Dallas, TX 75231`。
- 规则 ID：使用新的稳定 ID，不与已有默认规则冲突。
- 小费池来源：小费的 10%。
- 扣除角色：Server、Bartender、Cashier。
- 接收角色：Busser 50%、Runner 30%、Host 20%。
- 员工打卡设置：不打卡（`clockin: "noclock"`）。
- 分配方式：按工作时长占比分配（`distribution: "hours"`）。
- 工时配置：按照实际录入工时。

默认规则只在本地尚未初始化 `tipout_rules` 时随默认数据写入。不得覆盖用户已经保存的规则列表。

## 默认工时补录数据

针对 2026-01-01，在 Golden Dragon 门店的新默认规则下，为规则涉及且处于“未打卡”状态的员工提供默认 `6 h` 补录记录。

默认补录记录必须写入或转换为现有 `TipOutManualHours` 使用的标准数据结构，至少包含日期、员工、规则、池名称和工时。小费分配明细与员工对账不得各自维护一份独立的硬编码展示值。

默认值只在对应日期、员工和规则不存在补录记录时生效：

- 已存在任意工时补录（包括显式录入 `0 h`）时，保留已有记录，不用 `6 h` 覆盖。
- 已打卡员工不生成默认补录记录。
- 其他日期不生成默认补录记录。
- 其他门店或其他规则不生成默认补录记录。

## 页面行为

### 小费分配明细

打开 2026-01-01 的 Golden Dragon 小费分配明细时，新规则按“不打卡 + 按工时占比”模式展示。符合条件的员工工时输入默认显示 `6 h`，并继续允许用户修改。修改后保存至现有手动工时存储，并立即成为后续展示的权威值。

### 员工对账

员工对账不自行推导默认工时，而是读取小费分配明细所使用的同一条手动工时记录：

- 工时列显示 `6 h`（或用户后续修改后的值）。
- 工时右侧显示小标签“录入”。
- 考勤状态仍显示“未打卡”，补录工时不伪装成打卡记录。
- 班次、上班时间和下班时间仍按未打卡状态展示，不生成虚假打卡时间。

员工对账汇总、筛选、CSV、PDF 和邮件导出继续复用同一份对账行数据，因此工时值和“手动录入”来源在各出口保持一致。

## 数据兼容与边界

- 现有 localStorage 中已有的规则和工时记录保持不变。
- 默认演示数据初始化应具备幂等性，刷新页面不得重复生成记录。
- 员工姓名或标识的匹配沿用当前手动工时存储规则，不引入第二套员工映射。
- 本次不反向修改考勤系统，不创建班次，不补充上下班时间。
- 本次不重新计算或覆盖历史小费分配结果；工时仅进入现有“不打卡 + 按工时占比”规则已经支持的计算路径。

## 验收标准

1. 全新浏览器存储下，Golden Dragon 规则列表出现新增的不打卡按工时规则，Sakura 原规则仍存在。
2. 进入 Golden Dragon 的 2026-01-01 小费分配明细，所有符合规则且未打卡的员工默认显示 `6 h`。
3. 进入上述员工的员工对账，2026-01-01 显示“未打卡”、`6 h` 和“录入”标签。
4. 已有补录值（包括 `0 h`）不会被默认 `6 h` 覆盖。
5. 已打卡员工、其他日期、其他门店和其他规则不会收到该默认值。
6. 页面刷新后不产生重复补录记录；修改工时后，明细、对账与导出读取修改后的值。
7. 原有小费分配算法及既有金额结果不变。
