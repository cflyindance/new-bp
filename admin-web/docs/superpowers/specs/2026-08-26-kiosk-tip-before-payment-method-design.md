# Kiosk 小费页面置于支付方式选择前设计

## 目标

在 Kiosk 本地配置后台「小费设置 → 选择小费流程」中新增「支付方式选择页面之前」。当信用卡/借记卡与柜台支付均启用且均允许展示小费时，门店可以把点单流程从“先选择支付方式，再选择小费”调整为“先选择小费，再选择支付方式”。

## 现状

- 「选择小费流程」使用 Kiosk 配置 `id: 24`、`key: "tip-procedure"`。
- 现有值：`0` 为「刷卡之前」，`1` 为「刷卡之后」。
- 当仅启用一种支付方式时，现有流程不会展示支付方式选择页，而是直接进入该支付方式对应的后续流程。
- 当信用卡和柜台支付同时启用时，当前先进入 `/paymentType`；选择信用卡且配置为刷卡前小费时，再进入 `/tippingPanel`。
- `/tippingPanel` 确认后当前固定继续信用卡最低消费校验与 `/cardPayment`，因此新流程不能只改入口顺序，还必须让小费页按进入场景决定下一页。

## 配置设计

扩展既有枚举，不新增配置 ID：

```js
{
  id: 24,
  key: 'tip-procedure',
  value: 2
}
```

- `0`：刷卡之前（既有语义不变）；
- `1`：刷卡之后（既有语义不变）；
- `2`：支付方式选择页面之前（新增）。

所有语言增加 `tip-procedure-2`。简体中文准确显示「支付方式选择页面之前」。

## 可选资格与联动

只有同时满足以下条件，值 `2` 才可选择：

1. 「支付设置 → 选择支付方式」同时启用信用卡/借记卡（`0`）和柜台支付（`1`）；
2. 「小费设置 → 显示小费选项」同时勾选信用卡/借记卡和柜台支付。

界面始终展示第三个单选项，但资格不满足时置灰禁用。资格由当前编辑态 POS 支付配置与 Kiosk `tipPaymentTypes` 共同计算，不等待保存后数据。

若当前已经选择值 `2`，之后取消任一支付方式或对应小费选项，系统立即把 `tip-procedure` 自动恢复为值 `0`「刷卡之前」。加载到值 `2` 的历史或异常配置时，在 POS 支付配置加载完成前不改写；加载完成并确认资格不满足后同样回退到 `0`，统一保存时持久化。

## 点单流程

### 双支付方式且选择值 2

在所有原本即将进入 `/paymentType` 的点单入口统一判断：

1. 当前确实同时启用信用卡和柜台支付；
2. 两种方式均启用小费；
3. `tip-procedure.value === 2`。

满足后先进入 `/tippingPanel`。小费确认并保存金额后进入 `/paymentType`，不在此时执行信用卡最低消费检查，也不预先写入信用卡支付方式。用户随后在支付方式选择页选择信用卡或柜台支付，并继续各自既有流程；此前选择的小费金额随订单继续保留。

返回操作遵循页面栈：支付方式选择页返回小费页，小费页返回其原点单入口。

### 单支付方式

值 `2` 在配置层面不会对单支付方式生效，因为资格不成立并会回退为 `0`。单支付方式继续沿用现有行为：不展示 `/paymentType`，符合小费条件时直接进入小费页，再进入唯一支付方式的后续流程。

### 既有值 0 与 1

- 值 `0` 与值 `1` 的入口、信用卡支付、小费和签名顺序保持不变。
- 新增判断使用严格枚举比较，不能再把所有非零值笼统当作“刷卡之后”，避免值 `2` 被旧的 truthy 判断误判。

## 组件与逻辑边界

- 新增共享流程资格/路由判断函数，集中处理支付方式集合、`tipPaymentTypes` 和 `tip-procedure`，供设置页及多个点单入口复用。
- `RadioGroup` 支持按选项禁用，不把业务资格判断写死在通用单选组件中；`ServiceItem` 接收计算后的禁用项。
- `serviceSetting/index.js` 负责当前编辑态资格计算、点击拦截、资格失效后的自动回退，以及保存前兜底。
- 所有现有“进入支付方式选择页”的入口改用同一个路由决策，避免手机号、姓名、CRM、短信判断等入口行为不一致。
- `TippingPanel` 根据明确的“支付方式选择前”场景决定确认后的目标页；其他场景继续进入信用卡校验/支付流程。

## 状态传递

进入小费页时通过路由 state（或等价的显式导航上下文）标记 `nextStep: paymentType`。小费页只信任该上下文与当前配置的再次校验：若配置在页面停留期间失效，则安全回退到既有支付方式决策，不盲目跳转。

不得仅根据 `tip-procedure === 2` 推断下一页，因为单支付、恢复页面或其他旧入口可能直接进入小费页；显式上下文能避免这些场景被错误导向支付方式选择页。

## 异常与兼容

- 未知 `tip-procedure` 值按值 `0` 的安全流程处理。
- POS 支付配置加载中，第三项禁用但不自动改写已保存值；加载完成后再确认资格。
- 资格失效即使未成功保存，点单运行时也会重新校验双支付及双小费条件，不会错误进入“先小费”流程。
- Dual Price 现有授权逻辑继续适用：值 `2` 与值 `0` 都属于刷卡前选择小费的模式；需要授权时仍走现有密码与 `Authorization` 流程。
- 礼品卡不参与该资格，也不新增礼品卡小费流程。

## 验收标准

1. 「选择小费流程」展示第三项「支付方式选择页面之前」。
2. 仅当支付设置和显示小费选项都同时包含信用卡/借记卡、柜台支付时，第三项可选。
3. 任一条件不满足时第三项置灰且点击无效。
4. 已选第三项后取消任一支付方式或小费选项，立即自动回退为「刷卡之前」。
5. 加载到无效的值 `2` 时，等待支付配置加载完成后回退，保存后刷新仍为值 `0`。
6. 双支付、双小费且值为 `2` 时，点单流程为：小费页 → 支付方式选择页 → 所选支付流程。
7. 小费页确认后不会预设信用卡，也不会提前执行信用卡最低消费校验。
8. 在支付方式选择页选择信用卡或柜台支付，均保留此前选择的小费金额。
9. 单支付方式不展示支付方式选择页，继续直接进入小费页及唯一支付流程。
10. 值 `0`、值 `1` 的既有流程不变，值 `2` 不会被 truthy 判断误当作值 `1`。
11. 姓名、手机号、CRM、短信及其他既有支付入口对值 `2` 的行为一致。
12. 资格运行时失效或配置保存失败时，不会进入无效的先小费流程。
13. Dual Price 授权、售罄检查、信用卡最低消费、签名、No Tip 与礼品卡行为除必要顺序调整外保持不变。

## 验证策略

- 为流程资格、无效值回退和入口路由决策增加单元测试。
- 为小费页确认后的 `paymentType`/`cardPayment` 分流增加行为测试。
- 覆盖双支付双小费、单支付、仅一项小费、配置加载中及运行时资格失效。
- 运行 KioskLite 全量测试和生产构建。
- 发布并校验 `dist/kpos/kiosklite` 嵌入包。
- 浏览器验证值 `0`、`1`、`2` 以及支付方式/小费选项取消后的联动。

## 非目标

- 不增加新的支付方式或礼品卡小费支持。
- 不改变小费金额、比例、No Tip 或签名配置本身。
- 不新增后端接口或配置 ID。
