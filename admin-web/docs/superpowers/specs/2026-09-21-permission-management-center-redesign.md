# 权限管理中心重设计方案

> 日期：2026-09-21  
> 状态：已完成产品设计确认，待实施计划  
> 范围：商家后台权限管理中心；兼顾集团、品牌、门店三级组织与企业级权限中心

## 1. 背景与目标

当前权限中心已经具备 RBAC、员工多角色、品牌/区域/门店数据范围、组织视角限制、设置项只读/可编辑以及授权链审计等基础能力，但权限表达和管理体验仍存在明显缺口：

- 人员只能绑定角色与数据范围，无法在角色基线上为个别人设置少量例外。
- 权限节点普遍使用 `enabled`、`display`、`l4EditMode` 等结构，不同层级的业务语义不统一。
- 普通业务页面机械生成“新建、编辑、删除、导出、审核”动作，可能出现页面并不存在或后端无法校验的伪权限点。
- 角色编辑采用四列级联，适合逐层浏览，但不利于跨页面对比、搜索差异、查看权限来源和最终生效结果。
- 权限总览偏数量统计，缺少高风险权限、人员例外、即将过期权限和长期未使用角色等治理信息。

本次设计目标：

1. 同时支持按角色和按人员授权，避免为每个特殊人员创建相似角色。
2. 最小颗粒度达到真实功能点，并准确表达页面可见、动作可执行、设置可见和设置可编辑。
3. 功能权限与数据范围继续分离，且所有下级授权受上级授权天花板约束。
4. 最终权限可计算、可解释、可预览、可审计。
5. 前端展示与后端 API 使用同一权限资源键和判定结果。

## 2. 当前实现评估

### 2.1 值得保留的设计

- `RbacRole.selection` 已能表达四级权限树。
- 员工支持绑定多个角色，当前实现按权限并集合并。
- `StaffAssignment.storeAccess` 将功能权限与数据范围分离，支持 `all / brands / regions / stores`。
- `maxPerspective`、`scopeCeiling`、`grantedBy` 已能表达组织视角和授权链上限。
- 设置项已有 `denied / display-only / editable` 三态落地逻辑。
- 导航可见性、设置项可见性、设置项只读状态已与登录会话权限快照连接。

### 2.2 需要修正的问题

1. **人员差异无法表达**：同角色人员的少量差异只能通过复制角色解决，角色会快速膨胀。
2. **资源语义混杂**：模块、页面、动作、设置项共用相似的启用字段，管理员难以理解“启用”究竟代表可见还是可操作。
3. **动作节点失真**：固定动作模板不能保证页面真实具备该能力，也不能保证后端存在对应鉴权点。
4. **最终结果不可解释**：管理员无法直接看到某项权限来自哪个角色、是否被人员例外覆盖、为何被组织上限裁剪。
5. **缺少变更影响预览**：角色修改前不能明确看到受影响人员与高风险权限变化。
6. **权限治理不足**：缺少异常授权、临时权限、孤儿角色和高风险权限的集中诊断。

结论：现有“RBAC + Data Scope + Perspective”总体方向合理，无需推翻；应升级资源语义、引入人员例外层，并重做配置与解释交互。

## 3. 设计原则

1. **默认拒绝**：未知、缺失或失效的权限资源按无权处理。
2. **角色是基线，人员只存差异**：不为人员复制完整权限树。
3. **权限点必须真实**：只有前端有控制点、后端有校验点的业务能力才能注册为动作权限。
4. **功能与数据正交**：功能允许不代表可以访问所有品牌或门店数据。
5. **授权时下级只能获得上级权限的子集**：新增或重新授权时，功能、数据范围、最高视角均按授权人当时的最终权限生成并校验授权天花板；授权完成后按保存的快照执行，不持续跟随历史授权人的实时权限变化。
6. **最终结果可解释**：任何权限都能展示状态、来源和覆盖原因。
7. **前端限制不是安全边界**：隐藏、禁用和只读用于体验，后端接口必须独立鉴权。

## 4. 权限资源模型

### 4.1 资源类型与最小颗粒度

| 资源类型 | 示例 | 权限状态 | 作用 |
|---|---|---|---|
| `module` | 订单中心 | `hidden / visible` | 控制一级模块入口及其整体可达性 |
| `page` | 订单列表 | `hidden / visible` | 控制导航入口和直接路由访问 |
| `action` | 退款、作废、导出、修改支付方式 | `denied / allowed` | 控制真实业务动作及对应 API |
| `setting` | 自动接单、允许修改税率 | `hidden / read / edit` | 控制设置项不可见、只读或可编辑 |

页面中的真实业务动作是普通业务页的最小权限颗粒度；配置型页面可进一步到单个设置项的可见与可编辑状态。

父级规则：

- 模块隐藏时，其下所有页面、动作和设置项均不生效。
- 页面隐藏时，其下动作和设置项均不生效。
- 父级重新开放时，保留下级原配置，避免管理员重复配置。
- 后代配置存在差异时，父级显示半选或“部分开放”，但不创造新的权限语义。

### 4.2 资源注册表

```ts
type PermissionResourceType = "module" | "page" | "action" | "setting";
type PermissionRisk = "normal" | "sensitive" | "critical";

interface PermissionResource {
  key: string;
  type: PermissionResourceType;
  parentKey?: string;
  moduleId: string;
  pageId?: string;
  title: string;
  route?: string;
  actionId?: string;
  settingId?: string;
  risk: PermissionRisk;
  active: boolean;
  backendPolicyKey?: string;
}
```

要求：

- `key` 发布后稳定，不因展示名称或导航排序变化而改变。
- 动作权限由业务页面显式注册，不再为所有页面统一生成五个固定动作。
- 资源下线使用 `active = false`，不直接物理删除；历史审计保存名称快照。
- `backendPolicyKey` 用于把前端资源与后端接口策略关联起来，并支持覆盖度检查。

## 5. 角色与人员权限模型

### 5.1 角色基线

角色保存默认权限，不保存人员差异：

```ts
interface RoleGrant {
  resourceKey: string;
  value: "hidden" | "visible" | "denied" | "allowed" | "read" | "edit";
}
```

一个人员可绑定多个角色。多个角色之间采用允许优先的并集：

- 页面任一角色可见，则角色基线可见。
- 动作任一角色允许，则角色基线允许。
- 设置项取最高权限：`edit > read > hidden`。

### 5.2 人员例外

人员例外仅保存与角色基线不同的节点：

```ts
type UserOverrideMode = "inherit" | "allow" | "deny";

interface UserPermissionOverride {
  employeeId: string;
  resourceKey: string;
  mode: UserOverrideMode;
  settingAccess?: "read" | "edit";
  reason?: string;
  effectiveFrom?: string;
  expiresAt?: string;
  grantedBy: string;
  updatedAt: string;
}
```

覆盖优先级：

1. 授权天花板、组织视角、产品版本等硬约束；
2. 人员明确禁止；
3. 人员额外允许；
4. 多角色并集；
5. 默认拒绝。

“额外允许”仍不能突破授权人的有效功能权限、数据范围和最高视角。

### 5.3 功能授权天花板与委派生命周期

功能授权天花板采用**授权时快照**，不在每次鉴权时递归读取历史授权人的当前权限。这样既能阻止越权下放，也不会因为上级人员后续调岗造成下属权限静默、大面积中断。

角色绑定与人员例外分别保存授权快照：

```ts
interface FunctionalGrantCeiling {
  grants: Record<string, string>;
  resourceVersion: string;
  capturedAt: string;
  capturedFromEmployeeId: string;
  hash: string;
}

interface StaffRoleBinding {
  employeeId: string;
  roleId: string;
  grantedBy: string;
  grantedAt: string;
  functionalCeiling: FunctionalGrantCeiling;
}

interface UserPermissionOverride {
  // 其余字段同上
  /** 仅 mode = allow 时必填；deny 为降权，不使用功能 ceiling */
  functionalCeiling?: FunctionalGrantCeiling;
}
```

规则如下：

1. 新增角色绑定或人员 `allow` 时，服务端使用授权人**当时的最终有效功能权限**生成不可由客户端提交的 ceiling 快照。
2. 某个角色日后新增权限时，成员通过该角色得到的权限仍不得超过其 `StaffRoleBinding.functionalCeiling`；需要扩大时，由有权管理员重新授权并生成新快照。
3. 多角色、多授权人分别按各自绑定快照裁剪后再合并，因此不会让一个低权限授权人的绑定抬高其他绑定的上限。
4. 人员 `deny` 是降权，不要求目标权限位于授权人允许集合，但操作者仍须具备“管理员工权限”能力及目标人员管理范围。
5. 多级委派时，新一层 ceiling = 授权人当前最终权限；授权人当前最终权限本身已被上一层 ceiling 裁剪，因此权限不能逐级放大。
6. 鉴权不递归遍历 `grantedBy` 链，只消费已验证快照，因而不存在运行时授权环。禁止给自己新增角色或 `allow` 例外；自己降权须走专门确认流程。
7. 授权人后来失去权限或离职时，既有下级授权**不自动级联撤销**，但系统产生“授权来源已失效”风险项，要求有权管理员复核。显式停用账号、紧急撤权或组织安全策略可批量撤销相关授权。
8. ceiling 快照随资源版本迁移；无法映射的新资源默认拒绝。

该设计将 `grantedBy` 保留为审计关系，将 ceiling 快照作为实际计算边界，避免历史人员状态影响在线鉴权的稳定性。

### 5.4 数据范围

继续沿用：

```ts
type StaffStoreAccessMode = "all" | "brands" | "regions" | "stores";

interface StaffStoreAccess {
  mode: StaffStoreAccessMode;
  ids: string[];
}
```

最终业务可操作性同时满足：

```text
功能权限允许
AND 目标数据位于员工有效数据范围
AND 当前视角不超过 maxPerspective
AND 当前筛选位于有效数据范围
```

切换顶栏品牌或门店只改变当前查询范围，不重新计算功能权限。

## 6. 最终权限计算与快照

```text
逐个角色绑定：角色权限 ∩ 该绑定的功能 ceiling
→ 合并所有已裁剪的角色绑定
→ 逐个人员 allow：允许值 ∩ 该 allow 的功能 ceiling
→ 应用人员 allow
→ 应用人员 deny（明确禁止优先）
→ 组织层级 / 产品版本 / 最高视角硬约束裁剪
→ 与数据范围组合
→ 生成最终权限快照
```

不得先合并多个角色再统一裁剪，因为不同角色绑定可能来自不同授权人并带有不同 ceiling。人员 `deny` 是降权，不需要功能 ceiling；人员 `allow` 必须先由自己的 ceiling 裁剪后才参与最终计算。

快照在登录、角色变更、人员授权变更、资源版本变更时重新生成。每个最终节点应能返回解释信息：

```ts
interface EffectivePermission {
  resourceKey: string;
  value: string;
  source: "role" | "user-allow" | "user-deny" | "ceiling" | "default-deny";
  sourceRoleIds?: string[];
  reason?: string;
}
```

所有业务鉴权统一调用权限计算器或读取同版本快照，禁止各页面自行拼接角色判断。

### 6.1 临时权限的时间边界

临时人员例外不能依赖定时任务或重新登录来保证失效。安全执行规则如下：

- 快照保留 `effectiveFrom`、`expiresAt`，但 API 鉴权在每次请求时按服务端时间再次判断有效窗口。
- 未到生效时间或已过期的 `allow` 一律按不存在处理；已过期的 `deny` 同样不再覆盖角色基线。
- 缓存键包含授权版本与时间窗口；缓存有效期不得超过最近一个激活或过期边界。
- 定时任务只负责提前刷新快照、更新界面和写入“已生效/已过期”事件，不作为安全失效的唯一机制。
- 已打开页面在收到版本刷新信号或下一次接口返回 403 时刷新权限状态，并提示权限已变化。
- 服务端时间是唯一依据，客户端时间仅用于倒计时展示。

## 7. 权限中心信息架构

权限中心保留五个入口：

### 7.1 概览与风险

展示：

- 角色数、已授权人员数、人员例外数、高风险授权数。
- 即将过期的临时权限。
- 拥有关键动作的人员，如删除角色、退款、修改支付方式。
- 长期未使用角色、无成员角色、失效资源授权。
- 可下钻到对应角色、人员或权限点。

### 7.2 角色权限

角色列表支持搜索、复制、查看成员、编辑、停用或删除。系统角色不可删除；有关联人员的角色须先迁移成员或停用。

角色编辑器采用：

- 左侧模块导航；
- 右侧按页面展开的权限表；
- 页面行展示可见状态及动作/设置摘要；
- 展开后显示真实业务动作或设置分组；
- 支持搜索、仅看已开放、仅看高风险、仅看差异；
- 支持模块或页面级批量设置；
- 保存前展示受影响人员数及权限差异。

### 7.3 人员权限

编辑顺序固定为：

1. 选择或确认人员；
2. 绑定一个或多个角色；
3. 配置品牌、区域或门店数据范围；
4. 配置最高视角；
5. 必要时增加人员例外；
6. 预览最终生效权限；
7. 填写原因并保存。

人员例外编辑器与角色编辑器共用资源浏览框架，但每项同时展示：

- 角色基线；
- 人员例外；
- 最终生效状态；
- 权限来源或被裁剪原因。

默认只显示“与角色不同”的节点，支持切换查看全部。每项提供“恢复继承”。

当角色变化使某个人员例外暂时与角色基线相同时，系统标记为“当前冗余”，但不自动删除：明确 `deny` 可能是面向未来的安全约束，自动清理会改变角色下次扩权时的结果。概览分别统计“有效差异”和“冗余例外”，由管理员人工恢复继承。

### 7.4 账号与登录

仅处理账号状态、登录方式、创建账号、重置密码、撤销会话，不与业务授权混排。通过人员详情互相跳转。

### 7.5 变更记录

支持按人员、角色、资源、模块、操作人、时间和风险级别筛选。每条记录保存：

- 操作人、对象、时间；
- 变更前后值；
- 变更原因；
- 临时权限有效期；
- 授权链和当时的授权天花板；
- 受影响人员数量。

## 8. 关键交互规则

### 8.1 批量操作

- 模块或页面级批量操作只作用于当前过滤结果时，必须明确标注范围。
- 批量撤销或开放高风险权限前展示影响人数和具体权限项。
- 父级批量操作后允许展开子级进行局部调整。

### 8.2 保存与确认

正常权限展示差异摘要后保存；敏感或关键权限要求填写原因。保存流程：

```text
编辑
→ 查看变更摘要和受影响人员
→ 高风险变更填写原因并确认
→ 服务端校验授权天花板与版本号
→ 保存
→ 刷新受影响权限快照
→ 写入审计日志
```

### 8.3 冲突与并发

- 角色和人员授权记录带版本号。
- 保存时发现版本变化，展示当前编辑与服务端最新值的差异。
- 不允许静默覆盖，管理员需刷新或重新合并。

### 8.4 无权与失效状态

- 导航无权：不展示入口。
- 直接访问无权路由：展示明确无权页，不伪装为 404。
- 动作无权：前端隐藏或禁用；后端返回 403。
- 设置只读：控件不可编辑；提交接口也拒绝修改。
- 权限资源已停用：配置页显示“已失效”，最终结果按拒绝处理。

## 9. 安全边界

1. 所有写接口必须校验对应动作或设置编辑权限。
2. 敏感读接口也必须校验页面或专门的读取权限，不能只依赖侧栏隐藏。
3. 列表查询和详情查询必须同时应用 `storeAccess`。
4. 新增或重新授权时，授权接口必须校验被授权功能权限、数据范围、最高视角均不超过授权人当时的最终有效权限，并生成授权快照；既有授权不持续跟随历史授权人的实时权限变化，授权人后续失权按 5.3 节产生风险复核项。
5. 权限中心自身的“创建角色、编辑角色、删除角色、管理员工授权、查看审计”等能力必须注册为真实动作权限。
6. 防止最后一个超级管理员被停用或撤销关键权限。
7. 角色绑定和人员额外允许必须带服务端生成的功能 ceiling 快照；客户端不得伪造或扩大快照。
8. 临时权限必须在每次 API 鉴权时校验服务端时间窗口，不能只依赖会话快照刷新。

## 10. 迁移方案

### 10.1 映射

- 现有 L1/L2 `enabled` 映射为模块或页面 `visible/hidden`。
- 现有页面动作节点按实际页面能力清单筛选；无真实控制点的节点不迁移为有效动作。
- 现有 L4 `enabled = false` 映射为 `hidden`。
- 现有 L4 `enabled = true + display-only` 映射为 `read`。
- 现有 L4 `enabled = true + editable` 映射为 `edit`。
- 现有角色绑定、`storeAccess`、`maxPerspective`、授权链元数据原样迁移。

### 10.2 切换

1. 建立新资源注册表和统一权限计算器。
2. 编写旧数据映射和一致性校验。
3. 新旧模型并行计算但仍使用旧结果执行。
4. 按账号比较导航、页面、动作、设置项与数据范围结果。
5. 差异归零或人工确认后切换到新结果。
6. 原权限数据保留至少一个回滚周期。

迁移既有角色绑定时，由迁移任务使用当时租户超级管理员或系统迁移主体的有效权限生成初始 `functionalCeiling`，并在报告中标注为“系统迁移快照”。后续人工调整时再替换为实际授权人的快照。

## 11. 验收标准

### 11.1 功能验收

- 无页面权限时侧栏不展示，直接访问路由显示无权状态。
- 无动作权限时前端不可执行，对应 API 返回 403。
- 设置项的隐藏、只读、可编辑状态分别有效，无法绕过前端修改只读项。
- 多角色合并结果符合允许优先规则。
- 人员 `deny` 能撤销角色已有权限，人员 `allow` 能增加权限但不能突破授权天花板。
- 角色变化后继承项自动变化，人员例外继续有效；恢复继承后回到角色基线。
- 功能允许但数据不在范围时，查询与写入都被拒绝。
- 临时人员权限到期后自动失效并记录事件。
- 临时权限即使在会话未刷新、定时任务延迟的情况下，也会被 API 按服务端时间拒绝。
- 角色后续扩权不会突破成员绑定时保存的功能授权天花板。
- 多级委派和多授权人场景中，任何新增权限都不能超过对应授权路径的快照上限。
- 多角色计算必须先逐绑定按各自 ceiling 裁剪，再合并结果。

### 11.2 安全验收

- 所有受控写接口均有后端鉴权覆盖。
- 未注册或失效权限键默认拒绝。
- 无法将权限、数据范围或最高视角授予到授权人范围之外。
- 无法撤销系统最后一个可用超级管理员。
- 并发修改不会发生静默覆盖。
- 授权人后续失权不会造成未声明的自动级联撤销，但会产生可处理的风险项。

### 11.3 审计验收

- 每次角色、人员例外、数据范围和最高视角变化均记录前后值。
- 可按人员、角色、权限点和操作人查询。
- 记录能解释最终权限来源和授权链。
- 资源改名或停用后，历史记录仍可读。

### 11.4 迁移验收

- 新旧模型对现有账号的最终权限比对有自动报告。
- 所有差异均有归因和处理结论。
- 切换前完成核心角色和高风险账号抽样走查。
- 保留可验证的回滚路径。

## 12. 实施分期

| 阶段 | 内容 | 结果 |
|---|---|---|
| P0 | 统一资源注册表、真实动作清单、权限计算器 | 形成可信权限内核 |
| P1 | 重做角色列表和角色权限编辑器 | 角色基线可高效配置 |
| P2 | 人员例外、最终权限预览、临时权限 | 支持差异化人员控制 |
| P3 | 后端 API 鉴权覆盖、版本冲突、完整审计 | 形成安全闭环 |
| P4 | 风险看板、权限诊断、长期治理能力 | 降低运营与审计成本 |

P0 是所有后续工作的前置条件。P1 与 P2 可共用权限编辑器组件，但应先完成角色编辑，再开放人员例外。P0 至 P2 均以内部或暗发布方式运行；P3 后端鉴权覆盖、迁移比对和回滚演练完成前，不启用新模型作为生产安全边界，也不把前端隐藏宣称为完整权限控制。

- `src/permissions/rbac-store-factory.ts`：增加统一权限计算、来源解释和迁移适配。

- `src/permissions/nav-access.ts`：改为消费统一最终权限结果。

## 14. 非目标

- 本期不引入复杂条件策略语言或通用 ABAC 规则编辑器。
- 本期不允许人员维护一份完全独立于角色的完整权限矩阵。
- 本期不把数据范围合并进功能权限树。
- 本期不支持通过 UI 自定义新的权限资源键；资源必须由产品代码注册。

## 15. 最终决策摘要

1. 采用“角色基线 + 人员例外”。
2. 人员例外使用“继承 / 额外允许 / 明确禁止”三态，明确禁止优先。
3. 权限按资源类型表达：模块/页面可见，动作允许，设置项隐藏/只读/可编辑。
4. 权限编辑器采用“左侧模块导航 + 右侧可展开权限表”。
5. 权限中心由概览与风险、角色权限、人员权限、账号与登录、变更记录组成。
6. 功能权限与品牌/区域/门店数据范围继续分离。
7. 所有最终权限必须可解释，所有关键变更必须可审计，所有前端限制必须由后端校验兜底。
8. 功能授权天花板使用服务端生成的授权时快照；授权人后续失权触发风险复核，不做隐式级联撤销。
9. 临时权限由 API 请求时的服务端时间校验强制失效，定时刷新仅用于体验与审计。
