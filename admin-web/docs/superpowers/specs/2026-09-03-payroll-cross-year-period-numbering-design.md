# 薪资年度与跨年 Period 编号设计

## 背景

薪资管理当前将每个自然年首个完全落在该年的 Sun–Sat 双周区间编号为第 1 期，因此 `01/04/2026–01/17/2026` 被标记为 2026 第 1 期。业务口径要求按周期结束年份归属：跨年区间 `12/21/2025–01/03/2026` 才是 2026 第 1 期，上述区间应为第 2 期。同时，年份筛选需要始终支持当前年份的下一年。

## 已确认口径

- 薪资周期固定为 14 天，周日开始、周六结束。
- 周期年度取结束日期所在年份。
- 同一年度内，按结束日期升序从 1 连续编号。
- 2026 第 1 期为 `12/21/2025 (Sun) – 01/03/2026 (Sat)`。
- 2026 第 2 期为 `01/04/2026 (Sun) – 01/17/2026 (Sat)`。
- 跨年周期只属于结束日期所在年度，不在两个年度重复出现。
- 年份选项至少覆盖既有起始年度 2025 至运行时当前年份加 1；2026 年运行时必须展示 2027。

## 方案

采用单一连续周期基准，而不是为每个自然年写死起始日期。

以已确认的 `12/21/2025` 为双周锚点，按 14 天向前或向后生成周期。生成目标年份时，保留结束日期落在目标年份内的周期，再按结束日期排序并编号。该算法允许某些年度自然产生 26 或 27 期，不强制截断为 26 期。

每个周期继续使用 `p{year}-{两位期数}` 作为 ID，例如 `p2026-02`。详情标题、年份/期数筛选、员工数据索引、导出内容和状态统计都读取同一份周期对象，禁止各自重新推算编号。

## 数据生成与迁移

`buildPresetPeriods` 根据运行时年份动态生成 2025 至下一年的周期。演示状态映射继续按目标周期 ID 应用。

旧缓存中所有受影响周期都必须按日期范围迁移，不能只给 2026 的编号加一。例如旧 `p2025-26` 会跨年重键为新 `p2026-01`，旧 `p2026-26` 会重键为新 `p2027-01`。迁移必须从不可变的旧快照构建全新的周期、员工和选择状态，禁止在原对象上依次改键，以免 `p2026-01 → p2026-02 → p2026-03` 形成覆盖链。

日期解析规则：优先读取有效的 `startDate` 与 `endDate`；否则从 `rangeLabel` 解析两个 `MM/DD/YYYY` 日历日期。必须严格校验年月日、14 天长度和 Sun–Sat 边界，并转换为不含时区的标准键 `YYYY-MM-DD/YYYY-MM-DD`。日期加减使用本地日历字段或 UTC 日历运算，禁止用可能受 DST 影响的毫秒差直接判定天数。

迁移顺序为：

1. 深拷贝旧 `periods`、`employees` 和顶层选择状态；在替换周期列表前，捕获旧 `periodId` 对应的标准日期键。
2. 为可解析旧周期建立“日期键 → 旧周期”索引。重复日期键视为冲突：保留首个有效周期用于展示，其余记录进入隔离数据，不静默合并。
3. 创建全新的目标周期列表。新周期只按完全相同的日期键继承旧状态；目标 ID 相同但日期不同不构成匹配。
4. 创建全新的 `employees` 映射，按日期键将旧员工数组写入目标 ID。若目标已有初始化数据，迁移数据优先；同一来源数组原样保留，不按员工 ID 合并，避免修改用户内容。
5. 对已知旧 schema 但缺少可解析 `rangeLabel` 的周期，可通过旧版本的年度起始规则和旧 ID 重建日期，校验通过后再迁移。不能证明日期语义一致时，禁止按相同 ID 回退。
6. 无法解析、超出当前支持年份或发生重复日期冲突的数据放入专用的兼容隔离字段，保持原周期元数据和员工数组完整，不进入当前筛选列表，也不覆盖有效目标数据。
7. 用捕获的旧选择日期键解析新 `periodId`；成功时同步年度与期数筛选并保留仍存在的 `employeeId`，否则清空无效员工选择并使用确定性回退：优先选择有员工数据的周期，再按开始日期倒序取最近一期。
8. `periodNumberFilter` 更新为新期数；`periodYearFilter` 与 `workspacePeriodYearFilter` 更新为新归属年度。空筛选值保持为空，不强制写入。
9. 新快照以完整旧快照为基础，只替换明确迁移的 `periods`、`employees` 和选择字段；`coCode` 及未知扩展字段原样保留。
10. 使用同一份“旧周期 ID/日期键 → 新周期 ID”映射更新 `auditLog[].periodId`。无法可靠映射的审计条目保留原 ID，并附加 legacy 标记，禁止将它错误关联到日期不同的新同名 ID。

迁移必须是幂等的：重复加载不会继续移动员工数据，也不会覆盖用户已编辑内容。

演示状态和演示员工仅用于完全没有迁移来源的新周期。已迁移员工及其确认状态优先；若周期状态由员工状态汇总推导，则以迁移后的员工为准，不再使用按目标 ID 配置的演示状态覆盖。

## 界面行为

- 年份下拉按升序展示支持年度，包含下一年。
- 切换到未来年度时，Period 下拉展示该年度实际生成的全部期数。
- 当前选择如果在重新生成或迁移后仍能按日期范围定位，则自动切换到对应的新周期 ID。
- 若无法定位，则使用现有安全回退逻辑选择有员工数据的最近周期，避免空白或崩溃。

## 验收与测试

- 2026 年选项中存在 2027。
- `12/21/2025–01/03/2026` 为 2026 第 1 期。
- `01/04/2026–01/17/2026` 为 2026 第 2 期。
- 年末到次年年初的相邻周期连续、无重叠、无缺口，每期恰好 14 天且为 Sun–Sat。
- 2027 年可选择，首期按结束年份口径计算。
- 2027 共 26 期；2028 是锚点后的首个 27 期年度：`p2028-01` 为 `12/19/2027–01/01/2028`，`p2028-26` 为 `12/03/2028–12/16/2028`，`p2028-27` 为 `12/17/2028–12/30/2028`，下一周期 `p2029-01` 为 `12/31/2028–01/13/2029`。周期连续、无缺口。
- 旧 `p2026-01` 中属于 `01/04/2026–01/17/2026` 的员工、状态及调整项迁移到新 `p2026-02`，重复迁移结果不变。
- 旧 `p2025-26` 迁移为新 `p2026-01`，旧 `p2026-26` 迁移为新 `p2027-01`。
- 当前选择旧 `p2026-01` 时迁移为新 `p2026-02`；选择旧 `p2026-26` 时迁移为新 `p2027-01`，并同步年度、期数和仍有效的员工选择。
- 自动化测试覆盖：目标 ID 已有初始化数据、重复日期范围、重复员工 ID、日期无法解析、超出支持年份的数据隔离；迁移前后被迁移内容深度相等，连续迁移两次结果不变。
- `coCode`、审计日志及任意未知扩展字段迁移后仍存在；可映射审计条目指向新周期 ID，隔离周期对应的审计条目保留旧 ID 且标记为 legacy。
- 在运行时年份从 12 月 31 日切换到 1 月 1 日时，年份选项重新计算并包含新的下一年，但已有历史年度和当前有效选择不丢失。
- 页面选择 Period 2 后，主卡片、详情、导出均显示相同编号和日期范围。

## 非目标

- 不改变双周周期长度、周起止日或 Paycheck Date 的“结束日加 6 天”规则。
- 不引入后端薪资日历配置。
- 不调整薪资页面的视觉布局。
