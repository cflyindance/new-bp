# 从原型代码导出产品 PRD + 技术规格 — 设计方案

> **状态**：已落地（Skill / 模板 / README / Rule）  
> **日期**：2026-07-28  
> **范围**：admin-web 仓库内的导出机制（Skill + 模板 + 产物约定）  
> **非目标**：不自动改业务代码；不替代真实后端契约评审；不一次盲扫整仓

---

## 1. 背景与目标

产品经理通过 Cursor vibe coding 已在本仓库实现业务场景、字段、状态与分支逻辑。希望 **不再对着原型手写完整 PRD**，而是由 Cursor 从已实现内容逆向产出可交给研发的 Markdown；研发再将文档投入常用开发工具完成工程实现。

### 1.1 成功标准

- PM 只需指定导出范围（可选补少量业务意图），即可得到完整文档套件
- 研发拿到 SPEC 能独立开工，少追问字段 / 状态 / 异常
- 意图与实现不一致时，浓缩在 DIFF 中由 PM 拍板
- 输出格式稳定，可被工程侧 AI 工具直接消费

### 1.2 已确认决策

| 决策点 | 结论 |
|--------|------|
| 文档形态 | **双文档**：产品 PRD + 技术规格；另附 DIFF |
| 主投喂对象 | 研发工具以 **SPEC.md** 为主；PRD 作场景与验收上下文 |
| 导出范围 | **灵活**：模块 / 页面路由 / 目录文件，导出时指定 |
| 触发方式 | **项目 Skill + 固定模板**（保留 `generate_spec.md` 作手动兜底） |
| 内容准绳 | **双轨对照**：PRD=意图与验收；SPEC=实现细节；不一致进 DIFF |

## 2. 整体架构

### 2.1 工作流

```
想法 → Cursor vibe coding 实现原型
     → 用户：「导出 PRD/规格」+ 范围
     → Skill 按清单扫代码与现有文档
     → 输出 PRD.md + SPEC.md + DIFF.md
     → PM 裁决 DIFF / 开放问题
     → 研发以 SPEC 为主实现工程代码
```

### 2.2 仓库落点

```
admin-web/
├── .cursor/skills/export-prd-spec/
│   ├── SKILL.md                      # 触发条件 + 固定执行步骤 + 质量门禁
│   ├── references/
│   │   ├── prd-template.md           # 产品 PRD 章节模板
│   │   ├── spec-template.md          # 技术规格章节模板
│   │   └── analysis-checklist.md     # 从代码要挖掘的证据类型
│   └── examples/
│       └── tipout-mini.md            # 对照现有 TipOut PRD 的精简样例
│
└── docs/产品PRD/
    ├── README.md                     # PM 用法说明
    ├── generate_spec.md              # 手动兜底提示词（与 spec-template 对齐）
    └── exports/                      # 导出产物根目录
        └── YYYY-MM-DD-<scope-slug>/
            ├── PRD.md
            ├── SPEC.md
            └── DIFF.md
```

### 2.3 产物职责

| 产物 | 读者 | 内容重心 |
|------|------|----------|
| PRD.md | 产品 / 设计 / 研发对齐 | 场景、角色、范围、用户故事、验收标准 |
| SPEC.md | 研发 / 工程 AI | 字段、状态机、校验、分支、接口契约、伪代码 |
| DIFF.md | PM 决策 | 意图 vs 实现差异、推测项、建议处理 |

## 3. 文档大纲

### 3.1 PRD.md

1. 文档元信息 — 范围、版本、日期、关联代码路径、关联现有设计文档  
2. 背景与目标 — 问题与目标（缺上下文标「待产品补充」）  
3. 角色与权限边界 — 使用者与集团/品牌/门店视角  
4. 范围边界 — In / Out  
5. 核心业务场景 — 主流程 + 关键分支（Mermaid）  
6. 功能需求清单 — 编号表（筛选/展示/操作/校验/空状态等）；表格列结构与粒度对齐 TipOut PRD（`dist/TipOut/docs/PRD_产品需求文档.md` 的「编号/类型/描述/关联」），**编号格式以 §3.4 为准**（不用 `P1-01` 页面前缀）  
7. 用户故事与验收标准 — Given / When / Then  
8. 页面/入口清单 — 路由或模块入口、依赖关系  
9. 非功能与约束 — 多语言、权限、下发/保存、产线差异（有则写）  
10. 开放问题 — 需 PM 拍板的项  

### 3.2 SPEC.md

1. 规格元信息 — 对应 PRD 路径、代码证据路径、技术栈假设  
2. 术语与枚举 — 常量/枚举及含义  
3. 数据模型 — 字段表（名/类型/必填/默认/校验/说明）  
4. 状态机 — 状态列表、流转条件、非法流转处理  
5. 核心业务逻辑 — 输入/输出/伪代码步骤/异常；互链 PRD 编号  
6. 交互与 UI 契约 — 控件行为、空态、禁用、文案键（不写视觉稿）  
7. 接口/存储契约 — 现有 API、localStore、mock；工程实现建议契约  
8. 权限与作用域 — RBAC / Scope 判定点  
9. 边界与并发 — 重复提交、无数据、跨页依赖  
10. 实现检查清单 — 从 PRD AC 映射的可勾选项  

### 3.3 DIFF.md

| 类型 | 说明 |
|------|------|
| 代码有、意图未写清 | Spec 已写，PRD 待补 |
| 意图有、代码未做 | PRD 有，标「原型未实现」 |
| 行为冲突 | 两侧不一致，需 PM 裁决 |
| 推测项 | 从命名/分支推断，置信度低 |

每条须含：证据路径（文件+符号）、建议处理（补 PRD / 改代码 / 接受现状）。

### 3.4 需求编号

- 格式：`<SCOPE前缀>-<序号>`，如 `TIP-01`、`SCHED-12`  
- **前缀推导**：取 `scope-slug` 的字母数字，压缩为大写 3～5 位（优先可读缩写：`tipout`→`TIP`，`team-shift-scheduling`→`SCHED`）；同一次导出内前缀固定；多页面导出时序号在该 scope 内全局递增，不嵌套页面前缀  
- PRD / SPEC / DIFF 共用同一编号体系  
- 一经发布尽量稳定；删除用「废弃」标记，不复用编号

## 4. Skill 执行流程

### 4.1 触发示例

- 「导出 PRD/规格：TipOut」
- 「按页面导出：排班表」
- 「分析 `src/config/team-shift-scheduling-ui.ts` 并导出」

未给范围时：**先问清范围**，禁止整仓盲扫。

### 4.2 固定步骤

1. **定范围** — 解析模块/页面/路径；大范围先列文件清单请用户确认  
2. **收证据** — 按 analysis-checklist 读取代码与 `docs/` 设计稿  
3. **建需求编号** — 为能力点分配稳定 ID  
4. **写 SPEC** — 以代码为准，先落实现细节  
5. **写 PRD** — 回写场景与验收；缺意图标「待产品补充」  
6. **写 DIFF** — 列出差异与建议  
7. **自检门禁** — 未通过则补挖，不直接交差  
8. **交付** — 写入 exports 目录；向用户摘要开放问题与需拍板项  

### 4.3 本仓库分析优先级

```
types / enums / constants
  → store / factory / api mock
  → *-ui.ts 交互与校验
  → permissions / scope
  → 路由与导航注册
  → docs/项目文档、docs/superpowers 已有设计
```

隐式规则重点：`if` / `switch`、禁用条件、空态、默认值、产线与视角差异。

### 4.4 质量门禁

| 门禁 | 要求 |
|------|------|
| 证据可追溯 | 关键字段/状态/分支注明代码路径或符号 |
| 编号闭环 | PRD 每条需求在 SPEC 有对应；SPEC 能指回 PRD ID |
| 无空章节滥竽 | 不适用写「N/A + 原因」；不编造 API/表结构 |
| 推测显式化 | 推断项进 DIFF 并标置信度 |
| 研发可执行 | SPEC 含字段表 + 状态/分支 + 异常处理 |
| 语言 | 简体中文；代码标识符保留英文原名 |

### 4.5 PM 最小介入

- 导出前：给范围（可选补 2～3 句业务目标）  
- 导出后：只处理 DIFF / 开放问题  
- 裁决后可说「根据裁决更新 PRD/SPEC」再出一版  

### 4.6 与 generate_spec.md

保留为手动兜底提示词；内容与 `spec-template.md` 对齐，避免两套标准。

## 5. 命名、版本与交付

### 5.1 目录命名

```
docs/产品PRD/exports/YYYY-MM-DD-<scope-slug>/
```

- `scope-slug`：小写英文或拼音短横线  
- 同日同范围再导出：加 `-v2`、`-v3`，**不覆盖**旧目录  

### 5.2 版本策略

| 场景 | 做法 |
|------|------|
| 原型逻辑变更需同步文档 | 新建导出目录或升 `vN`；元信息写代码依据日期/commit |
| 仅裁决 DIFF | 可原地更新三份；文首变更记录加一行 |
| 部分范围导出 | 元信息写清包含/排除文件 |

文首统一字段：范围、版本、导出日期、代码依据、PRD/SPEC 互链。

### 5.3 交给研发

1. 主投喂 `SPEC.md`；可附 `PRD.md` 作验收上下文  
2. 对齐会用 PRD 讲场景与 AC，用 DIFF 清开放问题  
3. 推荐开场白：

> 请严格按 SPEC 实现工程代码；验收以 PRD 的 Given/When/Then 为准。  
> DIFF 中未关闭项不要擅自发明，标为待确认。  
> 原型代码仅作行为参考，最终以 SPEC 契约为准重写/接入真实服务。

### 5.4 可选轻量 Rule

当用户要求「导出 PRD/规格」时，遵循 `export-prd-spec` Skill，输出到 `docs/产品PRD/exports/`，不得只写摘要不写完整三件套。

## 6. 落地实现范围（获批后执行）

实现本设计时，仅新增/调整以下内容：

1. `.cursor/skills/export-prd-spec/`（SKILL + references + 精简 example）  
2. `docs/产品PRD/README.md`  
3. `docs/产品PRD/exports/.gitkeep`（或说明目录）  
4. 将现有 `docs/产品PRD/generate_spec.md` 与 `spec-template.md` 对齐演进  
5. （可选）一条短 Cursor Rule  

**不在首期范围**：类型抽取脚本、CI 自动导出、整仓批量生成。

## 7. 风险与缓解

| 风险 | 缓解 |
|------|------|
| 原型逻辑散落、漏挖 | checklist + 质量门禁；大范围先出文件清单 |
| AI 编造接口/表 | 禁止无证据断言；无则 N/A 或「建议契约」并标推测 |
| PRD 缺少商业 Why | 允许「待产品补充」；不阻塞 SPEC 交付 |
| 文档与代码漂移 | 版本目录不覆盖；变更后重新导出或升 vN |
