# 项目级开发规则

## eMenu 嵌入包构建与发布

- 修改 `vendor/emenu-new` 下的任何源码后，不得只执行 eMenu 子项目中的 `npm run build`。
- 必须从本项目根目录执行以下命令，构建并发布 eMenu 嵌入包：

  ```bash
  npm run build:emenu-new-embed -- --skip-install
  ```

- 上述命令必须把最新产物发布到 `dist/emenu-new`；仅生成 `vendor/emenu-new/build` 不视为完成。
- 构建完成后，必须检查：

  1. `dist/emenu-new/index.html` 已更新并引用本次构建生成的哈希资源。
  2. `dist/emenu-new/.emenu-embed-build.json` 存在，且 `builtAt` 已更新为本次构建时间。
  3. 构建命令成功退出；如有错误，必须修复后重新构建。

- 对 eMenu 页面进行浏览器验证前，必须重新加载 eMenu iframe。若页面仍使用旧资源，应执行浏览器强制刷新后再验证。
- 未完成嵌入包构建、发布及上述产物校验时，不得将相关 eMenu 代码修改汇报为已完成。

## 产品 PRD 与研发交付版双权威文档维护（强制）

### 适用范围与文档分工

- 本项目所有模块的新增需求、功能调整、业务规则、字段、交互、文案、状态、计算、权限、异常与验收口径变更，必须在同一次任务交付中同时输出或更新两份权威文档，不需要用户再次提醒。
- 产品 PRD 是产品范围、业务目标、用户场景、交互、业务规则和验收口径的权威；研发交付版是同一需求的字段定义、对象关系、状态流转、计算过程、数据口径、异常边界和测试算例的权威。
- 两份文档是一套业务定义的两种视角，不是两个可各自决定业务的来源。研发版不得自行新增或覆盖产品决策；代码只是实现证据，不得自动覆盖已确认需求。
- 每个功能模块维护唯一一对文档；新模块复用既有产品 PRD，并创建对应《<模块名>业务规格说明书（研发交付版）》；没有既有文档时成对建立。其他模块不得写入小费文档，不按每次任务复制出新的“最终版”。
- 两份文档顶部必须互相链接，声明范围、状态、配对版本与同一变更编号。历史副本、归档和实现计划不是新增权威入口。

### 每次变更的执行要求

1. 开始前定位实际工作检出目录，读取该模块两份权威文档及版本记录；只有一份时补齐另一份。发现多个候选或缺失文件时先确认来源，不从同名旧副本推断最新版。
2. 先明确已确认变更、影响模块和待确认项，再同步更新两份正文的对应章节。小改动只改受影响内容，不重写全文，不只在文末追加相互覆盖的说明。
3. 产品 PRD 更新业务目的、范围、页面行为与验收；研发版同步展开字段含义、类型、单位、必填／默认／空值、来源、编辑限制、对象关系、状态前后条件、成功／失败写入、公式、精度、计算顺序和正常／边界／异常算例。无关项明确不适用，不为凑模板新增业务。
4. 每次产品或功能语义变更，两份文档各自递增版本、最新记录置顶、保留历史；使用相同变更编号（如 TIPOUT-20260930-01），记录对方对应版本及本次实际变化，版本号不必相同。仅排版／不改含义的错字修正可不升版，但必须核对另一份是否受影响。
5. UI 文案、字段名称、示例、图示、导出与汇总口径若受影响，也必须同步核对；不适用的旧表述应从有效正文移除或标为历史，不能继续与新规则并列生效。
6. 两份文档冲突时，优先追溯用户明确确认的最新决策，并同步修正；无明确依据则在两份文档中关联同一待确认项，说明影响，不能擅自选择或声称已可实施。文档治理变更不自动批准旧待确认项。
7. 实现与文档不一致时明确区分“已确认待实现”“实现偏差”“待确认”；纯修复既定行为且产品定义未变时，核对两份文档并在适用的实现／验证状态中同步记录，不编造新需求。
8. 回退业务方案时同步回退两份文档的有效定义，保留变更记录与原因；不默认执行代码、数据或 Git 历史回退。用户明确限定只处理一份时尊重该例外，并报告另一份的同步缺口。

### 交付检查

- 两份文档可定位、相互链接有效，配对版本和变更编号一致。
- 字段、枚举、状态、参与范围、公式、金额方向、统计范围与异常行为没有新增冲突；算例可复算。
- 待确认项保持同一状态；既有历史差异须明确登记，不因本次小改动宣称全部已解决。
- 最终回复列出两份文档链接、版本、变更摘要、校验情况及未闭合事项；缺少任一份的同步不得报告需求文档交付完成。
- 用户授权提交时，将本次相关两份文档与必要图示纳入同一提交；本规则不自动授权提交、合并、推送、上线或修改线上文档。
